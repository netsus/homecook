# 무먹 · Homecook

**집밥은 맛있게 먹고, 기록은 덜 번거롭게.**

무먹은 레시피 한 번 등록으로 **요리 계획·장보기·재료 관리·식단 기록**을 연결해, 같은 정보를 다시 입력하는 번거로움을 줄이는 서비스입니다.

현재 핵심 흐름을 개발하고 베타테스트를 준비하고 있습니다. 이 README의 제품·사업 계획과 수요조사 수치는 2026년 9월 17일 최종 지원서 기준이며, 구현과 운영의 최신 기준은 [공식 문서 인덱스](docs/sync/CURRENT_SOURCE_OF_TRUTH.md)를 따릅니다.

## 왜 만들었나요?

무먹은 부부가 함께 집밥을 준비하고 식단을 기록하며 겪은 불편에서 출발했습니다. 2024년 10월부터 섭취 칼로리를 기록하면서, 한 번의 식사를 위해 같은 재료와 사용량을 여러 곳에 입력해야 했습니다.

| 집밥 과정 | 직접 겪은 불편 |
| --- | --- |
| 메뉴와 레시피 선택 | 집에 있는 재료를 확인하고 만들 수 있는 메뉴를 다시 찾기 |
| 장보기 준비 | 레시피의 재료를 메모·노션의 장보기 목록으로 옮기기 |
| 요리 | 영상을 반복해서 확인하고 실제 사용한 재료와 양을 따로 정리하기 |
| 식단 기록 | 같은 재료를 식단 앱에서 다시 검색·입력하고 먹은 양에 맞춰 계산하기 |

한 번의 식사를 위해 만든 정보가 다음 단계로 이어지도록, 레시피의 재료와 양을 집밥 준비부터 개인의 섭취 기록까지 재사용하는 구조를 만들고 있습니다.

## 누구를 위한 서비스인가요?

초기 고객 가설은 **집에서 주기적으로 요리하며 칼로리·영양성분을 기록하고, 여러 도구에 재료와 사용량을 반복 입력하는 사용자**입니다.

계획·장보기 과정의 불편이 큰 사용자와도 반응을 비교합니다. 실제로 입력 부담이 줄고 다른 식사에서도 반복 사용이 나타나는 흐름을 확인해, 집중할 고객과 기능을 좁힐 계획입니다.

## 집밥 정보를 어떻게 연결하나요?

1. **레시피 등록** — 레시피의 재료와 양을 등록해 이후 과정에서 활용합니다. 직접 입력과 YouTube 레시피 가져오기 흐름을 개발하고 있습니다.
2. **요리 계획** — 만들 메뉴와 인분을 계획하고, 보유한 재료를 확인합니다.
3. **장보기** — 계획에 필요한 재료 중 구매할 재료를 모아 목록을 만들고, 구매 정보를 팬트리 관리로 연결합니다.
4. **요리와 재료 관리** — 실제 사용한 재료와 양을 반영하고, 요리한 음식의 정보를 보관합니다.
5. **식단 기록** — 레시피·요리 정보를 재사용해 실제 먹은 양에 맞춰 영양성분을 기록합니다.

차별화하려는 지점은 레시피의 재료와 양을 **계획·구매·실제 요리·개인의 섭취 기록까지 재사용하는 범위**입니다. 보유 재료를 활용해 추가로 구매할 재료가 적은 순서로 레시피를 확인하는 흐름도 포함합니다.

### 필요한 만큼 선택하는 기록 수준

| 기록 방식 | 입력과 활용 |
| --- | --- |
| 간편 기록 | 등록된 레시피 정보를 그대로 활용 |
| 실제 재료 반영 | 요리에 실제로 사용한 재료와 양으로 수정 |
| 섭취량 반영 | 완성 음식의 총무게와 먹은 무게로 전체 영양성분 중 섭취한 비율 계산 |

예를 들어 완성 음식이 600g이고 250g을 먹었다면, 전체 영양성분의 약 41.7%를 섭취한 것으로 계산합니다. 모든 사용자에게 무게 측정을 요구하지 않고 필요한 수준의 기록을 선택하도록 설계합니다.

영양성분은 입력한 재료 정보와 섭취 비율에 기반한 **추정값**입니다. 조리 중 영양 변화나 손실을 직접 측정한 값은 아닙니다. 가공식품도 함께 기록할 수 있도록 식약처 공공데이터를 바탕으로 **가공식품 데이터베이스 304,347건**을 구축했습니다. 이 수치는 지원서 작성 시점 기준이며 저장소를 내려받는 것만으로 해당 데이터 전체가 설치되지는 않습니다.

### 함께 쓰는 주방, 각자의 식단 기록

가족·룸메이트가 요리 계획·장보기·팬트리·요리한 음식을 공유하고, 각자 먹은 양에 맞춰 식단을 기록하는 구조를 설계했습니다. 한 사람이 만든 음식을 다른 구성원이 재료를 다시 입력하지 않고 기록하는 것이 목표입니다. **공동 주방 공유 기능은 아직 미구현이며 후속 개발 과제입니다.**

| 베타 운영 | 광고·설문·서비스 체험과 알림 신청 수집 | 핵심 흐름 안정화, 로그인·권한·데이터 보호 점검 후 참여자 초대 |

## 초기 수요조사

두 차례 광고·수요조사에서 설문, 서비스 체험, 베타 알림 신청을 진행했습니다.

| 조사 | 유입 | 설문 완료 | 서비스 체험 | 베타 알림 신청 | 유입 대비 신청률 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1차 · 집밥 식단 기록 | 136명 | 38명 | 26명 | 9건 | 6.6% (9/136) |
| 2차 · 집밥 흐름 | 106명 | 24명 | 14명 | 6건 | 5.7% (6/106) |

2차의 **별도 기록형 광고에서 발생한 신청 1건**을 더하면 전체 베타 알림 신청은 **16건 = 9건 + 6건 + 1건**입니다. 별도 1건을 집밥 흐름 조사 106명의 전환율에 합산하지 않습니다.

설문에서 확인한 초기 신호는 다음과 같습니다.

- **기록의 반복 입력·검색:** 기록 조사 응답자 38명 중 35명(92.1%)이 불편을 경험했습니다. 알림 신청 9건 모두 ‘재료·양 입력’ 또는 ‘비슷한 음식 검색’을 가장 불편해한 집단에서 나왔습니다.
- **계획·장보기의 불편:** 집밥 흐름 조사 응답자 24명 모두 준비 과정에서 불편을 선택했습니다. 알림 신청 6건 중 5건은 계획·장보기 불편 집단에서 나왔습니다.

이 결과는 소규모 광고 표본의 초기 관심을 보여줍니다. **알림 신청 16건은 실제 베타 참여자 수·활성 사용자 수·유료 고객 수를 뜻하지 않습니다.** 모집단 전체의 수요나 실제 시간 절약, 반복 사용, 지불 의사는 후속 검증 대상입니다.

## 수익모델 가설

기본적인 요리 계획과 식단 기록은 무료로 제공하고, 반복 이용자가 편의에 비용을 지불하는지 검증할 계획입니다. 아래는 사업화 가설이며, 구독료·포인트 가격과 제공 한도는 아직 확정하지 않았습니다.

| 모델 | 검증할 내용 |
| --- | --- |
| 월 구독 | YouTube 레시피 추출의 사용 한도를 확대하는 혜택부터 지불 의사와 실제 결제 확인 |
| 추가 이용 포인트 ‘무’ | 비정기 이용자나 구독 한도 초과 이용자의 추가 사용량 구매 방식 검토 |
| 장보기 제휴 | 실제 구매 수요와 제휴 가능 조건을 확인한 뒤 상품 링크·수수료 모델 검토 |

AI 식사 계획·식단 상담은 핵심 흐름의 반복 이용을 확인한 뒤 개발·고도화할 후보입니다. 테마·프로필 꾸미기 같은 부가 상품은 후순위로 둡니다.

무료 체험 지급량과 가격은 기능별 운영 비용을 고려해 정합니다. 가격·이용 한도를 명시한 소규모 유료 실험으로 결제율·재구독률을 확인하고, 사용자당 AI 사용 비용·서버 비용·결제 수수료를 함께 검토합니다.

## 단계별 개발·검증 계획

고정된 주차별 마감 대신 **핵심 작업의 완료와 실제 사용 결과**에 따라 다음 단계로 진행합니다. 참여자의 평소 요리 빈도를 고려해 여러 번 사용할 기회를 확보하고, 결과에 따라 기능 범위와 출시 시점을 조정합니다.

| 단계 | 진행 내용 | 다음 결정을 위한 확인 사항 |
| --- | --- | --- |
| 1. 핵심 기능 안정화·직접 사용 | 부부가 실제 집밥 준비·기록에 사용하며 레시피→계획→장보기, 실제 재료→기록 흐름 점검 | 주요 오류를 해결하고 핵심 작업을 끝까지 완료할 수 있는지 |
| 2. 클로즈드 베타 | 알림 신청을 바탕으로 참여자를 초대하고 요리 빈도·불편·사용 행동 확인 | 첫 완료, 다른 식사에서의 재사용, 작업 시간·재입력 횟수·중단 이유 |
| 3. 공개 베타·수익모델 검증 | 반복 사용과 개선 과제를 파악한 뒤 소규모 광고로 추가 모집, 가격·한도를 명시한 유료 실험 | 기존·신규 참여자의 실제 사용, 결제율, 이용량과 운영 비용 |
| 4. 정식 출시·확장 | 검증 결과로 출시 범위·가격 결정, 가족 공유 구현과 장보기 제휴 검토 | 첫 사용 완료율·반복 사용률·결제율·재구독률 |

의견은 기존 소통 도구를 활용한 소규모 커뮤니티와 인터뷰로 수집합니다. 반복 사용이 약하면 고객 가설과 사용 흐름을 보완하고, 계획·장보기에서 더 뚜렷한 반응이 나타나면 해당 흐름의 우선순위를 높입니다.

재료 활용과 공동 관리가 중복 구매, 남는 재료, 특정 구성원에게 몰리는 준비 부담을 줄이는지도 사용 전후 사례와 인터뷰로 확인할 계획입니다.

Supabase 운영·개발 기준은 [로컬 전용 운영 문서](docs/engineering/supabase-local-only-operations.md)에 있습니다. YouTube 백그라운드 추출은 별도 로컬 worker 구성이 필요하며, [worker 운영 문서](docs/engineering/youtube-extraction-worker-runbook.md)를 따릅니다.

## 개발 시작하기

### 설치와 로컬 실행

Node.js와 저장소에 지정된 pnpm 버전을 준비한 뒤 의존성을 설치합니다.

```bash
git clone https://github.com/netsus/homecook.git
cd homecook
pnpm install --frozen-lockfile
```

개인 데이터·인증 기능을 사용하려면 로컬 Supabase와 환경 설정이 필요합니다. [환경변수 예시](.env.example)와 [로컬 운영 기준](docs/engineering/supabase-local-only-operations.md)을 확인하고, 개발용으로 분리된 로컬 환경을 준비합니다. 운영 데이터가 있는 환경을 초기화하지 않습니다.

로컬 Supabase 환경이 준비된 경우:

```bash
pnpm dev:local-supabase
```

이미 필요한 환경변수가 구성되어 있다면 일반 Next.js 개발 서버를 사용할 수 있습니다.

```bash
pnpm dev
```

기본 개발 주소는 `http://localhost:3000`입니다. 외부 API나 worker가 필요한 기능은 각 기능의 별도 설정까지 완료해야 동작합니다.

### 주요 검증 명령

| 명령 | 용도 |
| --- | --- |
| `pnpm lint` | ESLint 검사 |
| `pnpm typecheck` | TypeScript 검사 |
| `pnpm test:product` | 제품 테스트 실행 |
| `pnpm test:e2e:smoke` | 핵심 사용자 흐름의 Playwright 검사 |
| `pnpm build` | 프로덕션 빌드 확인 |

현재는 출시 전 빠른 개발 단계입니다. 변경 범위에 맞춰 필요한 확인을 선택하며, 전체 테스트나 과거 Stage·workpack 절차를 매번 수행할 필요는 없습니다. 작업 규칙은 [AGENTS.md](AGENTS.md)가 우선합니다.
