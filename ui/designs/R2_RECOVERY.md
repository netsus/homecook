## 목적과 표시 위치

RECOVERY는 메뉴를 가리는 별도 페이지·modal이 아니라 실패한 화면의 저장 버튼 주변 inline 상태다. 연결 실패 중에도 공개 메뉴·사용 예시·질문을 읽고 이동할 수 있다. 네트워크 미확인과 서버 접수 완료를 구분한다.

## 오류별 표시·상태·이동

| 상황 | 문구 / 동작 |
| --- | --- |
| 최초 연결 중 | 제출 근처 '연결 중이에요'. 메뉴·질문·예시를 계속 열 수 있음 |
| 아직 전송하지 못함/명확한 저장 실패 | '아직 저장되지 않았어요'와 입력 유지, 재시도 |
| 응답 유실로 성공 여부 모름 | '접수 여부를 확인하지 못했어요' 또는 '저장 여부를 확인하지 못했어요'. 실패로 단정하거나 즉시 성공 화면을 열지 않음 |
| 재확인 중 | '저장 상태 확인 중' 또는 '접수 상태 확인 중'; 다른 완료 배지 유지 |
| 예시 저장 재시도 성공 | EXAMPLE_DONE, 자동 MENU 이동 없음 |
| 설문 접수 재시도 성공 | SURVEY_DONE, 답변 변경/다시 제출 버튼 없음 |
| 알림 접수 재확인/재시도 성공 | LEAD_DONE, 이메일 재입력 요구 없음 |
| 같은 오류 반복 | inline 안내 유지, 메뉴로 나갈 수 있음. 끝없는 전체 화면 spinner 없음 |
| validation 오류 | 해당 질문/이메일/동의 위치의 구체 오류와 연결. 일반 네트워크 재시도로 덮지 않음 |
| 보안 확인 만료 | 보안 영역 재확인. 입력 유지, 이전 토큰 재사용 없음 |
| 한 활동 완료·다른 활동 실패 | 이미 서버 확인된 완료는 유지, 실패한 활동만 안내 |
| 완료 정보 없음 | 미확인과 확인된 미완료를 구별. 접수 화면을 허위 생성하지 않음 |

알림 제출은 사용자가 누른 재시도만 허용한다. 응답 유실 후 서버 상태 복원에서 이미 신청한 참여로 확인되면 재입력 없이 완료 화면으로 보낸다. 재시도의 요청 식별·중복 방지·동시 탭 처리 API 세부는 #1551 확정 후 따른다. 재시도 버튼을 눌렀다는 사실만으로 완료 배지를 만들지 않는다.

## 저장소·메모리 구분

| 항목 | 보존 설계와 한계 |
| --- | --- |
| 서버 확인된 활동 완료 | 서버 복원 기준. 로컬 폼 값을 근거로 완료 만들지 않음 |
| 예시 장면·로컬 확인 | 현재 탭 메모리 유지. 서버 완료 배지와 별개이며 reload 보장 없음 |
| 설문 미제출 답변·비PII 대기 이벤트 | 현재 #1551은 r2 전용 IndexedDB 최대 30일 제안. 탭별 draft이며 미승인 정책 |
| 저장소 차단 시 draft | 열린 탭 메모리만. reload/탭 종료 후 사라질 수 있다고 명시 |
| 이메일·동의 | 열린 탭 메모리만. reload/탭 종료 시 폐기. 저장소·URL·로그에 넣지 않음 |
| 보안 토큰 | 메모리 전용, 제출 즉시 제거, 재시도에 필요 시 새 확인 |

현재 계약 draft는 저장소 오류 시 기존 서명 쿠키로 같은 참여의 서버 상태를 먼저 복원하는 경로를 제안한다. 복원이 유효하면 기존 참여의 활동 제출을 계속할 수 있다. 저장소도 없고 유효한 참여도 복원하지 못하면 예시·설문 draft 열기까지만 허용하고 제출 근처에 '신청이나 의견을 저장하려면 브라우저 저장 기능을 허용한 뒤 다시 시도해 주세요'를 표시한다. 새 참여를 임의 메모리 상태로 만들어 성공했다고 표시하지 않는다. 이 조건과 보존 기한은 계약 보완 중이므로 현재 문서가 확정하는 구현 계약이 아니다.

같은 주제 안에서는 다른 활동으로 이동해도 서버 확인된 완료를 보존한다. 뒤늦은 응답이 기존 완료를 미완료로 되돌려서는 안 된다. 서버 상태를 아직 읽지 못한 경우는 미확인이며 미완료로 단정하지 않는다. 세 활동에는 선행 조건이 없고 하나만 마쳐도 참여를 마칠 수 있다. 활동 개수 카운터·전체 완료 보상·자동 메뉴 복귀를 두지 않는다.

서버가 같은 참여의 알림 접수를 확인한 경우 LEAD 대신 LEAD_DONE으로 이동하며 이메일을 다시 묻지 않는다. 이메일 존재 여부를 공개 조회하거나 클라이언트 입력만으로 접수 완료라 판단하지 않는다. 이미 완료한 설문은 SURVEY_DONE으로 연결하며 답변 수정·재제출을 제공하지 않는다. 예시는 다시 볼 수 있다. 다른 주제는 별도 참여로 취급하고 완료나 입력을 복사하지 않는다.

## 치수·접근성·에셋

390px의 350px, 320px의 288px 내용 폭에 맞춘 inline 패널이며 padding 16px, radius 10px다. 오류 본문 16/24px, 아이콘 20px는 글자와 함께 쓰고 본문 대비를 확보한다. 재시도 최소 52px, 메뉴 44px, 8~12px 간격. 정해진 높이 없이 늘어나며 긴 한글 문구·주소가 페이지를 가로로 밀지 않는다.

원 화면의 로고·음식·mascot만 유지하고 별도 대형 오류 일러스트는 추가하지 않는다. 폼 바로 아래 패널이 삽입되면 같은 문서에서 스크롤로 접근한다. 입력 중 자동으로 위로 이동하거나 키보드를 닫지 않는다. 제출 결과 오류는 접근 가능한 알림으로 한 번 전달하고, 입력 오류면 첫 문제 필드에 초점을 준다. 재시도 도중 버튼 초점이 사라지지 않게 유지하고 성공 시 해당 완료 제목으로 이동한다.

## 공통 시각·접근성 기준

| 항목 | 390px | 320px |
| --- | --- | --- |
| 좌우 여백 / 내용 폭 | 20px / 350px | 16px / 288px |
| 제목 | 24px / 행간 32px, 700 | 22px / 행간 30px, 700 |
| 본문·입력·버튼 | 16px / 행간 24px | 16px / 행간 24px |
| 앱바 / 최소 터치 | 56px / 44×44px | 56px / 44×44px |
| primary / secondary / tertiary | 최소 52 / 48 / 44px | 최소 52 / 48 / 44px |
| 컴포넌트 간격 / 섹션 간격 | 8~12 / 20~24px | 8~12 / 16~20px |

흰 배경과 surface, ink `#212529`, 본문 `#495057`, 기존 `--brand-primary: #00A1FF`를 사용한다. primary는 밝은 파랑 위 dark ink이며 흰 글자를 올리지 않는다. secondary는 흰 면·진한 글자·식별 가능한 진한 outline, tertiary는 밑줄 있는 진한 text다. 컨트롤 radius는 기존 8px, 작은 카드 10px를 재사용한다. 본문에 연한 회색이나 파란색만 사용하지 않는다. 폰트는 기존 Avenir Next/Pretendard 계열을 유지한다. 토큰 전역 변경 지시가 아니다.

문서 본문 하나만 자연스럽게 세로 스크롤한다. 고정 높이, 내부 세로 스크롤, 큰 hero, sticky 하단 CTA를 두지 않는다. 하단에 24px + safe-area 여백을 둔다. 최소 높이는 글자가 늘면 확장하며 확대 글자를 자르지 않는다. 200% 글자 확대에서는 첫 화면 압축보다 읽기·스크롤 접근을 우선한다. 키보드가 열리면 현재 입력·오류·다음 행동까지 같은 문서에서 스크롤 가능해야 한다.

화면 제목으로 진입 초점을 옮기되 사용자 입력 중 비동기 응답은 초점을 빼앗지 않는다. DOM 읽기·Tab 순서는 표시 순서와 같게 한다. 버튼은 native button, 이동은 목적에 맞는 link로 구현할 계획이다. 포커스는 진한 2px 외곽선과 2px 간격, 상태는 글자와 아이콘을 함께 제공한다. 오류는 해당 입력의 `aria-describedby`와 `aria-invalid`에 연결하고 제출 시 첫 오류로 이동한다. 접수 완료는 `aria-live=polite`로 한 번만 알린다. 자동 전환·자동재생 없이 줄어든 모션 설정을 따른다. 대비·초점·키보드 동작은 아직 실측하지 않았다.

두 주제 × EXAMPLE/SURVEY/LEAD의 실패 위치를 각각 촬영한다. 최초 연결 실패 중 메뉴 표시, 저장 성공 응답 유실, 재시도 성공/반복 실패, 저장소 차단+유효 쿠키, 저장소 차단+복원 불가, 키보드 열림 오류, reload 전후 입력 수명, 다른 활동 완료 유지의 evidence를 남긴다. 실제 서버·메일·사용자 데이터에 오류를 주입하지 않고 승인된 격리 검증 경로를 사용한다.

현재 evidence는 입력 레퍼런스 직접 확인과 텍스트 설계뿐이다. 리더 소유의 정적 이미지 보드 및 `R2_DESIGN_DIRECTION.md`는 이 작성 범위 밖이다. design-critic 보조 검토는 pending이며 결과를 만들어 적지 않았다. 독립 authority의 실제 화면 검토 후에만 시각 확정을 판단한다.
