## 판단

선택한 날만 펼치는 주간 개요, 짧은 음식 행, 배경을 남기는 추가/수정 모달은 유지할 만하다. 계획 인분·먹은 g·요리 결과를 분리한 흐름도 좋다. 전체 재설계가 필요한 수준은 아니다.

다만 **P1 2건, P2 3건**이 있다. 빈 끼니의 계획 추가 경로와 잘못된 영양 막대는 승인 전에 수정해야 한다. 한 끼 상세의 진입 표시, 막대 의미, 기록 삭제에 따른 잔량 변화도 작은 수정으로 해결할 수 있다. P3 제안은 별도로 늘리지 않았다.

## 발견 사항

### WF-001 · P1 · 같은 음식의 영양 막대가 화면마다 다르고 열량 축도 고르지 않다

- **화면·위치:** 01 오른쪽 점심 김치찌개 작은 막대, 05 양 입력 영양 막대, 07 왼쪽 상세/오른쪽 수정 막대, 06 왼쪽 kcal 축 끝부분.
- **사용자 상황:** 김치찌개 300g을 기록한 뒤 상세를 열고 250g으로 수정한다. 또는 하루 영양에서 어떤 끼니를 많이 먹었는지 비교한다.
- **관찰:** 05와 07 왼쪽은 모두 탄수화물 14g·단백질 23g·지방 18g·310kcal인데, 05에서는 노랑이 약 절반이고 07에서는 분홍과 노랑이 비슷하다. 07의 250g 수정 미리보기 역시 같은 음식의 구성비가 바뀐다. 06의 0→200→400→600은 거의 일정 간격이지만 600→650 구간은 200 구간의 약 1/4보다 눈에 띄게 넓다.
- **문제·이유:** 막대가 실제 열량 구성비라는 확정 계약과 다르다. 양만 줄여도 영양 조성이 바뀐 것처럼 보이며, 눈금 폭이 다르면 실제 열량 비교도 왜곡한다. 예시 숫자라도 사용자 판단을 위한 차트는 숫자와 맞아야 한다.
- **최소 수정:** 이 예시에서 4/4/9 환산값은 56/92/162kcal, 합계 310kcal이므로 파랑/분홍/노랑을 **약 18.1%/29.7%/52.3%**로 통일한다. 동일 음식의 양만 바뀌면 구성비는 그대로 둔다. 06은 균일한 kcal 간격을 사용하며, 예를 들어 0/200/400/600/800으로 정리한다. 음식별 수치→끼니별 합→하루 합이 같은 예시 데이터에 연결되도록 한다.
- **해소 기준:** 01·05·07의 동일 음식이 같은 구성비이고, 양 수정 시 막대 비율이 유지된다. 06의 숫자 차와 눈금 거리가 비례한다. 새 이미지에서 직접 확인한다.
- **확신:** 높음. 픽셀 단위 자동 계측 결과가 아니라 직접 본 도형과 명시 숫자의 비교다.

### WF-002 · P1 · 일부 계획이 있는 날의 빈 끼니에 추가할 입구가 없다

- **화면·위치:** 01 왼쪽 선택일 상세는 10월 5일 제목 바로 아래 점심·저녁만 표시. 위 주간 목록은 계획 없는 날에만 + 표시. 02의 날짜·끼니는 이미 정해진 `10월 5일 · 점심`이다.
- **사용자 상황:** 월요일 점심·저녁 계획이 있는 사용자가 월요일 아침을 추가한다.
- **문제·이유:** 제시된 경로에는 아침 +도, 끼니 변경도 없다. 다른 날의 +를 쓰면 날짜가 달라지고 점심 +를 쓰면 점심으로 들어간다. 실제 앱이 막힌다고 단정하는 것이 아니라, **와이어프레임에 이 핵심 경로가 표현되지 않은 상태**다. 끼니를 숨기는 규칙대로 구현하면 추가가 막힌다.
- **최소 수정:** 선택한 날에는 사용자가 설정한 모든 끼니 제목과 +를 유지한다. 빈 끼니는 음식 카드 없이 `아침  +` 한 줄이면 충분하다. 주간 개요의 빈 날짜 +는 우선 그 날짜를 선택·펼치고 끼니 +를 고르게 하거나, 추가 모달 안에 명시적인 끼니 선택을 둔다. 앞의 안이 현재 구조를 덜 바꾼다.
- **해소 기준:** 월요일 빈 아침과 완전히 빈 금요일에서 시작해 올바른 날짜·끼니에 계획을 넣는 경로가 화면 또는 주석으로 단일하게 정해진다.
- **확신:** 높음(제공 화면 범위).

### WF-003 · P2 · 한 끼 상세로 들어가는 표시가 없다

- **화면·위치:** 01 왼쪽 `점심`/`저녁` 제목과 +, 03 왼쪽 한 끼 상세.
- **사용자 상황:** 점심 전체의 요리를 보고 준비 상태를 비교하거나 연결된 장보기 목록을 열고 싶다.
- **문제·이유:** 음식 행에는 >가 있어 한 요리 상세로 이동함을 알 수 있지만, 끼니 제목은 일반 제목처럼 보인다. +는 추가 의미다. 03 왼쪽 화면으로 들어가는 클릭 대상이 드러나지 않아 사용자가 음식 상세만 반복해서 열 수 있다.
- **최소 수정:** 끼니 제목 영역에 `점심 >`를 두고 제목 영역 전체를 한 끼 상세의 클릭 영역으로 삼는다. +는 별도 버튼으로 유지하고 클릭이 섞이지 않게 한다. 새 줄이나 큰 버튼은 불필요하다.
- **해소 기준:** 제목 클릭은 한 끼 상세, 음식 클릭은 개별 요리 상세, +는 해당 끼니 추가로 구별된다. 각 상세의 뒤로는 선택일과 위치를 보존한다.
- **확신:** 높음(보이는 진입 표시의 부재).

### WF-004 · P2 · 작은 막대의 의미가 화면 안에서 설명되지 않는다

- **화면·위치:** 01 오른쪽 음식 행의 동일 길이 3색 막대, 05·07의 g 숫자와 구성 막대.
- **사용자 상황:** 160kcal 현미밥과 310kcal 김치찌개의 막대 길이가 같은 이유를 이해하거나, 탄단지 g 숫자와 막대를 비교한다.
- **문제·이유:** 범례의 색은 알 수 있어도 길이가 절대량인지, g 구성인지, 열량 구성비인지 알 수 없다. 생성 지시의 정의는 앱 이용자가 읽을 수 없다. 목표 진행률의 빈 영역을 없앤 결정은 좋지만 의미의 모호함까지 없어지지는 않는다.
- **최소 수정:** 목록 전체에 한 번만 `막대: 탄·단·지 열량 비율`을 작게 표시하거나 하루 영양 옆 도움말에 같은 설명을 두고 접근 경로를 보인다. 상세에는 `열량 구성비`라는 짧은 라벨을 쓴다. 매 음식마다 긴 설명은 넣지 않는다.
- **해소 기준:** 첫 이용자가 음식의 막대 길이를 섭취 열량 자체나 g 비율로 읽지 않도록 최소한의 화면 내 단서가 있다.
- **확신:** 중간~높음. 실제 사용자의 오해 빈도는 검증하지 않았다.

### WF-005 · P2 · 식사기록 삭제 확인에서 남은 양 복원 영향이 빠져 있다

- **화면·위치:** 08 오른쪽 `선택한 기록만 삭제하고 음식과 레시피는 남겨둬요` 안내.
- **사용자 상황:** 실제 먹은 음식은 그대로인데 기록만 잘못됐는지, 남은 음식을 버린 것인지 구분하며 삭제하려 한다.
- **근거:** `docs/engineering/feedback-meal-log-navigation-20260928.md`는 기록 삭제 시 요리한 음식의 섭취량 되돌림을 유지한다고 명시한다. 05·07은 잔량 변화를 핵심 정보로 보여주는데 삭제에서는 사라진다.
- **문제·이유:** 삭제가 영양 기록에만 영향을 준다고 생각하면, 실제로는 남은 양이 늘어나는 결과를 예상하기 어렵다. 삭제 대상 자체는 현재처럼 날짜·끼니·음식·g로 충분히 명확하다.
- **최소 수정:** 요리한 음식에 연결된 기록일 때만 `삭제하면 남은 양이 300g 늘어나요` 또는 최신값을 확인한 `삭제 후 남은 양 600g`을 한 줄로 표시한다. 제품·재료 기록에는 이 줄을 표시하지 않는다. 삭제/버림을 새 복합 작업으로 합치지 않는다.
- **해소 기준:** 08에서 섭취 기록 삭제와 실제 음식 폐기가 구별되며, 잔량 복원 효과가 명시된다. 서버 충돌 시 확정되지 않은 잔량을 성공으로 보여주지 않는다.
- **확신:** 높음. 실제 삭제는 실행하지 않았다.

## 유지할 결정과 작은 보완

- **주간 개요 A안 유지:** 일주일 전체의 대략적인 계획과 선택일 세부 내용이 함께 보인다. 빈 끼니 한 줄 추가로 해결하고 7일 전체를 펼치는 구조로 바꾸지 않는다.
- **음식 행 유지:** 이름·양·kcal·작은 탄단지 막대는 반복 기록을 훑기 좋다. 색은 탄수화물 #94C9FF / 단백질 #FFA7C2 / 지방 #FFD477로 유지한다.
- **모달 배경 유지:** 02·04·05·07·08은 기존 날짜와 화면 맥락이 남는다. 02의 뒤로/레시피 바꾸기, 05의 이전 양/남은 양 전부도 재입력을 줄인다.
- **단위 분리 유지:** 계획은 인분, 개인 섭취는 g, 잔량은 별도 결과다. 03의 예상 영양 `2인분 기준`과 `1인분 310kcal` 구별은 좋다. 요리 완료를 섭취로 자동 기록하는 UI는 보이지 않는다.
- **혼합 상태 유지:** 03은 장보기 완료 요리와 등록 요리를 구별하고 각각 다른 행동을 준다. 아래 주석의 이어하기/완성 음식 보기도 유지한다.
- **삭제 위치 유지:** 관리 행동이 상세에 있고 확인창의 대상이 분명하다. 취소와 삭제의 구별도 충분하다. 과도한 추가 경고창은 필요 없다.
- **하루 영양 구조 유지:** 기본은 끼니별 실제 kcal, 영양소 탭은 공통 0점의 g 비교와 기여 음식으로 나뉜다. 간식 `기록 없음`을 수치 0으로 꾸미지 않은 점도 좋다.

## 별도 이미지 없이 동작 주석으로 정할 항목

아래는 구현에서 이미 고장 났다는 발견이 아니다. 기존 문서의 계약을 이어받는 짧은 설계 주석으로 충분하며, 모든 예외 화면을 새로 그릴 필요는 없다.

| 상황 | 유지·명시할 동작 |
|---|---|
| 장보기 진행/완료 뒤 인분 변경 | index.html은 기존 상태 제한을 유지한다고 명시한다. 03의 항상 활성처럼 보이는 `변경`은 실제 변경 가능 조건과 연결한다. 잠기는 상태라면 버튼을 숨기거나 비활성+짧은 이유를 보여준다. 완료 장보기는 읽기 전용이다. |
| 등록 / 연결 장보기 진행 / 요리 중 / 완료 | 등록 중 미연결은 장보기, 연결 중은 연결 목록, active session은 정확한 요리 이어하기, 완료는 완성 음식 보기로 분기. 새 세션/완료 기록을 자동 중복 생성하지 않는다. |
| 최근 음식이 없음 / 검색 결과 없음 | 최근이 비었으면 요리한 음식·제품/재료 탐색을 계속 사용할 수 있게 하고, 검색 결과 없음에서는 검색어 수정/지우기를 제공한다. |
| 소진된 음식 | 기존 문서대로 최근과 요리한 음식 후보에서 제외한다. 선택 후 소진·잔량 변화가 확인되면 입력을 무조건 버리지 말고 최신 잔량과 다시 선택/수정 경로를 제공한다. |
| 무게 없는 음식 / 지원 단위 | 04 하단 설명처럼 제품·재료는 실제 지원 단위를 쓴다. 근거 없는 g↔개 환산을 하지 않는다. 무게 없는 요리는 무게 확인 경로를 제공하고 잔량을 추정 확정값처럼 꾸미지 않는다. |
| 저장 중 / 실패 / 응답 불확실 | 입력과 날짜·끼니를 보존한다. 저장 중 중복 누르기를 막고, 같은 시도의 재시도는 같은 요청으로 처리한다. 확인 전 성공 토스트/목록 복귀를 하지 않는다. 잔량 충돌은 최신 수량 확인 후 명시적 재시도다. |
| 계정 변경 / 권한 실패 | 다른 계정의 늦은 응답을 보이지 않게 한다. 로그인 복귀 시 이전 입력 대상과 새 계정의 권한을 재확인한다. 서버 보호를 UI 편의로 우회하지 않는다. |
| 닫기 / 뒤로 / 성공 | 모달 내 뒤로는 검색어·탭·선택을 보존하고, 수정 저장은 갱신된 상세로 복귀한다. 취소는 원본 유지, 삭제 성공은 같은 날짜 목록의 가까운 위치로 복귀한다. 입력이 달라진 상태의 닫기 처리도 정한다. |
| 영양 정보 일부 없음 | 누락을 0으로 합치거나 알려진 일부를 전체 구성비처럼 단정하지 않는다. 해당 음식/합계에 부분 정보임을 짧게 구별한다. |

## 검증 한계와 실제 기기에서 남은 확인

이 보고서는 정적 와이어프레임의 경로·문구·시각적 관계를 평가했다. 이미지가 실제 375px UI 또는 동작 가능한 앱인 것은 아니다. 44px 터치 영역, 16px 입력 글자, 명암 대비 수치, 스크린리더 이름, 포커스 이동, 키보드 열림 시 자동 확대, 스크롤 충돌은 검증하지 않았다. 작은 +/닫기 그림의 크기만으로 실제 클릭 영역을 단정하지 않았다.

구현 이후 iPhone 13 mini에서는 ① 입력 자동 확대 여부 ② 모달 내부 하나의 스크롤만 움직이는지 ③ 키보드가 떠도 입력·오류·저장에 도달하는지 ④ 전역 탭과 하단 버튼이 겹치지 않는지 ⑤ 뒤로/취소/저장 뒤 같은 날짜·위치가 복원되는지를 확인해야 한다. 05의 `완료`는 키보드 닫기이며 실제 기록 저장과 혼동되지 않게 한다. 이 기기 확인은 design_ready 판단과 별개다.

## 후속 검토 방법

수정본에서 WF-001~WF-005를 같은 ID로 해소/부분 해소/미해소 판정한다. 빈 끼니 보완으로 주간 개요가 과밀해지거나, 제목의 >와 + 클릭이 겹치거나, 차트 수정으로 음식/끼니 합계가 달라지는 회귀를 확인한다. 합리적인 반박과 대체 경로가 제시되면 해당 발견을 재평가한다. **현재는 P1 핵심 경로·차트 문제가 남아 design_ready=false다.**
