# 요리계획·식사기록 독립 UX 재검토 — 2차

2026-10-05 · **설계 승인 / design_ready=true**

검토 대상은 `reviewed-v2`의 8개 원본 PNG와 의사결정·동작 규칙·공통 예시 데이터다. 변경된 01/05/06/07/08뿐 아니라 02/03/04도 이번 검토에서 모두 `view_image`로 직접 열었다. 합성본은 사용하지 않았다. 실제 앱·운영 DB·배포·Git·원본 파일은 변경하지 않았고 보고서 두 개만 만들었다.

## 판단과 범위

중요한 미해결 P1/P2는 없다. 1차 발견 5건은 설계 수준에서 해소됐다. 전체 A안, 선택일 펼침, 하단 모달, 짧은 음식 행, 확정 파스텔색을 유지하면서 작은 표시·문구·계산 규칙으로 해결한 접근이 합리적이다.

단, 모든 PNG의 그래프 픽셀이 수학적으로 정확해졌다고 승인하는 것은 아니다. WF-001의 핵심 해석 문제는 일정 축·동일 비율 명시·검산 데이터로 해소됐지만, 도형의 세부 폭과 어두운 배경 자산에는 P3 정리 사항 WF-006이 남아 있다. 이 구별 없이 ‘막대가 모두 정확하다’고 보고해서는 안 된다.

이번 승인은 **와이어프레임의 흐름과 함께 전달된 동작/계산 계약**에 대한 판단이다. 앱 구현·배포 승인 또는 실제 iPhone 검증 완료를 뜻하지 않는다.

## 기존 발견 재판정

### WF-001 · 기존 P1 · 설계 기준 해소

- 화면: 01, 05, 06, 07.
- 근거: 06의 kcal 0/200/400/600/800과 단백질 0/10/20/30/40 축은 일정 간격이다. 활성 음식 상세 07은 300g과 250g 모두 18%/30%/52%를 명시한다. 05는 지방이 약 절반인 구성으로 유지된다. 공통 데이터의 음식/끼니/하루 합계와 250g 환산을 검산했다.
- 남은 제한: 래스터 도형 폭은 정확히 일치하지 않으며 08의 어두운 배경은 이전 구성이다. 픽셀 정합성까지 완료로 선언하지 않는다. WF-006(P3)으로 분리한다.

### WF-002 · 기존 P1 · 해소

- 화면: 01, 02.
- 근거: 선택일에 빈 아침 제목과 +가 보인다. 주간 빈 날짜의 +는 >로 바뀌었다. 동작 규칙은 날짜 행 선택 → 모든 설정 끼니 표시 → 해당 끼니 +로 추가를 단일하게 정의한다.

### WF-003 · 기존 P2 · 해소

- 화면: 01, 03.
- 근거: 아침/점심/저녁 제목에 >가 붙고 +와 분리됐다. 제목은 한 끼 상세, 음식 행은 해당 요리 상세, +는 추가라는 클릭 책임이 명시됐다.

### WF-004 · 기존 P2 · 해소

- 화면: 01, 05, 07.
- 근거: 01 목록 전체에 열량 구성비·도움말·색 범례가 한 번 배치됐다. 05/07에도 열량 구성비 라벨이 있다. 도움말 문안은 g 비율 및 전체 섭취량과 구별한다. 매행 설명보다 간결한 대안을 수용한다.

### WF-005 · 기존 P2 · 해소

- 화면: 08.
- 근거: 기록한 300g이 남은 양으로 돌아갑니다가 표시된다. 제품·재료 기록에는 적용하지 않으며 최종 잔량은 성공 응답 후 확정하도록 규정한다. 동시 수정 가능한 최종 잔량 600g을 고정하지 않는 대안은 합리적이다.

## 수정 대안에 대한 독립 판단

- **매행 설명 대신 목록 전체 라벨:** 수용한다. 작은 막대의 의미를 한 번 알리고 상세에서 다시 확인할 수 있어, 반복 설명 없이 필요한 구별을 제공한다.
- **삭제 후 600g 대신 복원 효과:** 수용한다. 기록한 300g을 되돌린다는 안내는 결정을 돕고, 동시 변경될 수 있는 최종 잔량은 서버 성공 응답으로 확인한다. 충돌을 성공으로 확정하지 않는 동작 규칙이 함께 있으므로 정보 축소에 해당하지 않는다.
- **저녁 음식명을 볶음밥으로 변경:** 수용한다. 현미밥의 양만 바뀌었는데 구성이 달라진 오해를 없앤다. 가상 예시이므로 실제 볶음밥의 공인 영양값이라고 평가하지 않았다.
- **별도 예외 그림 대신 동작 규칙:** 수용한다. 소진 후보 제외, 잔량 충돌, 무게 없음, 지원 단위, 부분 영양, 저장 실패·중복 요청·계정 세대, 복귀 규칙이 명시됐다. 정적 이미지에 예외 상태가 전부 없다는 이유로 재설계를 요구하지 않는다.

## 수치와 파일 확인

공통 fixture를 읽는 독립 검사로 다음을 확인했다.

- 음식 6개의 탄수·단백질·지방 × 4/4/9와 energy_segments, 구성비 일치.
- 아침 430kcal / 점심 620kcal / 저녁 400kcal, 각 끼니의 g 합계 일치.
- 하루 1,450kcal · 탄수180g · 단백질70g · 지방50g 일치.
- 김치찌개 56/92/162kcal = 310kcal, 반올림 구성비 18/30/52.
- 300g→250g 환산은 258kcal이고 구성비 불변.
- manifest의 8개 SHA-256과 실제 PNG 일치. 02/03/04는 1차 원본과 바이트 단위 동일.

이는 예시 데이터의 내부 정합성 검사다. PNG의 모든 막대에 대한 픽셀 자동 계측이나 실제 음식 영양 검증은 아니다. 실제 제품의 표기 열량과 4/4/9 합계가 다른 경우는 interaction-contract.md의 구별 규칙을 따른다.

빈 아침과 한 번의 범례를 추가해도 현재 샘플에는 핵심 음식 행과 하단 탭이 남는다. 다만 이 이미지의 배치만으로 긴 음식명·5개 끼니·큰 글씨가 실제 375px 화면에서 통과한다고 판단하지 않는다. 제목의 >와 +가 시각적으로 분리되고 계약도 겹치지 않는 영역을 요구하지만 실제 터치 검증은 아직 없다.

03의 장보기 완료 상태에서 `변경` 버튼이 보이는 것은 1차와 같다. 상태별 허용 범위는 기존 계약을 따르고 불가능한 상태는 숨김/비활성 처리하도록 명시됐으므로 이번에 새로 발견된 우회 경로로 단정하지 않는다. 07에 추가된 +는 의사결정 기록상 같은 날짜·끼니의 음식 추가이며, 수정·삭제와의 역할 충돌은 보이지 않는다.

## 선택적 개선 WF-006 · P3

**래스터 막대의 정밀도와 모달 배경 자산 일치**

- 위치: 01 작은 음식 막대, 05/07 구성비 도형, 08 오른쪽 어두운 상세 배경.
- 상황: 검토자가 PNG들을 나란히 비교하거나 구현자가 그림의 폭 자체를 숫자 기준으로 사용한다.
- 관찰: 01 김치찌개의 파랑 조각은 상세보다 조금 넓고, 07의 두 막대는 같은 18/30/52 라벨이어도 도형 경계가 완벽히 일치하지 않는다. 08의 비활성 배경에는 이전에 사용한 약 1/3씩 나뉜 구성 막대가 남아 있다.
- 최소 개선: 시각 자료를 정리할 때 동일 데이터로 만든 막대와 최신 상세 배경을 재사용한다. 실제 구현은 fixture와 계산 규칙으로 그리며 PNG 폭을 복사하지 않는다.
- 승인 차단 사유가 아닌 이유: 현재 활성 상세에서 비율과 불변 규칙이 명시되고 숫자·축·합계가 검산됐다. 남은 도형 차이는 활성 화면에서 영양소 순서를 뒤집거나 기록·수정·삭제 경로를 막지 않는다. 삭제창 뒤의 어두운 배경은 영양 비교의 활성 영역이 아니다. 이 제한된 맥락에서 P3로 분류하며, 차트 오류를 일반적으로 허용하는 판단은 아니다.

## 실제 기기에서 남은 확인

1. iPhone 13 mini에서 숫자 입력 시 자동 확대 방지, 직접 확대 유지.
2. 키보드 열린 동안 모달 내부 단일 스크롤, 배경 잠금, 입력·오류·저장 접근.
3. 전역 탭·저장 패널·키보드 겹침 없음. 키보드 완료와 기록 저장 구별.
4. 닫기·뒤로·저장·삭제 후 날짜·끼니·위치·포커스 복원.
5. 실제 44px 클릭 영역, 16px 입력 글자, 대비와 스크린리더 이름.
6. 중복 누름·불확실 응답·재시도·잔량 충돌·계정 변경·소유권·상태 전이 보호.

위 항목들은 이번 검토에서 실행하거나 통과 판정하지 않았다. 설계상 규칙이 있다는 것과 실제 구현이 지킨다는 것은 별개다.
