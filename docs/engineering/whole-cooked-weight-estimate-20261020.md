# 완성 요리 전체무게 자동 추정 — 2026-10-20

요구는 완성한 요리 전체의 추정 g을 자동으로 넣고 그 무게로 기존 g 식사기록을 사용하는 것이다. 인분·전체의 1/4 같은 별도 섭취 원장은 범위에서 제외한다.

현재 앱 후보는 **서버가 유효한 전체 추정무게를 내는 경우 실제 숫자를 자동으로 채우도록 구현했다.** 안내만 바꾼 것이 아니다. 다만 아래 실제 카레의 양념/환산·조리수율 문제까지 해결한 상태는 아니다. 운영 기준 16cf3155c7b5·DB238은 변경하지 않았다.

사용자가 제공한 레시피북에서 저장 상세를 읽기 전용으로 다시 확인했다. `b74f5cd2-0db2-4354-b111-1136140763e7`, 제목 ‘맛있는 돼지고기 카레’, 기본 2인분이다.

따라서 이 사례는 핵심 음식과 물까지 누락된 사례와 구분해야 한다. 현재 정책에서는 소량 양념과 환산 불확실성이 숫자 산출을 전부 막을 수 있다. 현재 운영의 frozen quantity/proof를 DB에서 읽거나 새 요리 세션을 만들지 않았으므로, 위 관찰만으로 각 행의 실제 서버 reason code나 환산 바인딩까지 확정하지 않는다. 레시피북의 상세 읽기는 한 번 연결 오류가 났고, 저장 상세 화면에서 위 내용을 확인했다.

## 실제 계산과 저장 경로

1. `readSnapshotWeightPrediction`이 소유자·고정 snapshot·인분을 검증하고 승인된 재료/제품 환산을 hydrate한다. v4 원입력 proof가 있으면 `frozenQuantity`가 그것을 검증하며, 누락/불일치한 proof를 오늘의 임의 계량값으로 덮어쓰지 않는다.
2. `predictSnapshotWeight` → `predictCookedWeight`는 재료 g과 **완성 전체무게**를 분리한다. 구조화된 가열 없는 MIX는 ‘모든 적힌 재료가 남는다’는 공개 가정 아래 합계를 사용할 수 있다. 가열/배수/추가 물·기름 문장은 MIX 추론을 거부한다.
3. 수율 엔진에는 정확한 조건을 요구하는 USDA 저지방 다짐육 0.69 후보 하나만 등록돼 있다. 카레·국 전체에 적용되는 수율이 아니다. 현재 snapshot mapper는 식품역할·원상태·정확 프로토콜을 확인된 사실로 채우지 않으므로 일반 가열 레시피는 그 조건을 충족하지 않는다. 흡수·외부 손실 계산 능력은 순수 함수에 있으나 실제 snapshot에 자동으로 근거가 생기는 것은 아니다.
4. `withIngredientMassFallback`은 조리 조건만 부족하고 **모든 행의 정량·질량 근거가 있는 경우** 총 투입 질량×0.75를 적용한다. 이 75%는 기존 승인된 거친 보정 정책이며 카레의 실측 수율·물리 증발 계산이나 정확도 보증이 아니다. `TO_TASTE`, 양 미확인, 환산 불가가 하나라도 있으면 거부한다. 이름별 ‘소량 양념’ 예외는 없다.
5. 완료는 `complete_cooking_execution` 또는 기존 snapshot 완료 RPC로 이어진다. 수정 실행은 저장한 prediction과 revision을 사용하고, 자동 완료는 `weigh_later/null`로 서버 예측을 선택한다. 유효한 결과는 known/estimated batch가 되어 기존 g 식사기록에서 선택 가능하다. 실측은 별도 `reported_measured`이며 우선한다.

옛 `estimateCookedWeight`는 TO_TASTE를 건너뛰고 정량 합×0.75를 계산한다. 이를 새 경로의 우회로 재사용하면 현재의 불확실성·출처 정책이 달라진다. 특히 실제 카레에는 별도의 양 미확인 오일과 환산 문제도 있어 후추를 빼는 것만으로 해결된다고 할 수 없다.

## 앱 범위에서 구현한 보완

- 유효한 `conditional_estimate.predicted_g`를 ‘완성 음식 전체무게 (자동 추정, g)’ 칸에 원정밀도로 채운다. 자동값은 읽기 전용이며 그대로 완료할 수 있다. 서버를 재계산 권위로 유지하고 숫자를 실측 인자로 복사하지 않는다.
- ‘실측값 입력’을 선택하면 별도 빈 입력으로 전환한다. 저울로 잰 전체무게를 직접 입력하면 그 값·reported_measured를 전달한다. 자동값이 실측으로 승격되지 않는다.
- 자동 모드로 돌아가면 이전 실측 draft·개인 확인을 비운다. 직접 입력 후 fresh prediction이 도착해도 실측 draft를 유지한다. 포커스는 readOnly 해제 후 이동한다.
- 전체 추정이 unavailable이면 0이나 일부 합계를 자동 채우지 않는다. 기존 화면 개선과 g 식사기록을 유지하며 새 인분/비율 기능은 추가하지 않는다. 모든 재료 수동 입력을 새 기본 흐름으로 만들지 않는다.

이 변경은 기존 계산 숫자를 눈에 보이는 자동 전체무게로 연결하는 실제 UI 보완이다. 기존 75% 모델의 적용 범위나 정확도를 넓힌 것은 아니다. 수동 추정값 편집을 실측처럼 저장하는 경로도 추가하지 않았다. 지금 가능한 직접 덮어쓰기는 명시적 실측 입력이다.

## 수율과 소량 양념에 대한 근거

[USDA 원문](https://www.ars.usda.gov/ARSUserFiles/80400525/Data/retn/USDA_CookingYields_MeatPoultry02.pdf) 5~6쪽은 조리 전/후 무게와 특정 가열·배수 절차를 구분한다. 고기 수율을 물·소스가 포함된 카레 전체에 대입하는 근거가 아니다.

[FAO 계산 교육 자료](https://www.fao.org/fileadmin/templates/food_composition/documents/Presentations/Food_Composition_-_Recipes_and_other_calculations.pdf)는 중량수율과 영양잔존율을 구분하고, 물·조리 지방 누락과 결측 영양의 0 처리를 오류로 설명한다. [FAO에 보관된 EuroFIR 계산 지침](https://www.fao.org/uploads/media/vasquez-caicedo_et_al__2007_recipe_rulesD2.2.9_02.pdf)은 지역 레시피의 수율을 문서화하고 실험이 없을 때 유사 요리의 문헌 수율을 사용할 수 있다고 설명한다. 이는 아래 새 정책 설계의 근거이며 카레의 새 계수를 이미 확보했다는 뜻은 아니다.

질량수지 관점에서는 먹을 완성 음식 = 투입한 가식 질량 + 별도 추가량 − 외부로 버리거나 증발한 질량이다. 냄비 안에서 고기 수분이 국물로 이동하거나 쌀이 이미 포함한 물을 흡수하는 것은 전체 경계 안의 이동이므로 물을 다시 더하거나 고기 손실을 곧바로 전체 손실로 빼면 안 된다. 이것은 설계상 해석이다. 이번 조사에서는 이 카레의 외부 손실량이나 검토된 레시피급 수율 숫자를 확보하지 못했다.

현재 저장소에는 승인된 환산 자료가 있지만 ‘약간’이라는 사용량 자체를 자동 추정하는 검토된 dose 범위는 없다. 개인 보정 모듈도 apply=false인 오프라인 fixture이며 운영 보정으로 사용할 수 없다. 기존 문서는 실제 정확도 정답 표본 0건을 명시한다. Bognár의 후보를 새 운영 계수로 복사하지 않았으며 기존 재사용 권리 보류도 유지한다.

## 실제 카레까지 지원하는 정확한 다음 범위

권장안은 **기존 g 원장을 유지하고, 전체무게 모델의 입력·불확실성 정책을 확장하는 것**이다. 인분 원장 신설은 필요하지 않다.

1. 승인된 질량/부피/조각 환산을 쓰되 원량·단위·고정 source identity는 보존한다. 비표준 꼬집·크게 스푼은 계량큰술로 확정하지 않고 별도의 검토된 추정 근거와 범위를 사용한다.
2. 소량 분말 양념, 조리 기름, 주재료, 물/국물을 구분한다. 후추 같은 미확정 양념을 무조건 0g으로 만들지 않고 출처·요리 규모와 연결된 dose 범위로 반영한다. 오일을 후추와 같은 예외로 제외하지 않는다. 핵심 음식/물까지 미확인인 경우에는 그 부족한 문맥만 따로 다룬다.
3. 국물 보존 카레·배수 요리·쌀 흡수처럼 완성 음식 경계가 같은 검토된 레시피/문헌 수율을 선택한다. 원문에서 얻은 끓임 시간만으로 증발량을 만들지 않는다. 추정값에는 새 모델 버전·수율/환산/dose 출처·가정·범위를 고정하고 실측과 구분한다. 신뢰 확률이나 허용 오차를 검증 없이 만들지 않는다.
4. 모든 재료를 사용자에게 다시 입력시키는 대신 근거 있는 자동 후보를 먼저 제공한다. 정말 결정적인 물/주재료 누락이 있을 때만 그 입력을 확인하는 방향이다. 현재는 위 dose·레시피급 수율 자료를 아직 선정·검증하지 못했으므로 실제 카레의 새 g 숫자를 제시하거나 저장하지 않았다.

DB238의 `private.record_cooked_weight_evidence`는 허용 모델 2개와 75% 모델의 모든 행 정량·양수 g·확정 proof·합계 일치를 강제한다. 따라서 위 정책은 **앱의 안내나 TO_TASTE skip 한 줄로 완성할 수 없다.** 최소 추가 범위는 새 서버 모델/정책·검토된 근거 바인딩과 이 private 검증 함수에 새 모델을 엄격히 검증하는 후속 migration이다. 기존 모델 검사와 g 원장·권한·인증키·사용자 기록은 유지하고 새 요리부터 적용하는 형태가 가능하다. 일반적인 새 테이블/인분 구조가 필수는 아니지만 정확한 JSON 증거 형식과 원천 저장 방법은 정책 확정 뒤 결정해야 한다. 모델 whitelist만 늘려 검증을 우회해서는 안 된다.

그 범위의 격리 검증은 소량 양념만 미확인/오일 미확인/주재료 미확인/물 미확인/환산 미확인 각각의 산출·거부, 물 흡수 이중합산·국물 보존·배수/증발, kg/ml/인분 배율 한 번 적용, 위조 dose/수율/identity/버전 거부, 실측 우선·재시도·revision·과거 pin 보존, 실제 g 식사기록의 분모/잔량을 포함해야 한다. SQL은 소유한 빈 networkless DB에서 새 검증 함수와 기존 부정 회귀를 실행하고 운영 DB에는 적용하지 않는 순서다. 이번에는 새 정책이나 migration을 작성·적용하지 않았다.
