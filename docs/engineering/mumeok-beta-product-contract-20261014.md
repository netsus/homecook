# C03 공공제품을 독립 재료로 사용하기

상태: 로컬 구현·검증 준비. 운영 DB·권한·새 형식 쓰기는 별도 승인 전 적용하지 않는다.

## 사용 흐름과 보존 계약

- 대표 일반 재료가 없는 `public_dataset` 제품도 레시피 재료로 선택할 수 있다. 대표 연결은 분류·대체 후보 정보다. 수동/private 제품의 기존 대표 연결·소유자 제한은 유지한다.
- 재료 행은 안정적인 `row_key`와 `source_kind`를 갖고 제품 ID·영양 버전을 함께 고정한다. 일반 재료 ID가 없는 제품 행도 영양·상세·계획·장보기·요리까지 동일한 제품 버전을 사용한다.
- 검색 또는 기존 ‘내 팬트리’에서 선택한다. 팬트리는 실제 보유 항목의 정확한 버전을 다시 확인한다. 과거 공공제품 버전을 현재 버전으로 몰래 바꾸지 않는다. 지원되지 않는 과거 수동 제품은 선택을 막는다.
- 제품 또는 영양 버전이 바뀌면 실제 사용량을 빈칸에서 입력한다. 같은 제품·버전 재선택은 원래 수량·단위·적당량·배율 적용 여부·구성·단계 참조를 보존한다. 제품의 기준 100g을 실제 투입량으로 자동 입력하지 않는다.
- 환산은 고정된 제품 버전의 명시 근거만 사용한다. 근거 없는 g/mL 동등 처리, 일반 재료의 밀도·개당 무게 차용, 서로 모순되는 환산 경로 사용은 금지한다.
- 장보기의 실제 필요량과 참고 구매 팩 수는 별도로 표시한다. 구매 팩 올림은 원래 투입량·영양·스냅샷·팬트리 재고로 되돌려 쓰지 않는다. g 재고 자동 차감은 추가하지 않는다.
- 조리법 문장과 숫자는 원문 그대로다. 수동 단계 재료 연결이나 자동 수량 삽입은 추가하지 않는다. 유일하게 확인되는 기존 참조만 안전하게 행에 연결하고 모호한 참조는 임의 변환하지 않는다.

## 기존 기록과 로그인 복귀

공개 공공제품(public_dataset/public)의 기존 non-null 재료는 같은 레시피의 같은 물리 행과 정확한 제품/버전/재료 조합을 확인한 경우에 한해 대표 연결 해제 뒤의 무관한 편집도 보존한다. 새 행·다른 제품·다른 레시피로의 복사 및 수동/private 제품은 기존 대표 검사를 유지한다. 기존 원량과 numeric scale을 유지하고 일괄 backfill·과거 식단/영양 스냅샷 재계산은 하지 않는다.

제품 행이나 새 명시 행 참조를 모르는 옛 편집기가 이를 누락해 저장하면 `409 RECIPE_SOURCE_CONTRACT_REQUIRED`로 원자 거절한다. 원래부터 행 참조가 없던 모호한 조리 단계와 새 명시 참조를 구분하며, 새 참조를 과거의 모호한 형태로 되돌리지 않는다. 로그인 복귀는 검증된 같은 계정·세대·원래 레시피 권한/revision을 확인한 뒤 입력 화면만 연다. 저장이나 영양 미리보기를 자동 실행하지 않으며 다른 계정/세대의 초안을 이어 쓰지 않는다.

## API와 공개 경계

`GET /food-catalog/search`의 선택적 `pantry_item_id`는 현재 소유자의 실제 보유 항목 및 요청 제품 ID와 일치해야 한다. 공공제품의 과거 영양 정보는 기존 exact-version RPC로 읽으며 일반 테이블 읽기 권한을 새로 넓히지 않는다. `GET /users/me`의 선택적 `account_generation`은 기존 검증된 세션 권위에서만 읽고, 검증할 수 없으면 필드를 생략한다. 세션 갱신·키 발급·권한 확대 수단이 아니다.

새 공개 조회/검색 RPC 세 개는 공개 레시피에 사용된 접근 가능한 공개 제품 정보를 제공한다. 공공제품과 기존 public manual 제품이 포함되며 source_type을 공공제품으로만 제한하는 조회가 아니다. 신규 대표 미연결 재료 저장은 공공제품 한정이다. 정확한 signature는 public.read_public_recipe_product_sources(uuid), public.read_recipe_product_ingredient_classification(uuid[]), public.find_public_recipe_ids_by_product_name(text)이며 anon/authenticated에 EXECUTE를 부여한다. 숨김/private 제품이 섞인 공개 레시피는 상세/요리의 제품 source projection 전체 조회를 실패시킨다. 제품명 검색과 분류 조회는 허용하지 않는 source를 제외하며, 같은 레시피의 다른 공개 source에 해당하는 레시피 ID를 반환할 수 있다. 기존 direct DB role의 private product pin 조회 가능성은 별도 잔존 위험이며 이번 API 보호를 전체 보안 해결로 표현하지 않는다.

## DB 적용과 복구 경계

미적용 SQL `20261013190000_recipe_product_only_identity.sql`은 재료 행의 nullable 일반 재료 ID·출처 CHECK, 반올림 없는 제품 수량, 좁은 공개 RPC와 기본 OFF 제어를 준비한다. 수량은 기존 최대값과 유한 양수 검사를 유지한다. typemod 제거는 공통 amount 컬럼이므로 이후 일반 재료 저장의 정밀도에도 적용되지만 기존 행을 재작성하거나 반올림하지 않는다. numeric typemod 제거·CHECK 검사에는 테이블 잠금/검사 영향이 있어 정확 운영 대상과 백업 확인 후 승인받는다.

OFF에서는 nullable 제품뿐 아니라 모든 새 source marker·단계 row 참조의 저장을 막는다. 안전하게 확인되는 기존 일반/연결 제품 입력은 옛 저장 형태로 투영한다. 새 reader를 먼저 확인한 뒤 별도 승인된 ON으로 새 저장을 연다. 이후 문제가 생기면 쓰기를 OFF로 닫고 새 기록을 읽는 reader는 유지한다. 행 수가 0이라는 이유로 옛 reader를 허용하거나 DB를 자동 역변환하지 않는다.

최종 source·SQL hash, 독립 리뷰, 통합 build/type/lint, PR·운영 승인 및 실제 운영 확인은 확정 후 진행 장부에 기록한다. 로컬 fixture와 격리 DB 검증은 운영 적용 증거가 아니다.
