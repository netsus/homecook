# 유튜브 레시피 결과 우선 보기·개인 보관

상태: 자동 저장 후 저장된 상세 표시로 로컬 구현 완료. 운영 DB·worker·웹 변경 없음.

## 사용자에게 보이는 흐름

추출 결과를 열 때 서버가 원문으로 개인 레시피를 자동 저장하고, 저장 성공이 확인되면 저장된 레시피 상세로 바로 이동한다. 최초 저장 버튼이나 필수 검수 단계를 두지 않는다. 저장된 화면에서는 필요한 영역만 수정하고 변경이 생겼을 때만 변경사항 저장을 표시한다. 같은 추출을 다시 열면 최신 저장본을 반환하며 이전 편집을 덮어쓰지 않는다. 미확인 값과 원문은 보존한다.

## 저장 경계

기존 정규 등록은 모든 재료 UUID, 유효한 분량, 조리법 연결을 요구하고 공개 YouTube 레시피를 만든다. 새 흐름은 원문 기반의 불완전한 결과도 개인 보관해야 하므로 이를 우회하거나 공개 카탈로그에 임의 데이터를 만들지 않는다. 새 소유자 전용 저장 결과에 원본과 편집값을 별도로 보존한다. 식단·장보기·요리·영양에 자동 등록된 정규 레시피로 취급하지 않는다.

POST/PATCH는 계정 세대·소유권·멱등 키를 확인한다. 변경은 expected_revision으로 동시 편집 충돌을 감지한다. 작업 세션 만료 전 처음 저장한 결과는 세션 보존 기간과 독립적으로 다시 열 수 있다. 원본 근거는 브라우저 입력으로 덮어쓰지 못한다.

## 구현 범위

- 결과 화면과 선택적 영역 편집
- 개인 보관 API·DB 계약, 원본 보존·재시도·동시 편집 보호
- 보관 목록·상세 페이지·마이페이지 진입
- 기존 추출 모델·P5 평가·worker 변경 없음

## 이전 수동 저장 구현 검증 (자동 저장 정정의 검증과 구분)

- 관련 Vitest 5개 파일 44개 검사 통과: 결과 우선 화면, 원문 재료명 수정/추가, 미확인 수량·취향껏 구분, 조리법 미연결 단계 편집, 개인 저장·재조회·수정, 태그, 세션 복원, 오류·충돌·인증 경계.
- 최종 production 빌드의 실제 Next 앱을 로컬에서 열어 390px/1440px 브라우저에서 결과 → 재료 수정 → 저장 → 새로고침 → 재수정 → 보관 목록 흐름 확인. 가로 넘침과 페이지 오류 0. 이 검사는 API 응답과 로그인 쿠키를 격리 fixture로 제공했으며 실제 인증 서버·DB까지 연결한 브라우저 E2E는 아니다.
- 격리 테스트 DB의 schema/선택 fixture를 임시 DB로 복제해 새 migration 적용과 실제 canonical 세션 권한·권한 폐기·scope/path/method·ACL 차단을 검증했다. 원본 권한 함수를 바꾼 테스트는 shape 검사로만 별도 기록했다.
- 서로 다른 멱등 키의 실제 두 DB 연결로 동시에 최초 저장해 결과 1행과 영수증 2행으로 수렴했다. create → update → 원래 create 재시도가 원래 성공 응답을 돌려주는 것도 확인했다.
- 타입 검사·production 빌드·변경 코드 ESLint·diff 검사 통과. 최종 단순화·직접 단위 입력·반응형 편집 유지 수정 뒤 다시 통과했다. 마이페이지의 기존 showToast dependency 경고는 이 변경과 무관하다.
- 독립 코드 검토의 재시도/동시성/충돌 지적 3개를 수정해 재검토 CLEAR. 임시 검증 DB와 브라우저는 정리했다.

## 단순화와 남은 경계

필수 검수 화면·반복 제목·추출 완료 단계 표시와 도달할 수 없는 기존 등록 완료/끼니 추가 코드를 제거했다. 원문 결과를 읽는 화면과 선택적 편집 상태를 같은 데이터로 사용한다. 빈 분량의 임의 100g 보정과 숫자 입력 시 단위 g 자동 삽입도 제거했다. 화면 크기에 따라 화면 구성이 바뀌어도 편집 상태가 유지되도록 상위 화면에서 관리한다. 단위는 큰술·개 등 원문 단위를 직접 입력할 수 있고, 직접 확정한 분량은 미확인 표시를 해제한다.

개인 보관 결과는 기존 정규 레시피와 구분된다. 현재 이 결과를 식단·장보기·요리에 자동 연결하는 승격 동작은 제공하지 않는다. 새 DB 함수 migration은 빠른 추가형 테이블 배포 경로에 해당하지 않으며 격리 검증과 별도 통제 적용 후 웹 배포가 필요하다. 이 작업은 운영 배포·P5 성능 검증 완료가 아니다.

## 2026-10-08 사용자 정정 — 자동 저장 후 상세

사용자는 저장 전 미리보기가 아니라 이미 저장된 형태의 레시피를 원했다. 최초 수동 저장 설계는 이 지시로 대체한다. POST의 source-only 요청 `{extraction_id}`는 원본을 서버에서 읽어 저장하거나 동일 소유자·계정 세대의 기존 최신 결과를 반환한다. 요청에 편집 content가 없으므로 새로고침으로 기존 편집을 덮어쓸 수 없다. 저장 실패 시 완성 화면을 가장하지 않고 재시도/로그인 안내를 제공한다. 편집 후 PATCH의 동시 수정·멱등 보호는 유지한다.

## 자동 저장 정정 검증

- 최초 저장 버튼 없이 source-only POST를 자동 호출하고 서버 성공 확인 후 저장 상세로 이동한다. 저장 전에는 처리/실패 상태만 표시한다.
- 기존 저장 상세 새로고침은 GET만 수행한다. 추출 결과를 다시 열어 ensure를 호출해도 새 행을 만들거나 편집본을 원문으로 덮어쓰지 않는다.
- 읽기 상태에는 저장 CTA가 없고, 편집한 경우에만 revision 기반 변경사항 저장이 표시된다.
- 관련 Vitest 47개·타입 검사·최종 빌드 통과. 독립 검토는 수량 의미 및 테스트 권한 fixture 문제를 수정한 뒤 CLEAR다. 실제 격리 DB에서 원문 변환·소유권·만료·실제 canonical authority·동시 ensure를 검증했다.
- 390px/1440px 실제 앱 브라우저에서 자동 저장 후 상세 이동·최초 저장 버튼 없음·재열기·PATCH·편집 보존을 확인했다. 가로 넘침/페이지 오류 0. API와 로그인은 격리 fixture이며 실제 DB와 결합한 브라우저 E2E는 아니다.

- 운영 배포와 정규 식단·장보기 연결 범위는 그대로 미포함이다.
