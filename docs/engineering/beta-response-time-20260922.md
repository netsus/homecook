사용자는 집 Wi-Fi에서 `app.mumeok.kr`이 느려 수동 테스트하기 어렵다고 보고했다. 공개 주소, 같은 Mac의 Caddy HTTPS, 앱 loopback, DB와 호스트 자원을 나누어 확인했다. 인증·세션 liveness·소유권 검사를 생략하거나 캐시하지 않는다.

## 측정으로 확인한 범위

첫 측정은 같은 Mac에서 쿠키 없이 동일 경로를 호출한 결과다. 브라우저에서는 2026-09-22 19:49 KST에 Cloudflare 520 화면도 확인했다.

| 대상 | 공개 주소 | 앱 loopback |
| --- | ---: | ---: |
| 홈 HTML | 5.377초 | 0.0058초 |
| 레시피 HTML | 10.727초 | 0.0688초 |
| 레시피 목록 API | 4.046초 | 0.0221초 |

- 반복 측정에서도 공개 홈/API는 약 0.986~9.422초로 흔들렸고 앱 loopback은 약 0.004~0.021초였다.
- Caddy까지 직접 TLS 연결한 요청은 인증서 검증을 유지한 채 HTTP/2 15~19ms, HTTP/1.1 약 41ms였다. 실제 경로는 **Cloudflare → Caddy 8443 → 앱 3100**이다. cloudflared는 실행 중이 아니므로 tunnel/QUIC 변경을 해결책으로 삼지 않는다.
- 같은 회선에서 앱의 Cloudflare 접속 지점은 `SEA`, 비교 대상 `www.cloudflare.com`은 `ICN`이었다. 앱 도메인이 북미 중계를 거치는 것은 확인했지만, 이것만으로 특정 520의 원인을 확정하지 않는다.
- DB 연결은 7~9/100, 장기 활성 쿼리·잠금 대기 0이었다. 최근 188초의 웹 관련 DB 처리 평균은 약 0.9~9.8ms였다.
- 공유기와 외부 기준 주소 ping 10회씩 손실 0, 평균 21~25ms, 최대 약 115ms였다. 짧은 첫 구간 지연은 있으나 수초 지연·520을 집 Wi-Fi 문제로 단정할 증거는 없다.

**측정된 큰 지연은 외부 접속 구간에 집중된다.** 사용자 직접 로그인 후 Cloudflare 분석도 확인했다. 최근 한 시간 집계에서 Edge 520은 홈 `/`의 1건이며, 이 필터의 Origin 4xx/5xx는 모두 0이다. 별도의 Origin 500 3건과 구분한다. 520의 세부 원인(연결 중단·응답 형식·전송 문제 등)은 요청별 연결 증거가 부족해 미확정이다. [공식 520 안내](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-520/) 역시 비정상 원본 응답·접속 문제·HTTP/2 구성 등을 구분해 원본 로그와 Ray ID를 대조하도록 안내한다.

Cloudflare Origin Analytics의 최근 24시간 상단 기간 집계는 연결 성공률 99.4%, 응답 시간 P95 9,459ms였다. 같은 화면의 TCP/TLS 지표는 각각 145/271ms, Response Wait는 554ms였다. 기간 전체 집계와 차트의 개별 시간 구간 값을 혼합해 앱 쿼리 시간으로 해석하지 않는다. 공개 요청의 큰 편차가 단일 로컬 측정만의 현상은 아님을 뒷받침한다.

정적 CSS·JS는 공개 GET 4회 모두 `CF-Cache-Status: HIT`, 1년/immutable, Set-Cookie 없음이었다. 전체 캐시 적중률이 낮다는 이유로 개인화 응답을 캐시하는 규칙을 추가하지 않았다. 분석용 `Error monitoring` 대시보드를 만들었으며, DNS·캐시·TLS·접근 정책은 변경하지 않았다.

## 효과 없는 설정을 남기지 않은 비교

Caddy 원본 파일·live JSON·TLS·헤더 덮어쓰기·인증 경계·R2 증거를 확인하고, live `protocols` 항목만 일시적으로 HTTP/1.1로 바꿨다. 설정 파일은 바꾸지 않았으며 `finally`에서 원본 live JSON으로 복구했다. 각 구간의 공개 홈/API 6회가 모두 200이었다.

| 구간 | 응답 시작 중앙값 | 최대 |
| --- | ---: | ---: |
| 변경 전 HTTP/2 | 0.644초 | 0.893초 |
| 임시 HTTP/1.1 | 0.829초 | 0.937초 |
| HTTP/2 복구 후 | 0.853초 | 0.969초 |

**HTTP/1.1의 개선 효과는 없었다.** 최초 수초 지연은 변경 전부터 자연 회복됐으므로 이 회복을 최적화 효과로 계산하지 않는다. 영구 네트워크 변경 0, 프로세스 PID·원본 파일/live JSON·R2 proof 해시 보존을 확인했다. auth health 401과 비Auth 경로 404 차단도 모든 구간에서 유지됐다. Cloudflare proxy 비활성화·TLS 검증 우회·공개 범위 확대는 하지 않았다.

## 앱의 불필요한 대기 줄이기

- 플래너: 인증과 사용자 초기화가 끝난 뒤 열·계획·제품 계획을 함께 읽는다. 계획의 고정 데이터 검증 후 레시피·장보기 정보를 함께 읽는다.
- 레시피 상세: 조리 단계 조회를 재료·영양·출처 조회와 함께 시작한다. 기존 단계 관계가 없는 경우의 제한된 fallback은 유지한다.
- 사용자 확인·계정 세대·세션·행 접근 권한·오류 응답은 그대로 유지한다. 쿼리마다 수행하는 인증을 캐시하지 않는다.
- `scripts/diagnose-prelaunch-response-time.mjs`는 같은 요청을 공개 주소·인증서를 검증한 Caddy·앱 loopback으로 비교한다. 쿠키·비밀정보·개인 데이터를 읽지 않고 응답 시간·상태·중계 지점만 출력한다.

```bash
node scripts/diagnose-prelaunch-response-time.mjs --runs 3
```

실행 호스트는 현재 운영 Mac이며 앱 3100/Caddy 8443을 기준으로 한다. 성공 응답의 중앙값과 최대값, 전체 시도 수·실패 수를 구분한다. 속도가 정상이어도 오류 원인이 영구 해결됐다는 뜻은 아니다.

## 재발 가능성과 남은 범위

- 외부 중계·회선 경로 변동은 재발할 수 있다. 같은 증상 때 위 진단으로 외부/원본/앱을 먼저 구분하고 520 시각·Ray ID를 보관해 Cloudflare 요청 로그와 대조해야 한다.
- 운영 Mac은 개발 작업도 함께 처리한다. 32GB 메모리에서 swap 약 29GB와 지속적 메모리 압축·해제가 관측됐다. 측정 중 swap-out은 0이어서 이것을 현재 지연의 직접 원인으로 단정하지 않지만, 빌드·브라우저·동시 작업이 늘면 추가 위험이다. 사용자 앱이나 다른 작업의 컨테이너는 임의 종료하지 않았다.
- 순차 조회 병렬화는 앱 처리의 불필요한 대기를 줄인다. 외부 네트워크 지연을 없애는 조치라고 표현하지 않는다.
- 별도 Origin 500 집계와 성장 기능 로그도 확인했다. 업적·배지 중복키는 기존 코드가 `23505`를 정상 중복으로 흡수한다. 성장/XP/알림의 일부 직접 쓰기에는 RLS 거부가 있어 후속 보완 대상이다. 성장 알림은 주 화면과 별도 실행되고 식사기록 저장에는 호출이 없으며, 레시피/계획 등록의 부가 처리 대기는 남아 있다. 이 기록을 520이나 이번 병렬화의 원인으로 연결할 근거는 없다.
- 신규 로그인·실제 요리 완료와 섭취 기록은 이번 속도 측정의 범위가 아니다.

## 최종 확인과 배포

- API·권한 회귀 3파일 **116개 통과**. 새 회귀 9개는 시간 초과 기대값 대신 해제하지 않은 Promise로 실제 동시 시작과 의존 순서를 검사한다. 401/500, bootstrap 이전 조회 금지, 제한된 조리 단계 대체 조회도 확인했다.
- typecheck, 변경 파일 ESLint, diff 검사 통과. 독립 검토에서 차단 지적 없음.
