# 영양 계산 신뢰성: 1차 수정 경계와 단계별 개선안

2026-10-22 기준. 이 문서는 구현 후보와 후속 설계다. 운영 DB 변경, 기존 레시피 일괄 재계산, 과거 식사 기록 변경을 승인하거나 완료로 표시하지 않는다. 목표는 모든 음식을 임의의 숫자로 채우는 것이 아니라 **계산 가능한 값, 근거 있는 추정값, 아직 모르는 값을 정확히 구별**하는 것이다.

## 사용자에게 보이는 결과와 확인된 원인

| 사례 유형 | 읽기 전용으로 확인한 결과 | 행별 원인에서 아직 모르는 것 |
| --- | --- | --- |
| 부분 반영 | 프로필 누락·잘못된 수량·개수 정체성·단위 정의 경고가 함께 나타났다. | 경고와 원문 재료 행의 연결은 확인되지 않았다. |
| 정량 재료 반영·전체 부분 상태 | 정량 값은 계산됐으나 `TO_TASTE_EXCLUDED` 같은 제외 상태가 남았다. | 현재 저장본과 공개 응답의 revision·행별 누락 이유 일치는 확인되지 않았다. |
| 계산 불가 | 프로필 누락과 잘못된 수량 경고가 함께 나타났다. | 매칭·수량·발행 실패의 행별 비중은 확인되지 않았다. |

공개 API는 행별 결측 원인을 제공하지 않는다. 소유자 범위 조회나 기존 개인 데이터를 변경하지 않았으므로 위 표에서 특정 재료의 값을 지어내지 않는다. 추가 진단은 소유자 권한으로 **읽기만** 하는 행별 리포트가 필요하다.

재현 가능한 코드 결함은 둘이다. 첫째, 현재 DB 리더가 지원하는 `계량큰술`과 승인 밀도 근거로 `2계량큰술 × 15 ml × 1.2 g/ml = 36 g`을 계산하면 100 g당 200 kcal에서 72 kcal이지만, 공개 정규 레시피 경로가 frozen 비직접 단위를 곧바로 미확인으로 만들어 근거를 다시 읽지 않았다. 오래된 스냅샷이 있으면 이 읽기 계산 자체도 생략됐다. **일반 `큰술`은 현재 SQL context가 필요한 원문별 부피 정의를 제공하지 않으므로 이 복구 사례에 포함하지 않는다.** 둘째, 저장 API의 `nutrition_publication.status = ready`는 스냅샷 **발행 성공**을 뜻하는데, 화면에서 영양 **완전 계산**처럼 해석될 수 있었다. 로컬 1차 앱 수정은 공개 상세에서 승인된 서버 근거를 재조회하고 frozen 원문·단위·수치·근거 ID·근거 버전을 모두 대조한 경우에만 재계산하며, 비직접 수량이 있으면 이전 스냅샷보다 이 현재 계산을 우선한다. 저장 확인 응답에는 별도의 `calculation_status`를 담는다. 재조회 실패, 변조, 승인 근거 부재는 `null`/부분 상태로 남긴다. GET은 스냅샷을 쓰지 않는다.

**영구 저장은 별개의 결함이었다.** `supabase/migrations/20261019130000_youtube_saved_nutrition_publication.sql`의 `public.build_recipe_nutrition_input_guard`는 saved canonical의 비직접 수량을 `null`로 만들었다. `public.write_recipe_nutrition_snapshot`은 그 guard·content hash·revision·source 일치를 강제하므로 앱만 바꿔서는 72 kcal을 영구 스냅샷에 안전하게 실을 수 없다. 로컬 후속 후보는 `20261022120000_youtube_saved_nutrition_frozen_quantity.sql`에서 **현재 승인된 서버 수량 근거를 재실행**하고 frozen 원문·표시량·context fingerprint·결과 전체가 같을 때만 guard에 원문량을 반영한다. 앱 publisher도 같은 원문량과 근거를 재조회하여 영양과 guard를 만든다. 수량 정책이 꺼졌거나 프로필 버전만 바뀌어 fingerprint가 달라진 경우 두 경로 모두 수량을 미확인으로 둔다. 합성 `2계량큰술 → 36 g → 72 kcal` 및 표시만 `36 g`인 경우의 영구 스냅샷·미래 식사 pin·요리 완료 값을 격리 DB에서 검증했다. **운영 DB에는 적용하지 않았고 기존 기록도 재계산하지 않았다.**

## 목표 데이터 흐름과 불변식

`영상/원문 → 중복 제거된 재료 행 → 카탈로그/제품 매칭 → 승인된 수량 환산 → 레시피 총영양 → 완성 요리 전체 무게 → 먹은 g 비율 → 식사 시점 불변 스냅샷 → 일·주간 합계`.

각 단계에서 원문, 정규화 값, 출처 ID·버전, 추정 방식, 계산 버전, revision/hash, 누락 이유를 잃지 않는다. `null`은 모름이고 수치 `0`은 근거가 있는 영(零)이다. 사용자 확인은 입력을 확인했다는 사실이지 계량기의 실측으로 승격되지 않는다. 확률로 보이는 신뢰도 점수는 검증된 보정 데이터 없이는 제공하지 않는다. `계산 가능률`과 근거·상태·사용자 확인까지 충족한 `신뢰 가능한 계산률`을 별도 지표로 둔다.

영상 본문과 자막의 같은 재료를 두 번 더하지 않는다. 선택 재료·대체 재료·양념장 하위 재료는 포함 조건을 확정한 뒤 합산하며, ‘2인분 기준’과 레시피 전체량을 중복 배율로 적용하지 않는다. 생쌀/밥, 생고기/익힌고기, 가식부/구매 중량, 가당/무가당·브랜드 제품은 서로 다른 매칭이다. 100 g 기준과 1회 제공량 기준에는 기준량과 단위가 반드시 붙는다.

`약간/적당량`은 무조건 고정 g으로 치환하지 않는다. 문맥(음식, 분량, 조리법, 재료)에 따라 범위를 제시할 수 있으면 **추정·출처·범위·수정 가능**으로 표시하고, 근거가 없으면 사용자 확인을 요청한다. 기름·설탕 등 소량 오차가 열량/당에 큰 영향을 주는 재료는 보수적으로 별도 확인한다. 원문에 제시된 범위도 중앙값 하나로 사실처럼 확정하지 않는다. `ready`(처리 종료), `calculation_status`(영양 반영 상태), `record_complete`(그날 기록 완료)는 다른 축이다.

## 주간 리뷰: 기존 6화면 기획과 연결

오늘 기록·최근 집밥·체중·주간 추세·제안·로컬 저장 6화면을 연결하는 **통합 제안**이며 기존 프로토타입 원문을 수정했다는 주장은 아니다. 오늘/최근 집밥 화면에서 실제 식사 스냅샷의 섭취 g·영양과 `실측/추정/일부 누락`을 표시한다. 주간 추세에서는 먼저 ① 섭취 사실과 데이터 상태, 다음 ② 체중 변화, 마지막 ③ 데이터 조건을 충족할 때만 해석·제안을 보여준다. 미기록일은 0 섭취로 취급하지 않는다. 7일 중 2일 기록이면 `기록일 2일 평균`으로 표시하고 분모는 2이며, 완료 기록일이어도 재료 영양 누락이 있으면 영양 완전일로 세지 않는다. 로컬 저장은 화면 초안/사용자 표시 설정을 보관할 수 있지만 서버의 식사 사실 원장을 대체하지 않는다. 수정·삭제 후 일간 합계와 주간 합계는 같은 원장 snapshot에서 재생성하며 사용자 로컬 시간대의 일자 경계를 쓴다.

## 검증 기준과 지표

- Golden fixture는 직접 g, 현재 지원하는 `2계량큰술`+승인 밀도, 추후 단위 정의가 필요한 일반 `큰술`과 `1/2컵`, `약간`, 개수 크기 미상, 브랜드 1회분, 생/익힘, 가식부, 대체·선택·중복 자막, 혼합 국물/고기를 포함한다. 근거 버전·상태·허용오차를 사례별로 고정한다. 승인 부피/밀도는 근거 값의 곱과 표시 반올림 오차 내에서 일치해야 하고 미확인량은 숫자 허용오차 대상이 아니다.
- 물만 더하면 총영양은 같고 완성 g당 농도만 변한다. 같은 스냅샷에서 먹은 g을 두 배로 하면 섭취 영양만 두 배가 된다. 같은 실제량의 100 g 기준/1회분 기준 결과가 일치한다. `unknown ≠ 0`이다.
- 저장 재시도는 한 번만 반영한다. 수정·삭제·대체·인분 조절은 새 revision을 만들며 오래된 hash로 계산하거나 stale cache를 쓰지 않는다. 레시피/카탈로그의 현재 수정은 과거 식사 스냅샷을 바꾸지 않는다. 식사 수정·삭제 후 일간/주간 합계는 같은 원장과 일치한다.
- 소유자 외 요청, 공개 읽기, 인증 만료, storage/RPC 실패, 근거 폐기, revision 경합에서도 권한·source guard를 완화하지 않고 `null`/재시도 상태를 유지한다. 로그/지표에는 재료 타입·사유 코드·revision과 익명 집계만 남기고 개인 식사·토큰·원문 자막은 남기지 않는다.
- 지표는 신규 레시피의 유효 추출률, 재료 매칭률, 환산 가능률, **신뢰 가능한 계산률**, 고영향 미확인 재료 비율, 발행 지연/실패·재시도·중복률, stale 판정률, 주간 기록일 및 영양 완전일을 분리한다. 분모와 시간 창을 각 지표에 명시한다. 퍼센트 목표는 현재 기준선 측정 뒤 결정한다.

출시 순서는 A/B의 독립 리뷰·격리 확인 → 승인된 DB240 전용 보호 프로필로 **DB를 먼저** 적용 → 구 앱의 읽기·기존 v4 발행 호환성 확인 → 새 앱 활성화와 미래 저장 확인 → C의 데이터 개선 → D의 기록·주간 리뷰 → E의 과거 데이터 선택적 dry-run이다. 새 앱을 DB239에 먼저 배포하면 frozen-v1 발행이 거절되므로 운영 도구가 순서를 강제한다. DB240 적용 직후 구 앱은 기존 경로를 유지하며, 구 앱이 먼저 만든 v4 snapshot은 새 frozen-v1과 별도 식별자로 공존한다. 구 앱의 늦은 v4 재시도가 새 snapshot을 강등시키지 않는지도 검증한다. 새 앱 검증 실패 시 기존 앱으로 복귀하더라도 **DB240과 새 불변 snapshot은 자동으로 되돌리지 않는다**. 결과가 불확실한 DB commit은 guard·receipt와 원장을 읽어 forward reconcile하며 무조건 재실행하지 않는다. 세 함수 중 하나만 구 정의로 복원하는 절차는 금지한다. 기존 식사 pin·기록과 불변 snapshot의 삭제·수정, 레시피 일괄 재계산은 이 단계 밖이다. 아직 운영 적용·운영 smoke·기존 데이터 dry-run은 검증되지 않았다. 주요 미결정은 추정량을 제안할 재료군·허용 범위, 고영향 재료 확인 임계값, 제품 기준량의 소스 우선순위, 기록 완료의 사용자 동작, 주간 리뷰의 사용자 로컬 시간대 정책이다. 각 결정은 실제 golden 자료와 사용자 검토를 거쳐 확정한다.
