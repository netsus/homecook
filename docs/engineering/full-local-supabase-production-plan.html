집밥 서비스를
Mac 안의 Supabase로 옮기는 계획

Google, 네이버, 카카오 로그인부터 DB와 이미지 저장소까지 현재 Mac에서 운영하되, 로그인 보안은 직접 만들지 않고 Supabase Auth를 self-hosting하는 전환 계획입니다.

작성일 2026-07-31 KST 상태 로컬 복원 rehearsal 완료, 외부 공개 대기 대상 homecook production
현재 상태: 원격 Auth·DB의 암호화+HMAC 백업과 두 번의 독립 로컬 복원, 별도 Storage 복사, Google·Kakao 로컬 Auth 설정까지 통과했습니다. 다만 mumeok.kr이 아직 등록되지 않아 Mac 자동 시작 명령까지 준비했습니다. Cloudflare HTTPS, callback 변경, 실제 소셜 로그인과 최종 전환은 시작하지 않았습니다.

한눈에 보기

딱 한 줄 요약

OAuth와 세션을 직접 구현하지 않고, Supabase Auth까지 Mac의 Docker로 옮겨 기존 auth.uid() 기반 권한 규칙을 유지합니다.

지금

Mac에서 Next.js를 실행하지만 로그인과 운영 데이터는 원격 Supabase 프로젝트가 담당합니다.

목표

Mac 안에서 Supabase Auth, PostgreSQL, PostgREST, Storage를 함께 실행하고 Cloudflare Tunnel로 필요한 주소만 공개합니다.

비유로 이해하기

가게를 임대 건물에서 우리 집으로 옮기는 일

원격 Supabase

건물주가 경비, 전기, 시설 보수를 맡아주는 임대 건물과 비슷합니다.

현재 Mac

가게와 창고를 직접 관리하는 우리 집입니다. 통제권이 늘지만 책임도 늘어납니다.

Cloudflare Tunnel

집 주소와 내부 방을 숨기고, 손님이 들어올 정문만 연결하는 안전한 통로입니다.

중요한 현실

로컬로 옮긴다고 자동으로 더 안전해지는 것은 아닙니다. Mac 보안 업데이트, Docker 업데이트, 백업, 장애 복구, 인터넷과 전원까지 직접 책임져야 합니다.

목표 구조

외부에는 로그인 문만 열고, 데이터 방은 닫습니다

휴대폰은 앱과 로그인 주소에만 접근합니다. DB와 이미지 Storage는 Next.js 서버를 거쳐야 하며 인터넷에 직접 노출하지 않습니다.

핵심 선택

소셜 로그인을 직접 만들지 않는 이유

선택: self-hosted Supabase Auth

  • 기존 Supabase SDK와 로그인 흐름을 재사용합니다.
  • 기존 사용자 UUID와 auth.uid() RLS를 유지합니다.
  • Google·Kakao는 기본 provider를 사용합니다.
  • 네이버는 custom:naver로 먼저 격리 검증합니다.

금지: Homecook 자체 Auth 구현

  • OAuth code 교환과 PKCE를 새로 만들지 않습니다.
  • refresh token 회전과 세션 폐기를 새로 만들지 않습니다.
  • 계정 연결 충돌 처리를 임의로 단순화하지 않습니다.
  • 브라우저에 service key를 전달하지 않습니다.

정확한 주소 계약

비슷해 보여도 세 값은 다릅니다

SUPABASE_PUBLIC_URL=https://auth.<owned-domain>
API_EXTERNAL_URL=https://auth.<owned-domain>/auth/v1
GOTRUE_SITE_URL=https://app.<owned-domain>

provider callback=${API_EXTERNAL_URL}/callback
초보자가 자주 틀리는 부분

API_EXTERNAL_URL에는 반드시 /auth/v1이 붙습니다. provider 개발자 센터의 callback은 그 뒤에 /callback을 붙인 정확한 주소여야 합니다.

비밀키 보호

Keychain에서 container까지 비밀값이 가는 길

  1. 원본 비밀값은 macOS Keychain에 저장합니다.
  2. 시작 직전 repo 밖 ~/.homecook/secrets/local-supabase/에 필요한 파일만 만듭니다. 폴더 권한은 0700, 파일은 0600입니다.
  3. Docker가 파일을 /run/secrets에 읽기 전용으로 연결합니다.
  4. 고정된 entrypoint가 파일을 읽어 서비스 실행 순간에만 환경변수로 넘깁니다.
  5. 검사 script가 Git, build, browser bundle, log, Docker 설정의 유출 0건을 확인합니다.
보안 한계도 기록합니다

이 방식은 Compose와 docker inspect의 Config.Env에서 비밀값을 숨깁니다. 그러나 Mac 관리자나 container 내부 root는 실행 중 process를 볼 수 있으므로 FileVault, 화면 잠금, 최소 관리자 계정, Docker socket 비공개도 필요합니다.

로그인 전환 안전장치

진행 중인 로그인이 0이 된 뒤 문을 바꿉니다

원격 로그인 화면을 연 사용자가 callback으로 돌아오는 도중 local Auth로 바뀌면 계정 연결이 꼬일 수 있습니다. 그래서 로그인 버튼은 먼저 POST /auth/flow/start 서버 route를 호출하고, 서버가 진행 중 흐름을 private ledger에 기록합니다.

무엇을 저장하나

서버가 HMAC 처리한 attempt 값, login/link 종류, provider, 시작·만료·종료 시각만 저장합니다.

얼마나 기다리나

TTL은 900초입니다. 전환 때 최대 960초를 기다리고 남은 만료 흐름을 닫습니다.

무엇을 거부하나

이전 remote 권한이나 이전 cutover epoch의 cookie와 code는 local callback에서 거부합니다.

저장하지 않는 값

OAuth code, access token, refresh token, email, 사용자 UUID 원문은 ledger와 cookie에 넣지 않습니다.

서버가 __Host-homecook-auth-flow HttpOnly cookie를 만든 뒤에만 브라우저가 signInWithOAuth() 또는 linkIdentity()를 실행합니다. 기존 JavaScript provider cookie는 제거하고 callback은 ledger의 provider만 믿습니다.

데이터 이전

DB와 이미지는 서로 다른 공식 경로로 옮깁니다

현재 원본은 원격 Supabase 하나입니다

hybrid 전환은 실제 production에 적용되지 않았습니다. 따라서 원격 Auth·DB·Storage를 같은 maintenance 시점에 백업한 결과만 이전 원본으로 쓰고, Mac의 기존 연습용 DB·이미지는 버린 뒤 fresh restore합니다. 두 데이터를 섞지 않습니다.

DB와 Auth 데이터

fresh volume에 role, schema, auth.users, auth.identities, 앱 데이터, RLS 순서로 복원합니다. 기존 사용자 UUID는 그대로 보존합니다.

Storage 이미지

같은 설정의 bucket을 먼저 만든 뒤 hosted /storage/v1/s3에서 Mac loopback gateway의 /storage/v1/s3로 pinned rclone을 사용해 복사합니다.

직접 파일 복사 금지

hosted Storage의 내부 파일이나 Docker volume을 직접 복사하지 않습니다. 임시 S3 credential은 Keychain에서 mode 0600 임시 rclone config로 전달하고 성공·실패 모두 파일을 지운 뒤 hosted key를 폐기합니다.

local Storage에는 REGION=homecook-local-1과 S3 protocol key를 secret mount로 주입합니다. 이 S3 주소는 인터넷에 공개하지 않고 같은 Mac의 loopback에서만 복사와 백업에 사용합니다.

복사 후에는 object path, 개수, byte, MIME type, SHA-256, DB reference가 모두 일치하는지 확인합니다. mismatch 허용값은 0입니다.

실행 순서

한 번에 바꾸지 않고 11단계로 검증합니다

STAGE -1

공식 계약 변경

원격 Auth 전제를 공식 문서에서 먼저 full-local 계약으로 바꿉니다.

STAGE 0

원본 목록 고정

사용자, DB, Storage, provider 설정과 off-Mac 백업을 기록합니다.

STAGE 1

격리 runtime

fresh Docker 환경에서 Auth, DB, Storage와 ES256 key를 검증합니다.

STAGE 2

세 provider 검증

Google, 네이버, 카카오 login/link를 운영 데이터 없이 시험합니다.

STAGE 3

앱 이중 경로

기본 remote를 유지한 채 local mode와 flow ledger를 추가합니다.

STAGE 4

복원 예행연습

fresh volume에서 DB restore와 S3/rclone 복사를 두 번 반복합니다.

STAGE 5

RLS와 세션 검증

다른 사용자 접근, 로그아웃 뒤 이전 token 사용을 모두 차단합니다.

STAGE 6

외부 경계 검증

Cloudflare에서 Auth allowlist 외 경로가 모두 닫혔는지 확인합니다.

STAGE 7

전환 예행연습

callback drain, 재로그인, 되돌리기까지 production과 같게 연습합니다.

STAGE 8

최종 전환

운영자 승인 뒤 callback과 데이터를 local authority로 전환합니다.

STAGE 9-10

14일 안정화와 정리

원격을 복구용으로 남겨 관찰한 뒤 별도 승인으로 hybrid를 정리합니다.

되돌리기

첫 local Auth 변화가 되돌리기 경계입니다

Rollback floor

첫 local production session 발급, provider identity 연결, 사용자 범위 DB/Storage 쓰기 중 하나라도 처음 성공한 순간입니다.

시점 가능한 복구 하면 안 되는 것
경계 전 provider callback과 app env를 원격으로 되돌림 검증 실패 상태에서 login/write 개방
경계 후 login/write 동결 후 Auth·DB·Storage 변화분을 함께 복구하거나 앞으로 수정 env만 원격으로 되돌리는 단순 rollback

새로운 local signing key를 사용하므로 기존 원격 session은 유지하지 않습니다. 전환 뒤 모든 사용자는 한 번 다시 로그인해야 합니다.

완료 기준

아래 항목이 모두 통과해야 production을 엽니다

  • 세 provider의 실제 local OAuth login 성공
  • 기존 사용자 UUID와 소유 데이터 mismatch 0
  • User A가 User B의 row/object에 접근한 건수 0
  • 로그아웃 뒤 만료 전 token mutation 0
  • server-issued flow cookie 전 OAuth SDK 호출 0
  • old remote cookie/code의 local 수락 0
  • 공개 Auth allowlist 외 Supabase endpoint 노출 0
  • S3/rclone 복사 후 Storage mismatch 0
  • Git·bundle·log·Docker 설정의 secret 노출 0
  • Storage payload까지 포함한 Mac 밖 complete backup의 실제 restore 2회 성공
  • Mac 재부팅 뒤 ordered recovery 성공
  • 경계 전·후 rollback 예행연습 성공
  • 첫 local Auth 변화에 운영자 별도 승인
무엇을 자동 테스트하나요?
URL 검증, JWT issuer와 audience, flow ledger 만료, RLS, Storage owner policy, 세션 폐기, account delete/recreate, callback 변조와 replay, Cloudflare path 차단, secret scanner를 unit·integration·Playwright로 확인합니다.
무엇을 사람이 직접 확인하나요?
Google·네이버·카카오 개발자 센터 callback, 실제 LTE/5G 로그인, 장애 복구 시간, backup restore 결과와 최종 cutover 승인은 운영자가 evidence와 함께 확인합니다.

용어 사전

이 문서에서 쓰는 말

Auth

누가 로그인했는지 확인하고 session을 발급하는 기능입니다.

OAuth

Google 같은 외부 계정으로 안전하게 로그인하는 표준 방식입니다.

Callback

소셜 로그인이 끝난 뒤 provider가 사용자를 돌려보내는 정확한 주소입니다.

JWT

로그인한 사용자의 신원을 증명하는 서명된 token입니다.

RLS

DB가 사용자마다 볼 수 있는 행을 제한하는 행 단위 보안 규칙입니다.

Storage

레시피 이미지 같은 파일과 그 정보를 저장하는 서비스입니다.

Self-hosting

외부 회사 서버 대신 내 컴퓨터에서 서비스를 직접 운영하는 방식입니다.

Cloudflare Tunnel

공유기 port를 직접 열지 않고 Mac 서비스를 HTTPS 주소와 연결하는 통로입니다.

Authority

현재 어떤 시스템의 로그인과 데이터를 진짜 원본으로 믿을지 정한 기준입니다.

Rollback floor

이 시점 뒤부터는 환경변수만 되돌려서는 안전하게 복구할 수 없는 경계입니다.

Ledger

진행 중인 로그인 흐름의 상태만 최소한으로 기록하는 내부 장부입니다.

rclone

S3 같은 저장소 사이에서 파일을 검증하며 복사하는 도구입니다.

다음 행동

도메인을 소유한 뒤 외부 공개를 이어갑니다

다음 단계는 mumeok.kr 또는 실제 사용할 도메인을 구입·소유한 뒤 Cloudflare named tunnel에 app과 auth hostname을 연결하고, 세 개발자 센터의 callback을 바꿔 실제 로그인·계정 연결을 검증하는 것입니다.

아직 실행하지 않은 고위험 단계

소유하지 않은 도메인으로 callback을 바꾸지 않습니다. custom:naver 등록, 첫 local production session·identity·user write, 원격 프로젝트 삭제와 최종 authority 전환은 별도 운영자 승인 전까지 계속 차단합니다.

Mac 자동 시작은 준비만 완료

로그인할 때 Docker runtime을 시작하는 LaunchAgent 설치·상태·삭제 명령은 만들고 테스트했습니다. 아직 최종 전환 전이라 이 Mac에는 설치하지 않았으며, 설치 전 상태는 unloaded입니다.

상세 기술 절차와 acceptance 기준은 전체 로컬 Supabase production 전환 계획 MD를 기준으로 합니다.
