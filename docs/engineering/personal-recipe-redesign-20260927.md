# 개인 레시피 복사·편집·계획 반영

상태: 2026-09-27 사용자 피드백 묶음의 로컬 구현. 머지·배포·운영 데이터 변경은 별도 요청 때 수행한다.

## 사용자 흐름과 설계

1. 공개 레시피의 **내 레시피로 수정**은 원본을 건드리지 않고 비공개 사본을 만든다. 제목·기준 인분·재료·조리 단계와 대표 이미지를 이어받는다.
2. 재료는 `번호. 이름 · 구성 · 변경 표시`와 `[수량] [단위 선택] [교체] [×]` 두 줄로 표시한다. 작은 화면에서 한 줄에 억지로 밀어 넣지 않는다. 필드 이름은 접근성 이름으로 제공한다.
3. 단위는 기존 계산기가 지원하는 질량·부피·개수 단위 중 선택한다. 단위를 바꿔도 수량을 자동 환산하지 않는다. 기존 비표준 단위는 해당 원본 재료·구성에서 이어받은 값에 한해 보존한다. 제품의 기준 단위는 임의로 바꾸지 않는다.
4. 편집을 열었을 때와 비교해 수정·교체·추가를 표시한다. 삭제는 ×로 실행하며 되돌릴 수 있다. 제목·설명·인분·단계도 바뀐 곳만 표시한다.
5. 개인 레시피를 다시 편집하면 같은 레시피의 revision을 올린다. 저장 오류는 초안을 유지하고 재시도할 수 있게 하며 저장 실패와 영향 확인 실패를 구분한다.
6. **기존 계획 유지**는 기존 계획에 고정된 제목·인분 기준·재료·단계를 유지한다. 계획 카드에서 여는 상세는 고정 내용 전용 읽기 화면이다. 최신 원문은 별도 링크로만 연다. 고정 내용이 없으면 최신 원문으로 몰래 대체하지 않는다.
7. **전체 반영**은 기존 계약에 따라 반영 가능한 미래 계획의 고정 내용을 새 버전으로 바꾼다. 미완료 장보기 수량을 다시 계산하되 체크·팬트리 제외 상태를 보존한다. 완료한 장보기 내역과 과거 요리 기록은 변경하지 않는다.
8. 상세 화면의 고정 하단은 **플래너에 추가 / 요리하기** 한 줄만 둔다. 편집·복사·삭제는 스크롤 본문 관리 영역에 둔다. 마지막 재료와 관리 영역까지 하단 탭 위로 스크롤할 수 있게 한다.
9. 알림 종은 홈과 플래너·식사 기록의 상단 헤더에만 둔다. 스크롤을 따라다니는 전역 버튼은 제거하고 알림 수신·완료 안내 기능은 보존한다.

## 저장과 공개 범위

- 복사본은 `recipes`의 새 ID, `source_type=manual`, `visibility=private`, 현재 사용자 `created_by`로 저장한다. `origin_recipe_id`는 출처를 연결하며 원본을 수정하지 않는다.
- 재료와 조리 단계는 복사본 ID에 저장한다. 재편집은 같은 ID의 revision을 갱신한다.
- 공개 검색은 `visibility=public`인 레시피만 대상으로 하므로 다른 사용자는 개인 편집본을 검색할 수 없다. URL을 알아도 소유권 검사로 보호한다.
- 계획은 `recipe_content_snapshot_id`로 별도의 고정 내용에 연결된다. 개인 레시피 최신 내용과 계획의 고정 내용은 서로 다른 읽기 대상이다.
- 기존 내용 고정 데이터에는 이미지가 없다. 계획 고정 상세에 현재 사진을 끼워 넣어 과거 사진으로 오인시키지 않는다. 일반 상세·계획 카드의 대표 사진 상속은 별도 이미지 읽기 정책을 따른다.

## 확인된 원인과 수정 경계

- 재편집 writer의 `user_selected` 태그 provenance는 실제 DB constraint에서 허용하지 않았다. 계약값 `user_reviewed`로 수정하고 constraint 자체는 유지한다.
- 미완료 장보기 갱신 함수가 실제 `ingredients.standard_name` 대신 오래된 필드명을 사용했다. 운영 스키마를 반영한 격리 테스트로 검증한다.
- 계획 카드가 `/recipe/{id}`로 최신 원문만 열었다. `/meal/{id}/recipe`는 소유한 계획의 pin만 읽고 원본 ID·snapshot ID·소유자 일치를 검사한다.
- 개인 복제 writer가 원본 대표 이미지 정보를 복사하지 않았다. 검증된 원본 이미지의 상속과 local-only 환경에서 접근 가능한 읽기 경로를 사용한다.
- 이미지가 없을 때는 다른 음식 사진을 임의 표시하지 않고 중립적인 기본 이미지를 쓴다. 이미 만들어진 이미지 없는 개인 사본은 원본이 현재 공개·가시 상태일 때만 원본 사진을 읽으며 운영 데이터를 backfill하지 않는다.
- 관리 이미지의 내부 저장소 URL을 휴대폰에 노출하는 대신 같은 사이트의 이미지 읽기 endpoint가 레시피 접근권한과 이미지 레지스트리 경로를 검사해 전달한다. 상세·계획 카드·레시피북이 같은 읽기 규칙을 쓴다.

## 검증 및 반영

관련 UI·API 회귀와 모바일 375px/데스크톱 1440px 화면 확인을 통과했다. 계획 상세의 소유자·pin 일치·고정량 보존·조리 시간/불세기 표시를 확인했고, 단위·재료 편집과 하단 가림·알림 헤더 배치를 브라우저에서 확인했다. 격리 PostgreSQL에서 기존 계획 유지/전체 반영/멱등 재시도, 완료 장보기·과거 기록 보존, 단위 거부, 같은 구성 재료 합산, 고정 수량 및 한국 자정 경계를 검증했다. DB 검증은 운영 DB가 아닌 폐기 가능한 격리 환경에서 실행한다. 실제 소셜 계정과 운영 계획에 대한 최종 확인은 사용자 요청에 따른 묶음 배포 때 진행한다. 전체 테스트·백업 복원·자동 시작 점검은 이번 로컬 수정의 반복 조건이 아니다.


## 후속 — 개인 레시피 발견·삭제 후 복귀·기존 계획 장보기

- 개인 사본 저장 성공 시 ‘내가 추가한 레시피’와 `마이 → 레시피북` 위치를 안내한다. 새 사본 상세에는 원본 화면의 return context를 전달한다.
- 개인 상세 제목 바로 아래에 레시피북 위치 링크와 편집·삭제 두 버튼을 둔다. 고정 하단 영역을 늘리지 않는다. 삭제 확인 단계는 유지한다.
- 책뷰의 모바일·데스크톱 모두 명시적인 ‘레시피 상세’ 진입을 제공한다. 복귀 URL은 책/목록 모드와 선택한 레시피 위치를 보존한다. 삭제 후 선택 항목이 없어지면 남은 항목으로 안전하게 돌아간다.
- 삭제 성공은 전역 완료 안내와 안전한 내부 returnTo로 이동한다. 삭제된 상세를 새로 읽어 not-found 화면을 보여주지 않는다. 네트워크·권한 실패는 삭제 성공으로 처리하지 않는다.
- 삭제한 개인 레시피의 기존 계획은 고정 내용으로 장보기를 생성할 수 있다. 본인 소유의 private 원본, 본인 계획·컬럼, 등록/미연결 상태, 일치하는 snapshot 원본·소유자와 정상 세션을 모두 검증한다. 미삭제 원본의 기존 접근 규칙, 삭제된 원본의 일반 조회 차단은 유지한다.
- 이번 후속도 미커밋·미배포다. 변경된 흐름의 UI/API 및 격리 DB 회귀만 선택 확인한다.

후속 검증: 상세 저장·삭제/인증 관련 20개, 책뷰 37개, 장보기 API 10개 테스트 통과. 375px/1440px에서 책뷰 → 개인 상세 → 삭제 → 원래 책뷰의 남은 항목 복귀를 확인했다. 격리 DB에서 실제 soft-delete 후 장보기 생성 성공과 다른 사용자·누락/불일치 pin 거부를 확인했다.
