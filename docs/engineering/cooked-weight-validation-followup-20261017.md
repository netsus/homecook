## 근거를 확인해도 즉시 수율을 늘리지 않은 이유

2026-10-17에 [USDA ARS Release 2 원문](https://www.ars.usda.gov/ARSUserFiles/80400525/Data/retn/USDA_CookingYields_MeatPoultry02.pdf)의 5~6쪽과 [공식 Data.gov 메타데이터](https://catalog.data.gov/dataset/usda-table-of-cooking-yields-for-meat-and-poultry)를 다시 읽었다. 원문은 정해진 조리 조건의 가열 후 무게와 조리 전 무게를 비교한다. 다짐육 연구는 지방 범위·추가지방 없음·가열 및 배수 절차를 구분한다. 메타데이터는 배포 자료를 CC0으로 표시한다.

이는 특정 실험 조건 자료이며 일반적인 국·볶음·밥의 완성 총무게 정답표가 아니다. 현재 고정 snapshot에는 그 조건을 확정할 정보가 없어 기존 69% 후보의 운영 적용 범위를 늘리지 않았다. 단순 볶기 태그·원문 문장·대표 재료명으로 정확한 프로토콜을 만들지 않는다. 밀도가 없는 mL를 g로 바꾸지 않고, Bognár 2.98의 재사용 권리 보류와 영양잔존율/중량수율 분리는 유지한다.

## 사용자가 보는 작은 변화

기존 완료창은 `unquantified_ingredient`도 조리 조건 부족으로 안내했다. 이제 양이 정해지지 않은 재료는 ‘적당량처럼 양이 정해지지 않은 재료’, 잘못된 양은 ‘일부 재료의 양’, 환산 근거 누락은 기존 ‘무게 환산 근거’로 안내한다. 여러 사유가 함께 오면 양 미확정 → 잘못된 양 → 환산 근거 → 일반 조건 순서로 대표 원인 하나를 보여 준다. 이 문구는 전체 원인 목록이나 고쳐야 할 필수 과제를 뜻하지 않는다. 알 수 없는 새 reason code는 기존 보수적 안내로 읽는다.

계산 모델·숫자·API·실측 저장/우선순위는 그대로다. 예측값을 실측 입력에 넣지 않고, 빈칸으로 완료할 수 있다. UI 변경은 위 문구 연결뿐이며 사용자 Mac Chrome에서 실제 컴포넌트의 격리 모바일/데스크톱 시각 확인을 마쳤다. 운영 저장 확인과는 구분한다.

## W5 오프라인 평가기

`lib/server/cooked-weight-validation.ts`의 `evaluateSnapshotWeightCases`는 검토자가 명시적으로 넘긴 고정 입력을 기존 `predictSnapshotWeight`로 다시 계산한다. DB/네트워크/파일 쓰기·사용자 데이터 자동 조회·수집·모델 적용이 없는 메모리 계산이다. 사용자 화면이나 운영 reader/writer에 연결하지 않았다.

- 산출률: 유효하고 고유한 case/batch의 전체 수 중 숫자를 낸 수. unknown도 분모에 포함하며 사유는 한 case에서 한 번씩 센다. 입력 fixture에서 나온 산출률을 실제 서비스 모집단 산출률로 부르지 않는다.
- 오차: `reviewed_physical`이며 검토 근거 참조·전체음식/용기제외/섭취 전/먹을 액체 및 고정 입력 일치 확인·snapshot/인분 일치가 있는 독립 조리만 비교한다. 이는 검토자가 실제 자료를 확인해 제공하는 계약이며 enum이나 사용자 체크박스가 물리 검증을 해주는 것은 아니다. 실제 자료 사용 권한과 출처 검토는 호출 전에 필요하다.
- QA·합성·단순 자기보고·원인 불명 숫자는 실측 정답에 넣지 않는다. 같은 case나 batch가 반복되면 그룹 전체를 제외한다. 실측이 있어도 예측이 null이면 오차를 0으로 넣지 않는다.
- 비교한 표본의 MAE(g), signed bias(g), 실측값을 분모로 하는 MAPE(%)를 반환한다. 무게·규모가 다른 군의 의미는 별도 검토해야 하며 전체 평균만으로 모든 조리법이 정확하다고 판단하지 않는다. 반올림·허용 오차·신뢰 구간·정확도 통과 기준을 새로 만들지 않는다.
- 표본 0이면 `accuracy.status=unavailable`, 모든 오차는 null이다. 표본이 있어도 `descriptive_only`, `accuracyValidated=false`, `apply=false`다. 검증 코드의 `reviewed_physical` 예시는 adapter 산술을 검사하는 합성 테스트이며 실제 표본으로 보고하지 않는다.

**현재 실제 검증 정답 표본은 0건이다.** 기존 QA 180/190/200g 등의 저장 값은 음식의 물리 측정 정답이 아니므로 정확도·개인 보정·C05 자료로 승격하지 않았다. 실제 추정 정확도 개선 완료나 W0/W2/W5 전체 완료를 주장하지 않는다.

## 검증·반영 경계

관련 unit/UI 6파일125검사 통과, 전체 프로젝트 `tsc --noEmit`와 변경5파일 ESLint exit0(출력 오류/경고0), `git diff --check` exit0이다. 독립 리뷰는 추가 결함0·표적2파일26검사 통과이며 앞선125와 겹치므로 합산하지 않는다. 검사는 실제 실측 우선 저장의 기존 계약·선택 입력/skip·잘못된 입력·재시도·저장 잠금·가정·밀도 누락·합성/QA 배제·중복·표본0·오차 산술을 확인했다. jsdom의 기존 `Window.scrollTo()` 미구현 안내2회는 테스트 실패가 아니다.

사용자 Mac Chrome에서 localhost의 실제 `CookedBatchCompletionSheet`와 프로젝트 CSS를 확인했다. 375×900에서 양 미정·잘못된 양·환산 근거 없음·조리 조건 부족 안내4종과 가로 넘침 없음을 확인했고, 빈칸 완료는 `weight_action=weigh_later`, `finished_weight_g=null`을 전달했다. 1440×1000에서 예상300g은 실측 아님으로 표시하고 입력칸은 빈 상태였다. 200g을 입력해 완료하면 `set_finished_weight`/200/`reported_measured`를 전달했다. 이200g은 모형 입력이며 실제 음식 정답이 아니다. 오류 콘솔0·운영 연결0이다.

증거는 `/tmp/mumeok-beta-integration-20261017/06-weight-reason-mobile375.jpg`, `07-weight-invalid375.jpg`, `08-weight-conversion375.jpg`, `09-weight-conditions375.jpg`, `10-weight-estimate-desktop1440.jpg`, `weight-reasons-dom.json`, `11-weight-measured-submit.txt`다. 최초 자연1496px 캡처는 모바일 증거로 사용하지 않고 명시375px를 다시 적용해06파일을 교체했으며 최종 파일은375px다. 임시 Chrome 탭을 닫고 viewport를 복원했으며 격리 서버도 종료했다.

전체 build·운영 데이터 쓰기·물리 음식 측정·운영 배포는 실행하지 않았다. 기존 개인 기록, 과거 예측·식사 분모와 C05/R2 OFF를 보존한다. push/PR/merge/배포는 이 신규 후보 범위에 포함하지 않는다.
