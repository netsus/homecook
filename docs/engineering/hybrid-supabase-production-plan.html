원격 Auth + 로컬 DB/Storage 전환 계획

Google·네이버·카카오 로그인은 원격 Supabase에 남기고, 실제 Homecook 데이터와 이미지는 현재 Mac에서 운영하기 위한 초보 개발자용 안내서입니다.

!딱 한 줄 요약

로그인 증명서는 원격에서 받고, 그 증명서로 Mac의 로컬 데이터 보관함을 여는 구조로 바꿉니다.
일상 비유: 원격 Supabase Auth는 신분증 발급 기관입니다. Mac의 로컬 Supabase는 그 신분증의 공개 서명을 확인하고 사용자별 보관함을 열어 줍니다. Mac은 Google·네이버·카카오 비밀번호를 보관하지 않습니다.
아직 구현하면 안 됩니다 현재 계획의 가장 큰 blocker는 로컬 DB가 직접 읽는 auth.users를 안전한 원격 identity mirror로 바꾸는 공식 계약입니다.

1무엇이 원격이고 무엇이 로컬인가

원격 Supabase Auth

  • Google·네이버·카카오 OAuth
  • auth.users, auth.identities
  • 로그인 세션과 refresh token
  • JWT 발급과 공개 JWKS 제공

현재 Mac의 로컬 Supabase

  • 레시피, 장보기, 팬트리, 플래너
  • 사용자 설정과 앱 프로필
  • recipe-images 이미지
  • PostgreSQL, RLS, RPC, Storage
중요한 사실 “로그인만 원격”이어도 이메일, 소셜 계정 식별자, 세션 정보는 원격 Auth에 남습니다. 레시피와 개인 앱 데이터가 로컬로 이동하는 것입니다.

2먼저 알아둘 용어

Auth Authentication
사용자가 누구인지 로그인으로 확인하는 기능입니다.
JWT JSON Web Token
로그인한 사용자 UUID와 만료시간이 서명되어 들어 있는 신분증입니다.
JWKS JSON Web Key Set
JWT 서명이 진짜인지 확인하는 공개키 목록입니다. private key는 포함하지 않습니다.
RLS Row Level Security
사용자가 자기 데이터 행만 읽고 바꾸게 하는 PostgreSQL 규칙입니다.
auth.uid()
검증된 JWT의 사용자 UUID를 PostgreSQL에서 읽는 함수입니다.
PostgREST
PostgreSQL 테이블과 RPC를 HTTP API로 제공하는 Supabase 구성요소입니다.
Identity mirror
원격 Auth 사용자의 최소 신원 정보를 로컬 DB에 안전하게 맞춰 둔 사본입니다.
Shadow read
사용자에게는 기존 결과를 주면서 로컬 결과도 읽어 조용히 비교하는 검증입니다.
Cutover
실제 데이터 권위 주소를 원격에서 로컬로 바꾸는 마지막 전환입니다.
Rollback floor
이 시점이 지나면 단순 설정 복귀로는 안전하게 되돌릴 수 없는 경계입니다.
RPO
장애가 나면 최대 얼마 동안의 데이터를 잃을 수 있는지 나타냅니다.
RTO
장애 뒤 서비스를 몇 시간 안에 복구할지 나타냅니다.

4데이터가 움직이는 길

휴대폰
→
원격 Auth 로그인
→
Next.js 서버
→
로컬 Data API + RLS
→
DB / Storage

로그인한 뒤 데이터 요청이 처리되는 순서

  1. 원격 Auth가 사용자 JWT를 발급합니다.
  2. Next.js가 issuer, audience, 만료시간, sub, session_id를 확인합니다.
  3. Next.js는 로컬 apikey와 원격 사용자 JWT를 서로 다른 header에 넣습니다.
  4. 로컬 PostgREST와 Storage가 공개 JWKS로 JWT 서명을 확인합니다.
  5. PostgreSQL이 auth.uid()로 기존 RLS를 적용합니다.
apikey: <local publishable key>
Authorization: Bearer <remote user JWT>
왜 이 방법을 선택했나 사용자용 local JWT를 새로 만들지 않으므로 토큰이 두 종류로 늘어나지 않고, 현재 사용자 UUID와 RLS 의미를 가장 적게 바꿉니다.

5반드시 지킬 보안 규칙

허용

  • remote public JWKS로 서명 검증
  • request마다 사용자 JWT 전달
  • local Data API를 127.0.0.1에 제한
  • User A/B negative RLS test
  • 별도 장치와 off-site encrypted backup

금지

  • remote private signing key 복사
  • 사용자 요청을 service_role로 처리
  • PostgreSQL 5432와 Studio 공개
  • remote/local dual-write
  • 검증 전 remote DB/Storage 삭제
RLS 우회 금지 모든 요청을 local service_role로 처리하면 구현은 쉬워 보이지만, Route Handler 한 곳의 실수로 다른 사용자 데이터까지 노출될 수 있습니다.

6실행 순서

  • -1

    공식 계약과 workpack부터 작성

    공식 5종 문서에 Auth/Data authority, identity mirror, 탈퇴와 account-generation 의미를 먼저 반영합니다.

    승인과 독립 security review 없이는 다음 단계로 가지 않습니다.

  • 0

    용량·데이터·권한 inventory

    DB roles/schema/data dump, table digest, Storage object hash, auth.users 참조를 전부 기록합니다.

  • 1

    공식 Docker self-hosted Supabase 설치

    supabase start가 아니라 pinned Docker Compose를 사용하고, DB/Storage/Studio를 loopback에 제한합니다.

  • 2

    JWKS trust bridge

    원격 ES256 공개키를 local PostgREST/Storage가 검증하게 하고 잘못된 token을 모두 거부하는지 확인합니다.

  • 3

    Auth client와 Data client 분리

    remote | local-shadow | local feature flag를 만들고 기본값은 계속 remote로 둡니다.

  • 4

    Identity mirror와 lifecycle authority

    로컬 auth.users 직접 의존을 private mirror authority로 바꾸고 callback/reconcile/delete를 멱등화합니다.

  • 5

    DB와 Storage 이전 연습

    isolated local instance에 두 번 restore하여 replay가 안전하고 row/object mismatch가 0인지 확인합니다.

  • 6

    24시간 shadow read

    사용자에게는 원격 결과를 주면서 로컬 결과를 함께 읽어 권한과 응답 차이가 0인지 비교합니다.

  • 7

    최종 cutover

    write를 잠그고 final delta를 옮긴 뒤 15분 read-only smoke와 세 provider 실제 로그인을 통과해야 local write를 엽니다.

  • 8

    14일 안정화

    remote data를 read-only 복구본으로 유지하고 backup restore, Mac reboot, Docker restart, JWKS rotation을 연습합니다.

7언제 진행하고 언제 멈추나

진행 가능 원격 JWKS가 비대칭키이고 capability가 legacy이며, 디스크·backup·restore rehearsal을 모두 통과했습니다.
먼저 보완 디스크 여유가 80 GiB 미만이거나 off-Mac backup이 없으면 인프라와 저장공간부터 준비합니다.
즉시 중단 User A가 User B 데이터를 읽거나, identity mirror digest가 다르거나, Storage hash mismatch가 하나라도 있습니다.
Cutover 금지 기존 account-generation safeguard보다 안전성이 낮아지거나 auth.users transaction 대체 계약이 승인되지 않았습니다.

10예상 문제와 대응

JWT key 변경

증상: 모든 요청이 401.

대응: 5분 JWKS poll, 이전 key 유지, canary 뒤 reload.

Identity mirror 불일치

증상: callback bootstrap 실패.

대응: 개인 write를 닫고 remote Auth 기준으로 reconcile.

Mac 전원·디스크 장애

증상: DB와 이미지 동시 중단.

대응: SSD, UPS, off-Mac backup에서 restore.

인터넷 장애의 의미 만료 전 access token은 로컬에서 확인할 수 있지만, 원격 Auth에 연결하지 못하면 새 로그인과 refresh가 실패합니다.

12구현 시작 전 체크리스트

  • Hybrid contract-evolution을 사용자가 명시 승인했습니다.
  • 공식 5종 문서와 CURRENT_SOURCE_OF_TRUTH.md가 먼저 갱신됐습니다.
  • 신규 workpack과 acceptance가 작성되고 독립 검토됐습니다.
  • Capability가 legacy이고 canonical generation row가 0입니다.
  • 디스크 여유와 off-Mac encrypted backup을 준비했습니다.
  • PostgreSQL 17 restore rehearsal을 통과했습니다.
  • Identity mirror와 auth.users 대체 설계가 security review를 통과했습니다.
  • User A/B RLS negative test를 통과했습니다.
  • Storage object mismatch가 0입니다.

  • Final cutover window를 운영자가 별도 승인했습니다.
