## 운영 적용 순서

1. 정확한 full-local 컨테이너·이미지·volume을 확인한다. 전체 DB와 사진 백업, 외장 사본을 새 경로에 보존한다.
2. 현재 구조를 복제한 격리 DB에서 새 SQL을 적용한다. 실제 카탈로그 사본에서도 분류·별칭과 권한을 확인한다.
3. 운영에는 00000 → 01000 → 02000 순서로 적용하고 checksum ledger와 적용 전후 상태를 기록한다. 기존 계정/소유권 trigger를 끄지 않는다.
4. 새 웹을 별도 빌드·확인한 뒤 전환한다. DB/worker/backup 운용은 웹 전환과 별도 소유·복구 절차로 조율한다.
5. 미확인 범위와 실제 적용 상태는 아래 결과에 사실대로 기록한다.

## 확인 결과

- 자동 테스트 실행·추가·수정 없음. 타입 검사 통과, 로컬 production 빌드 통과, 독립 코드 검토의 차단 지적을 수정했다. 샘플 미리보기에서 레시피북 전체 재료 펼치기를 모바일/데스크톱으로 확인했다. 실제 소셜 로그인·새 영상 추출·모든 사용자 쓰기 흐름은 재실행하지 않았다.
- 현재 구조와 실제 카탈로그를 복사한 격리 DB에서 새 SQL 3개 적용 후, 운영에도 세 파일과 checksum 이력을 한 transaction으로 적용했다. 데이터 변경은 확인된 앞다리살 분류 1개와 별칭 2개이며 사용자 레시피·식사기록을 일괄 재작성하지 않았다. 공개·인증 사용자에게 mutation/recovery RPC 실행 권한을 추가하지 않았다.
- 실제 DB에서 공백·앞다리 별칭이 같은 ID로 매칭되고 `국간장`은 정확한 표준명을 우선함을 확인했다. 영양값 일괄 추정·대규모 재료 병합은 하지 않았다.
- 전체 DB·Auth·Storage 백업, USB 사본, 실제 격리 복원과 서명된 readiness를 새로 만들고 운영 설정 참조를 갱신했다. 대용량 문자열 제한과 행 순서 때문에 발생하던 검증 오류를 고쳤다.
- 기존 archive 외곽 v5는 유지한다. 새 manifest의 `data_semantic_format=copy-row-sha256-multiset-v1`은 행별 SHA256를 외부 정렬하되 중복 개수·relation·column 순서·non-COPY SQL까지 확인한다. 이전 marker 없는 v5는 이전 규칙 그대로 검증하고 미지원 marker는 거부한다. 이전 실제 archive 호환과 새 archive 실제 복원이 모두 확인됐다.
- 추출 credential을 generation 42로 정상 회전했다. 만료는 2026-09-25 19:32 KST이며, 6시간마다 만료 48시간 전부터 상태를 기록하는 읽기 전용 점검을 추가했다. 자동 credential 회전이나 외부 알림 발송은 없다.
- 기존 자원 7개만 다루는 출시 전 재개 경로를 설치했고 실제 launchd 실행이 PASS/exit 0, started 0/stopped 0이었다. 사라진 자원 생성·DB reset·secret 재발급은 하지 않는다. 실제 호스트 재부팅은 하지 않았다.
- 옛 OMO 작업 세 개는 백업 후 비활성화했다. 매일 백업 실행 시각은 사용자 선택 대기이며 새 일일 일정은 설치하지 않았다. 현재 24시간 백업 신선도 기준은 유지한다.
