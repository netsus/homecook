# 요리계획·식사기록 설계 적용 — 2026-10-06

상태: 작업 브랜치 `codex/mumeok-ui-notification-feedback-20260928`에 구현. 커밋·머지·배포·운영 데이터 변경 없음. 이전 피드백 묶음의 변경을 보존했다.

## 적용 내용

- 요리계획: 한 주의 날짜/레시피 요약과 선택한 날짜의 끼니만 표시. 빈 끼니에도 +를 유지한다. 끼니 제목은 전체 상세, 음식 행은 같은 경로의 `mealId`로 계획 한 건의 상세를 연다.
- 날짜의 자동 스크롤 맞춤과 스크롤에 의한 날짜 변경을 제거해 사용자가 선택한 날짜를 유지한다. 모바일은 주간/선택일 세로 배치, 데스크톱은 좌우 배치다. 장보기는 계획, 남은 요리는 식사기록에 둔다.
- 상세: 전체 계획 분량의 영양은 접기 영역, 개별 요리는 인분과 저장된 영양, 당시의 재료·만들기로 연결한다. 혼합 상태별 장보기/시작/완성 음식 동작과 인분·삭제 보호를 유지한다. 임의로 만들던 조리시간·재료 칩과 중복 모바일/PC 코드를 제거했다.
- 식사기록: 선택한 날짜만 표시. 음식명 왼쪽/kcal 오른쪽, 먹은 양 아래, 독립된4px 막대와 탄단지 수치. 하늘색/분홍/노랑 팔레트,400/500/600의 제한된 글자 굵기를 사용한다.
- 하루 영양: 요약→상세→kcal/탄수/단백질/지방 전환→기여 음식→기록 상세. 실제 수치와 공통0점·동일눈금으로 그린다. 부분·없는 영양을0이나 완전한100%로 만들지 않는다. 계산 설명은 정보 버튼에서만 연다.
- 음식 상세는 읽기 전용이고 수정/삭제는 배경이 남는 모달이다. 상세+로 음식 추가 후 취소하면 상세로 돌아간다. 그래프에서 상세를 열었다 돌아오면 선택 영양소가 유지된다.
- 추가: 레시피 검색/레시피북/팬트리/유튜브/직접 등록을 보존한다. 선택→양 확인이 같은 모달 안에서 진행되고 검색어·초안·날짜·끼니를 유지한다. 최근/요리한 음식/제품·재료 탐색도 동일하다.
- 키보드에 따라 모달 높이를 제한하며 스크롤 영역을 하나로 둔다. 숨은 이전 단계는 포커스 대상에서 제외하고 겹친 모달이 닫힐 때 배경 스크롤이 잘못 풀리지 않게 했다.
- 추가 후 불필요한 성공 확인창을 제거했다. 계획 한 건의 상세에서 새 요리를 추가한 뒤에는 같은 끼니 전체 목록으로 돌아와 새 항목을 보여준다. 로그인 복귀에도 선택한mealId와 안전한returnTo를 유지한다.

## API와 DB 추가

1. `GET /api/v1/recipes/{id}?view=preview`: 동일한 가시성/소유권 검사를 거치되 조회수는 증가시키지 않는다. 계획 인분 선택의 재료·영양 미리보기에 사용한다.
2. `GET /api/v1/meal-log/nutrition-preview?source_type=...&source_id=...&amount=...&unit=...`: 인증된 본인의 요리/제품/재료 영양을 기존 계산 함수로 읽는다. 표준 래퍼 data는 `{source, quantity, nutrition}`. 요청 취소·지연·재시도와 실제 지원 단위를 처리한다. 미리보기는 식사·잔량·알림·영수증에 쓰지 않는다.
3. `POST /api/v1/meals`의 선택적 UUID `Idempotency-Key`: 새 모달은 한 저장 시도의 실패/재시도에 같은 키를 보낸다. 서버는 현재 소유자·계정 세대·내용을 확인하고 최초 성공 결과를 재사용한다. 다른 내용으로 재사용하면409, 키 없는 이전 호출은 기존 동작이다.

다음 SQL을 웹과 함께 배포해야 한다. 이번에는 반영하지 않았다.
- `20261006120000_meal_log_nutrition_preview.sql`
- `20261006130000_future_meal_create_idempotency.sql`

새 테이블 없이 기존 영양 계산과 멱등 영수증을 사용한다. 이전 묶음의 미배포 알림 migration도 별도 추적한다.

## 구현 범위의 한계

- 현재 끼니 목록 응답에는 활성 요리 세션 ID와 정확한 완성 음식 ID가 없다. 시작 버튼은 기존 세션을 재사용하는 API를 호출하며, 완성 음식 버튼은 남은 요리 목록으로 연결한다. 존재하지 않는 상태나 ID를 추정하지 않는다.
- 식사기록 항목 응답에는 원본 레시피 ID·현재 배치 잔량이 없어 음식 상세에 가짜 레시피 링크/수정 후 확정 잔량을 표시하지 않는다. 수정 미리보기는 해당 기록의 저장된 영양 기준이고, 성공 후 서버 정보를 다시 읽는다. 신규 추가에서는 현재 선택한 요리 잔량을 확인할 수 있다.
- 실제 iPhone의 키보드·핀치 확대·포커스/뒤로가기는 운영 또는 실제 기기 개발 연결에서 확인이 남아 있다. 로컬 QA는 예시 데이터와 격리 계산 검증이며 운영 계정의 저장/삭제 검증이 아니다.

## 2026-10-08 — 확인된 탄단지 그래프 후속 (미배포)

전체 calculation_status가 partial이면 탄단지가 모두 있어도 막대를 숨기던 조건을 수정했다. 세 탄단지 수치가 유효하고 합계가 양수이면 확인된 수치로 비율을 계산하고 ‘확인된 탄단지 기준’을 표시한다. 영양값이나 partial 상태를 complete로 변경하지 않으며, 실제 탄단지 결측/null/음수/비유한값/모두0/unavailable 상태는 막대를 그리지 않는다. 상세의 중복 상태문구는 막대의 한정 설명 하나로 정리한다. 공통 계산을 쓰는 목록·상세·수정/추가·하루비교에 적용되며 운영에는 아직 반영하지 않았다.
