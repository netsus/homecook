# 추정 중량·소량 열량 표시·대표 영양 정책 — 2026-10-10

상태: 사용자가 승인한 중량3건과 소량 열량 표시를 구현하고 복제 DB/렌더 검증을 완료했다. **이후 운영 반영까지 완료했다.** [최종 적용·남은 범위](ingredient-nutrition-completion-20261010.md)를 따른다. 앞선 [제외 재료 복구](ingredient-exclusion-recovery-20261010.md)와 같은 작업 브랜치에 누적했다. 아래는 최초 분류·방법 결정 기록이다. 이후 검토된 대표 영양·실사용 부분 영양11개와 마늘 교정을 반영했다.

## 승인된 중량 기준

| 재료 | 서비스 기준 | 원문과 처리 |
| --- | --- | --- |
| 마른 월계수잎 | 1장0.5g | 사용자 전달 Gemini 근삿값 |
| 생 깻잎 | 1장1g,10장10g | 제시된7~10g 범위 중 사용자가 후속 승인한10g |
| 통후추 | 1알0.067g,3알0.201g | 원문3알약0.2g을 기존 piece중량 소수3자리 정밀도로 정규화 |

기존 공식100g 영양을 그대로 사용하고 수량→g에만 이 기준을 적용한다. 원문·선택 이유·반올림 한계는 [중량 계획](data/user-estimated-piece-weights-20261010.json)에 보존했다. 출처는 `HOMECOOK_USER_STANDARD / 사용자 승인 AI 추정 중량`이며 공식 실측 또는 새 AI 영양값으로 위장하지 않는다. 외부 모델/API를 호출하지 않았다. 실제 측정 g가 있으면 그것을 우선한다.

복제 DB 계산 결과: 월계수1장1.565kcal, 깻잎10장3.8kcal, 후추3알0.50451kcal. 값은 내부에 그대로 남고 표시만 단순화한다. 현재516개 재료행 중 기존 영양자료가 선택되는 행의 환산누락4→1이며 다진마늘10개는 원문 확인 대기다. 그 행을10쪽/10통으로 임의 확정하거나 생마늘 영양에 자동 대체하지 않았다.

## 소량 열량 표시

- `0 < 실제 열량 < 5`이면 `5 kcal 미만`으로 표시한다. 판정은 반올림 전·선택 분량 계산 후에 한다.
- 실제0은 `0 kcal`, 누락/null은 정보 없음으로 구분한다.
- 부분 계산의 소량은 `확인된 열량 5 kcal 미만`, 부분 계산0은 `확인된 열량 0 kcal`로 표시한다. 전체 열량이5kcal 미만이라는 상한을 주장하지 않는다.
- 내부 합계·저장·그래프 데이터·탄단지/나트륨은 변경하지 않는다. 예를 들어4kcal×10인분은40kcal다.
- 레시피·플래너·식사기록·제품 예상열량은 공통 formatter를 사용한다. 제품 입력 숫자나 그래프 축·마케팅 고정 예시는 적용 대상이 아니다.
- 기존 ‘영양성분 더 보기’와 식사기록 설명 펼치기에 기준 안내를 넣는다. 개수/부피 환산 경고가 있을 때만 대표 중량 안내를 추가하고, AI 영양 추정 경고만으로 중량 환산을 했다고 표시하지 않는다.

## 대표값을 정할 수 있는 경우

현재 영양자료가 선택되지 않는12행은 넓은8종10행과 화이트크림1행·해물육수코인1행이다. 승인된 대표 연결은 아직 없다. 아래는 확정된 연결이 아니라 적용 조건을 정할 후보다.

| 분류 | 재료 | 결정 방향 |
| --- | --- | --- |
| 조건부 대표 후보 | 신김치 | 기본 종류를 배추김치로 승인하면 기존 공식 배추김치 자료를 대표로 연결할 수 있다. 다른 김치 종류는 예외. 현재 한 레시피는 씻고 짜므로 같은 나트륨/수분 상태로 단정하지 않는다. |
| 조건부 대표 후보 | 고추 | 종류 미상 고추의 기본을 풋고추로 승인하면 기존 자료 활용 가능. 청양/꽈리/홍고추 등 명시가 있으면 해당 종류 우선. 현재 개 단위 입력은 개당 중량도 별도 필요하다. |
| 종류·형태 확인 우선 | 알룰로스 | 순수 분말/액상/다른 감미료 혼합을 구분한다. |
| 종류·형태 확인 우선 | 치즈 | 종류와 자연/가공, 형태를 확인한다. |
| 종류·형태 확인 우선 | 호박 | 애호박·늙은호박·단호박 등을 구분한다. |
| 종류·형태 확인 우선 | 옥수수 | 단/찰옥수수, 생/삶은/통조림/가루를 구분한다. |
| 종류·형태 확인 우선 | 버섯 | 종과 생/건조를 구분한다. |
| 종류·형태 확인 우선 | 김치국물 | 김치 종류·건더기 제거 범위·물김치 여부·희석 상태를 확인한다. |
| 원문 정체성 확인 | 화이트크림 | 실제 원문에서 생크림과 별개 재료로 쓰여 생크림으로 자동 대체하지 않는다. 제품명/포장/영상의 원료를 확인한다. |
| 원문 형태 확인 | 해물육수코인 | 원문은 ‘해물육수8g’이라 코인인지부터 확인한다. 액체 육수나 분말을 코인 제품으로 자동 대체하지 않는다. |

대표값을 정하면 끝나는 것은 **영양자료를 선택하지 못하던 문제**다. 승인 연결·대표값이라는 출처/표시·해당 현재 레시피 재계산까지 필요하며, 수량·환산·개별 영양소 결측은 별도다. 종류/상태가 맞지 않는 대표값을 넣어 complete로 만드는 것은 피한다.

## 검증과 배포 경계

관련 렌더/단위/계산 회귀를 통과했고 전체 타입 및 변경 파일 lint를 확인했다. 실제 컴포넌트 렌더에서 4.99/5 경계, 0/null, 부분값, 10인분 합계와 단위 중복을 확인했다. 기존 AI 표시 검사2개는 별도 span 숫자/단위에 맞는 접근 가능한 전체 문구 검사로 정정했으며 통과한다.

앞선 제외 복구를 먼저 적용한 네트워크 없는 clone에 중량7행(source1/evidence3/piece3)을 추가했다. 재실행 무변경·정확한 기존 ID 변조 거부·원영양/기록 보존과 실제 SQL 선택을 검증했다. 중량 변경이 영향을 주는 현재 레시피2개에서 앱/SQL guard 일치 및 새 snapshot 저장을 검증하고 해당 저장은 rollback했다. 이 초기 검증 당시에는 운영 읽기 외 변경·AI 호출·커밋/PR·배포를 수행하지 않았다. 이후 운영 반영은 최신 완료 기록을 따른다. [검증 기록](data/nutrition-completion-followup-verification-20261010.json).

반영 순서는 앞선 선택 복구 SQL → 제외 복구 데이터 → 이번 추정 중량 데이터 → 관련 웹 → 영향받은 현재 레시피 재계산이다. 제외 복구 데이터의 사전값 검사를 우회하려고 순서를 바꾸지 않는다. 과거 식사 snapshot은 보존한다. 실제 모바일/데스크톱 화면 확인은 이 수정 묶음의 배포 단계에서 수행한다.
