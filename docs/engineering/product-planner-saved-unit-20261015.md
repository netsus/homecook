# 완제품 계획 새 선택의 저장 단위 제안

2026-10-15 로컬 구현. 기준 master `1bdc44dd9870228e5b0b892f723db8468bddc9f7`. 운영 미적용이며 C04 U-A11의 **완제품 계획 새 선택 한 소비자**만 연결한다. 앞선 [식사기록 최근 단위](meal-log-recent-unit-20261015.md)와 용도를 섞지 않으며 U-A11 전체 완료를 뜻하지 않는다.

## 범위와 선택 규칙

- catalog가 명시 `quantity-v4`일 때 기존 `fetchPlanner(planDate, planDate)`로 당일 저장 계획을 picker 인스턴스의 해당 날짜·끼니마다 한 번 읽는다. 새 API·RPC·SQL·권한·의존성·전역 설정표·브라우저 저장소는 추가하지 않는다. 일반 식사기록의 최근 단위나 다른 용도의 입력을 가져오지 않는다.
- 사용자가 목록에서 제품을 **새로 선택하는 시점**에 같은 날짜·끼니 column·제품 ID·비어 있지 않은 현재 영양 version과 일치하는 항목만 사용한다. 저장된 양은 유한한 양수여야 하며 저장 display 단위는 현재 `buildCompatibleFoodProductUnits(product, true)`의 환산 가능 목록 안에 있어야 한다. 이름/브랜드·비슷한 규격으로 추정하지 않는다.
- 기존 `list_product_planner_entries`의 `plan_date,column_id,created_at,id` 순서를 바꾸지 않고 뒤에서 첫 유효 항목의 단위만 제안한다. dedupe는 이 순서를 보존한다. **같은 날짜·끼니에서 저장 생성 순서로 고른 단위**이며 전 기간 최근 사용·마지막 수정 단위·가장 최근 버튼 클릭을 뜻하지 않는다. DTO에 없는 수정 시각을 만들어 비교하지 않는다.
- 새 양·raw는 계속 빈칸이다. 저장 항목의 수량·원분수·snapshot·영양을 새 요청에 복제하지 않는다. 사용자가 새로 입력한 원문만 기존 수량 전환/저장 경로로 보낸다.
- 이력이 없거나 version/날짜/끼니/제품/단위가 맞지 않으면 기존 catalog 기본 추천을 유지한다. guest401·조회 실패도 기본 추천으로 진행하며 optional 이력 때문에 새 로그인 이동·저장 실패를 만들지 않는다. 원 보호 액션의 로그인/복귀는 그대로다.

## 늦은 응답과 원기록 보존

조회 결과는 현재 양·단위를 변경하는 effect에 연결하지 않는다. 선택 이후 늦게 도착하면 현재 입력을 유지하고, 이후 사용자가 다시 새 선택을 할 때만 쓴다. 날짜·끼니 변경 또는 unmount의 옛 응답은 무시한다. 검색/출처 필터는 같은 날짜·끼니의 저장 이력을 다른 용도로 바꾸지 않는다.

로그인 복귀의 원분수/수량·명시 초기 선택·기존 항목 편집은 저장 이력으로 덮지 않는다. quantity-v4 OFF에서는 새 이력 요청과 제안을 실행하지 않는다. 취소·미리보기·실패 저장은 로컬 성공 이력을 만들지 않으며 다음 새 선택에도 기억하지 않는다. 성공한 새 항목은 기존 서버 저장·페이지 복귀/재조회 계약을 따른다. 과거 계획/식사/제품 version·원량·영양·snapshot은 쓰지 않는다.
