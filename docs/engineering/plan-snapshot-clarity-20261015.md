# 계획에 저장한 레시피: 제품 조회·미확인 분량·조리 안내

상태: 로컬 수정·검증 후보, 운영 미반영. source는 master `e71a0a5237dcfc5ad5fd9ff0fcddf849b1c9b02c`이며 운영 reader `af88126b44cf5abb6fa06f7c08f9eee23ca7de99`와 변경 대상 UI/API 원문이 동일함을 확인했다. 실제 운영 두 계획의 배포 후 재확인은 총괄이 수행한다.

## 최소 수정

- 제품 재료는 `ingredient_id=null`과 고정 제품/영양 버전을 함께 가진다. 계획 snapshot을 정상 투영한 뒤 이름 조회 ID 목록에 null까지 넣던 경계만 고친다. 제품만 있으면 일반 재료 label query를 실행하지 않고, 혼합 목록은 기존 일반 재료 ID만 중복 제거해 조회한다. 현재 제품·레시피를 다시 읽거나 새 권한·RPC를 추가하지 않는다.
- 일반/제품의 확정 양과 단위는 그대로 표시한다. 숫자0도 빈값으로 취급하지 않는다. 양 또는 단위가 빠졌으면 알려진 부분을 보존하고 기존 ‘분량 확인 필요’를 표시한다. 둘 다 없으면 안내만 표시한다. 명시 TO_TASTE는 기존 ‘적당량’이며 재료 이름·고명 구분만으로 TO_TASTE를 추측하지 않는다.
- 만들기 시작에 ‘재료표는 선택한 인분으로 환산됩니다. 조리법의 수량은 원문 그대로입니다’를 정확히 표시한다. 계획 인분만 설명하며 검증된 원본 인분 출처가 없는 숫자를 새로 주장하지 않는다. [기존 B08 계약](mumeok-beta-cooking-notifications-20261013.md)을 계획 snapshot에도 적용한다.

snapshot ID/레시피/owner 검사는 이름 조회 전에 그대로 실행한다. 원 재료 JSON·소수·단위·제품ID/영양버전·단계 숫자/문장·정렬·환산 함수·DTO·DB·영양·권한·AI는 변경하지 않는다. 저장·연결·인분 조절 기능을 추가하지 않는다.

## 확인 범위와 남은 일

수정 전 제품-only/혼합 null ID 조회 실패2개, 미확인/partial 안내3개, B08 안내1개가 실패했다. 수정 후 관련5suite31개가 통과했다. 제품0.125kg/base2→계획3의 기존0.1875kg와 고정 버전, 일반 재료 조회, owner/pin 실패, 0·partial·TO_TASTE·고명·원문 숫자 보존을 검사한다. 모형의 null 조회 오류 코드는 실제 운영 내부 오류 코드를 읽은 증거가 아니다.
