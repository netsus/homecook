# 무먹 YouTube 접수 복구 — 운영·Chrome 최종 검증

기존 V2 키를 그대로 재사용해 정책과 웹을 복구했다. 사용자 Mac Chrome에서 대표 영상 한 건의 로그인 신청→worker 성공→완료 알림→결과 등록→QA 레시피북 저장→플래너 추가를 확인했다. 새로고침 시 진행 화면이 사라지는 문제 등 아래 UI 관찰은 남아 있다. 전체 v9 완료나 모든 버그 없음을 뜻하지 않는다.

- 복구 PR1738: https://github.com/netsus/homecook/pull/1738
- 운영 웹: `25a6314ce16eef382b671b9086579e0909649afa`, build `prelaunch-25a6314ce16e-6R93aX`.
- 정책 한 행의 current1→2와 updated_at만 변경. 기존41건 전체 행 지문·원 C04/v74 권위·DB232·일반 자료·권한·worker PID49750/gen49를 보존했다.
- 새 키·JWT 발급/교체·외부 전송·별도 secret 파일·지속 접근권한 확대0. 승인 plan SHA만 담는 create-only Keychain 감사 앵커를 등록했다.
- C05/R2 수집OFF 유지. 별도 추출기 후보·완성 무게 후속은 이번 운영 후보에 포함하지 않았다.

## Chrome 실제 사용자 흐름

처음에는 현재 계정이 QA인지 불명확해 질문했으나, 부모가 전달한 사용자 직접 승인 원문에서 현재 Chrome 계정들은 모두 테스트 계정이며 기록 변경·복구 불필요임을 확인했다. 같은 기존 로그인 계정으로 계속했고 새 계정·비밀번호·권한·개인 건강자료를 입력하지 않았다.

1. `/recipes/new/youtube`에서 대표 영상 `pjwILwDVC7U` 미리보기1회 후 추출 신청1회. “추출을 시작했어요”와 대기 상태가 나타났다. HTTP 성공 상태 코드를 패킷으로 직접 캡처한 것은 아니며, 실제 UI와 V2 신규job1개로 접수 성공을 확인했다.
2. 새로고침하면 링크 입력 단계로 돌아갔다(F01). 추가 신청 없이 홈의 알림 센터에서 동일 작업 진행을 확인했다.
3. DB의 동일 작업은 `succeeded`, `attempt_count=1`이었다. 알림은 “추출 결과를 확인하고 레시피로 등록할 수 있어요”와 결과 확인 링크를 제공했다.
4. 결과 확인을 누르면 결과로 이동하지만 알림 창이 남았다(F02). 닫기 한 번으로 결과를 열었다. 결과는 “뼈 없는 순살 소갈비찜”, 기본2인분, 재료14개·단계11개였다.
5. 결과가 내 유튜브 레시피로 저장됐고 “내가 추가한 레시피에서 보기”로 개인 북의 첫 항목을 확인했다.
6. 저장 선택에서 기본 저장 북을 해제하고 기존 QA 북 “베타 감사 20261013” 하나만 선택해 저장했다. 마이페이지→레시피북→QA 북 재조회와 새로고침 후 같은 제목과 내용을 확인했다.
7. 리더 하단의 플래너 추가에서10/17 저녁·2인분을 선택해1건 추가했다. 완료 안내와 실제 플래너 항목을 확인했고 새로고침 후에도 유지됐다. 모바일375에서도 같은 항목이 보였다.

신규 신청은1회이며 중복 신청·다른 영상·별도 재추출은 하지 않았다. worker의 시도 횟수1과 실제 모델 호출 수는 같은 지표가 아니며, 모델/repair 호출 수를 별도 계측했다고 주장하지 않는다. 이 한 추출 작업에서 외부 모델 실행이 가능했고, 추가 검증용 모델 요청은 하지 않았다.

### F01 — 접수 후 새로고침 시 진행 화면 복구 누락

- 환경: 운영25a6314, 사용자 Mac Chrome1440×1000, 로그인 테스트 계정.
- 재현: URL 입력→미리보기→추출 신청→대기 화면에서 브라우저 새로고침. 주소는 `/recipes/new/youtube`이며 jobId가 붙지 않았다. 로딩 후에도 빈 입력 단계였다. 서버 작업은 계속돼 홈 알림에서 확인할 수 있었다.
- 근거 코드: `components/recipe/youtube-import-screen.tsx:2972`는 acceptedJobId를 React state에만 넣고, `:2710`의 복구는 URL jobId가 있을 때 동작한다. 원인 해석은 이 코드와 실제 주소·화면을 대조한 것이다. 이번 복구 PR은 이 제품 파일을 변경하지 않았다.
- 화면:06-job-accepted,07-refresh-lost-progress,08-notification-progress.
- 권장 수정: 접수 성공 시 동일 jobId를 주소나 계정에 결속된 복구 상태에 보존하고, 새로고침 시 소유권 검사를 거쳐 같은 작업을 조회한다. 기존 중복 식별·quota 보호를 유지한다.
- 검증 기준: 새로고침/뒤로가기 후 동일job·진행상태가 복구되고 신규job·모델 요청이 늘지 않으며, 계정 변경 시 다른 사용자의 작업이 노출되지 않는다.

### F03 — 이미 알려진 v74 추출 품질 문제

마늘 재료 누락, 간장·후추 등 여러 수량 미확인과 단계의 “다진 재료” 표현을 확인했다. 새 golden 채점이나 이전 평가와 동일한 응답이라고 주장하지 않는다. 알려진 진간장 충돌·마늘 누락·후추 모호량 문제와 구분 없이 새 발견 수로 세지 않는다. 별도 추출기 세션의 미완성 후보를 운영에 넣거나 반복 추출하지 않았다. 현재 대표 결과 화면을 보존했으며, 별도 추출기 검증에서 같은 근거와 회귀 영상으로 정확도를 확인해야 한다.

### F04 — 데스크톱 초기 배치 이동

1440px 새로고침 직후 모바일형 좁은 카드가 보였다가 정상 데스크톱 배치로 전환됐다. 지속 시간은 측정하지 않았다. 정착 후375/1440 입력 화면의 가로 넘침은 없었다. `components/shared/use-desktop-viewport.ts`의 `useMediaQuery(...,false)`와 desktop 분기가 원인 후보이며 해당 파일은 변경되지 않았다. 후속 UI 묶음에서 초기 렌더의 폭 안정화를 검토하고 연속 캡처로 확인한다. 화면02/03/04를 비교한다.

## 검사 이력·미검증 영역

- 샌드박스 DNS로 첫 fetch가 실패해 읽기 전용 권한 검토 후 성공했다. shell pnpm 경로·Vitest 소유 캐시 초기 실패 후 corepack/권한 검토로 정상 검사했다. 자동 검토 거절은 없었다.
- 잘못 옮긴 SHA의 첫prepare는 소스 불일치로 운영 변경 전에 거절됐다. 실제 병합SHA로 다시 고정했다. 첫 사후 DB 조회는 adapter inspect 누락으로 쿼리 전에 종료했고 inspect 후 읽기 전용으로 확인했다.
- 리더 내부의 중복 액션 위치를 처음 클릭했을 때 대화상자가 열리지 않아 화면을 확인하고 실제 하단 제어로 진행했다. 모바일 저장·데스크톱 하단 플래너는 동작했다. 첫 클릭 현상을 제품 버그로 확정하지 않는다.
- 새 추출 성공 표본은 한 영상·한 계정이다. 다른 계정·비로그인·소유권 우회·quota 한계·실패 재시도·중복 클릭의 실제 운영 흐름은 이번 유료 작업으로 반복하지 않았다. 관련 로컬 회귀·격리 PG 결과와 구분한다.
- 실제 완성 무게 정확도·네이버 일반 공개 가입·C05 신규 수집·별도 추출기 품질 후보·전체v9 통합 완료는 이 보고서의 성공 범위가 아니다.

대표 로그인 접수 연결은 복구됐으며 계정 확인 대기는 해소됐다. F01/F02는 새 운영 UI 관찰로 남아 있고, F03/F04는 기존 품질·UI 한계와 구분했다. 후속 완성 무게 변경의 PR·배포 준비는 최신 master와 운영25a의 전체 diff를 다시 확인해 진행한다.
