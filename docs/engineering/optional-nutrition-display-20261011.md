# 부가 영양소 결측 안내 간소화

상태: 운영 웹 반영·API 값 보존·운영 웹 직접 접속 화면 확인 완료. 공개 주소 브라우저 확인에는 아래 제약이 있다.

사용자는 칼로리·탄수화물·단백질·지방이 있으면 부가 영양소 결측을 안내하지 않고, 나트륨·당류·식이섬유·포화지방은 있으면 표시하고 없으면 생략하도록 요청했다.

## 표시 기준

- 레시피·식단 화면은 기존4개 주요 표시 성분이 모두 완전한 유효값일 때 전체 calculation_status 또는 나트륨/부가값 때문에 ‘일부 영양 정보 없음’, AI 일부누락 설명, ‘확인 필요’ 배지를 표시하지 않는다.
- 부가 영양소 표는 완전하고 유효한 값만 보여준다. 실제0은 표시하고 null/미기재는0으로 바꾸지 않는다. 일부 재료만 합산한 부가값도 전체량처럼 보이지 않도록 생략한다.
- 칼로리·탄단지 자체가 미연결/부분인 레시피는 기존 부분값 안내를 유지한다. AI 출처, 대표 영양값·중량 근거 및5kcal미만 표시 설명은 다른 의미의 출처 정보이므로 유지한다.
- 기존 식사 기록은 성분별 완전성 대신 단일 상태와 숫자만 저장한다. 네 주요 숫자가 모두 존재하면 부가 결측 안내를 생략하되 저장된 partial 상태·열량 표시·확인된 탄단지 표시를 덮어쓰지 않는다. 새 완전성 정보를 추정해서 저장하지 않는다. 기록 상세의 나트륨이 없으면 그 행을 숨긴다.

## 변경과 단순화

`recipe-nutrition-display.ts`의 기존 주요4개 표시 순서를 재사용한 공통 판정으로 레시피 카드·식단 미리보기·식단 안내를 통일했다. 식사기록은 기존 평면 근거의 네 숫자 존재 여부로 누락 문구를 판단한다. 계산기·SQL·영양값·스냅샷·과거 기록은 바꾸지 않는다. 새 의존성은 없다.

주요 파일은 `components/recipe/recipe-nutrition-card.tsx`, `components/planner/meal-add-recipe-preview.tsx`, `planner-nutrition-summary.tsx`, `meal-log-screen.tsx`와 각 영양 표시 helper다. 관련 UI 테스트5개 파일을 갱신했다.

## 확인

부가 영양소가 없거나 부분값이어도 칼로리·탄단지가 완전하면 안내 없음, 부가0 유지, 실제 핵심 누락 안내, AI 출처, 저장값 불변을 관련82개 검사로 확인했다. 타입 검사·변경 파일 ESLint 통과. 운영 DB 변경과 재계산은 필요하지 않다.

## 다음 보완 방식

대표값 정확도는 공식 계량 자료·제품 포장 중량/영양표를 먼저 사용한다. 예를 들어 포장 전체 중량과 동일 크기 낱개 수가 있으면 평균1개 중량을 산출할 수 있으며 이는 모든 낱개의 실측값은 아니다. 자료가 없는 ‘한 줌·한 웅큼’은 사용 빈도와 열량 기여가 큰 항목부터 실측 후보로 분리한다. 채썰기/다지기·담는 방법·도구와 크기를 정하고 여러 번 재어 범위와 대표값을 남긴다. 사용자 개인 레시피는 실제 잰g을 입력할 수 있다.

신규 재료 점검은 사용자가 요청할 때 진행한다. 실제 레시피에서 발생한 핵심영양 미연결·환산 누락·종류 불명만 모아 자주 쓰는 항목부터 공식 자료→제품 정보→검토한 대표/AI추정 순서로 검토하고 묶어서 반영한다. 적당량과 부가 영양소 결측은 계산 장애 목록에서 분리하며 자동 Gemini 호출/새 예약 작업은 만들지 않는다.

최종 웹은 `4f3f5d45862b63d4edf0d432dc6256f23ef328c1`, 빌드 `prelaunch-4f3f5d45862b-PQXgwE`다. 배포 계산·환산148검사와 빌드를 통과했다. 기존 빌드 내부 react-hooks ESLint 플러그인 탐색 경고는 별도 ESLint/타입 성공과 구분한다. DB 호환성 기록 파일은 배포 전후 동일하며 DB217/AI자동호출 정책을 변경하지 않았다. 공개 API 삼색샌드위치 영양 응답도 배포 전후 동일하다.

실행 중인 같은 운영 웹의 로컬주소에서 데스크톱·390×844모바일을 확인했다.517kcal·탄77g·단23g·지13g 유지, 부가 결측 안내 없음, 부분 식이섬유 행 생략, 완전한 나트륨799mg/당류14.5g/포화지방6.6g 유지다. 모바일 문서/스크롤폭375/375이며 화면크기를 복원했다.

공개주소 브라우저는 상세 로딩 오류가 반복됐고 API 직접 탐색은 `net::ERR_BLOCKED_BY_CLIENT`를 반환했다. 같은 공개 API의 별도HTTP검사는200으로 영양값이 동일했다. 브라우저 차단 설정을 우회하거나 변경하지 않았으며, 외부주소의 브라우저 end-to-end 성공으로 기록하지 않는다. [검증 요약](data/optional-nutrition-display-verification-20261011.json).
