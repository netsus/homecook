YouTube 추출 2026-07-25 계획 전용

설명란·댓글·자막·화면 OCR을 안전하게 production에 넣는 계획

초보 개발자가 구현 순서와 위험을 바로 이해할 수 있게 정리한 요약본

!딱 한 줄 요약

현재 최선 후보는 cv-goal-i031-ocr이다. 구현 완료 후에는 localhost에서 임의 공개 YouTube 레시피 링크를 넣어 새 OCR 통합 경로로 추출을 테스트할 수 있어야 한다.

비유: 요리 대회 예선과 준결승을 통과한 레시피를 식당 메뉴로 올리기 전, 마지막 블라인드 테스트와 주방 운영 매뉴얼을 먼저 잠그는 상황이다.

1헷갈리는 구분

서비스에 넣을 것

  • 설명란, 작성자 댓글, public caption/transcript, 화면 OCR의 조합
  • 기존 POST /api/v1/recipes/youtube/extract와 세션 흐름 확장
  • 사용자 검수 전제의 수량·재료·단계 보강

넣으면 안 되는 것

  • 실험 harness 그대로 복사
  • 특정 영상 ID별 하드코딩
  • golden/review note를 production prompt에 주입
  • raw frame, raw transcript, provider response 로그 저장

2알아둘 용어

Train 학습/개선셋
반복 개선 중 상세를 볼 수 있는 평가 데이터.
Validation 검증셋
개별 정답은 보지 않고 집계 점수로만 일반화를 확인하는 데이터.
Holdout 최종 블라인드셋
마지막 1회 검증용 데이터. 통과 전 배포 근거로 쓰면 안 된다.
Promotion 승격 판정
deterministic, semantic, timing 같은 gate 전체 통과 여부.
Deterministic 결정적 점수
재료 F1, 수량 일치, 단계 커버리지처럼 코드로 계산한 점수.
Semantic 의미 점수
추출 결과가 레시피로 쓸 만한지 judge 모델로 평가한 점수.
OCR 화면 글자 인식
영상 화면에 적힌 수량·조리 문구를 읽는 처리.
Provenance 근거 출처
어떤 값이 설명란, 댓글, 자막, 화면 OCR 중 어디서 왔는지 남기는 기록.
Feature flag 기능 스위치
문제가 생기면 새 OCR 경로만 끄고 기존 경로로 되돌리는 장치.
Contract evolution 공식 계약 변경
API/DB/Flow 문서를 먼저 바꾸고 승인받은 뒤 구현하는 절차.

4추출 흐름 그림

URL→ 설명란→ 작성자 댓글→ caption/transcript→ 화면 OCR→ Gemini 구조화→ 검수 화면→ 등록

중요한 점은 OCR과 Gemini를 원천 source로 보지 않는 것이다. 원천은 description/comment/caption이고, OCR은 보조 근거로 source_providers와 extraction_meta_json에 남긴다.

5목표와 성공 기준

1Validation 기준 F1 `.925`, semantic 평균 `3.875`, p50 `65s`, p95 `95.5s`를 초기 기준으로 삼는다.
2Fresh sealed Holdout을 1회 통과하기 전 production rollout을 금지한다.
3사용자 확인 없는 추정 수량 자동 등록을 금지한다.
4raw URL, raw transcript, raw frame, provider response, API key를 로그와 cache에 저장하지 않는다.
5pnpm dev로 켠 localhost에서 /menu/add/youtube 또는 /recipes/new/youtube에 임의 공개 링크를 넣어 추출 화면까지 확인한다.
6youtube_ocr_extraction feature flag를 켰을 때 OCR 시도/성공/cache/error가 서버 event에 남고, 껐을 때 기존 경로로 fallback된다.

6단계별 구현 순서

  • 1

    승인과 문서 변경

    OCR production 통합은 API/DB/User Flow 변경이므로 사용자 승인과 contract-evolution을 먼저 진행한다.

  • 2

    Claude Stage 1 workpack

    docs/workpacks/<slice>/README.md, acceptance.md, automation-spec.json을 먼저 만든다.

  • 3

    Backend 테스트 선작성

    source priority, OCR skip/fallback, review-required 차단, 로그 금지, cache/event를 테스트로 잠근다.

  • 4

    서버 모듈 추가

    youtube-import.ts는 orchestration으로 유지하고, OCR evidence와 관측성 모듈을 분리한다.

  • 5

    검수 UI 연결

    YT_IMPORT 화면에 evidence badge와 review-required 상태를 추가한다. 자동 등록 조건은 더 엄격하게 유지한다.

  • 6

    localhost 수동 확인

    pnpm dev 후 임의 공개 YouTube 레시피 링크 3개 이상으로 추출 화면, evidence badge, review-required 차단, cache hit를 확인한다.

  • 7

    검증과 출시

    backend verify, real smoke, fresh Holdout PASS 후 feature flag로 내부부터 단계 출시한다.

pnpm verify:backend
pnpm test -- tests/youtube-import.backend.test.ts tests/youtube-visual-quantity-eval.test.ts tests/youtube-corpus.test.ts
pnpm dev
# http://localhost:3000/menu/add/youtube 에서 공개 YouTube 레시피 링크로 확인

7localhost 테스트 방법

  • L1

    환경 준비

    .env.local에 YouTube key, Gemini key, Supabase dev env, youtube_import=true, youtube_ocr_extraction=true를 설정한다. 운영용 기존 flag인 YOUTUBE_RECIPE_VISUAL_QUANTITY_ENABLED, YOUTUBE_RECIPE_VISUAL_RECIPE_ENABLED도 계속 쓸 수 있다.

  • L2

    서비스 실행

    pnpm install --frozen-lockfile, local/dev migration 적용, pnpm dev 순서로 실행한다.

  • L3

    임의 링크 확인

    http://localhost:3000/menu/add/youtube에서 공개 레시피 링크를 넣고 제목, 재료, 수량, 단계, evidence/provenance 배지를 본다.

  • L4

    기록 확인

    같은 링크 재입력으로 cache hit를 확인하고, youtube_visual_extraction_events, youtube_visual_extraction_cache, youtube_extraction_sessions.extraction_meta_json에서 attempted/status/cache_hit 기록을 본다.

  • L5

    fallback 확인

    youtube_ocr_extraction=false로 다시 실행해 기존 public-text-only fallback을 확인한다. API 응답 shape를 새로 늘리는 일은 별도 contract-evolution 전에는 하지 않는다.

주의이 localhost 테스트는 계획만으로 가능한 일이 아니다. backend 구현, UI 연결, DB migration, env 설정이 끝난 뒤의 완료 기준이다.
