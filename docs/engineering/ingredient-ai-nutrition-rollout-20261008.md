## 작동 방식

- 외부 **Gemini API**, 현재 승인 모델 `gemini-3.1-flash-lite`를 사용한다. 구글 검색 결과나 Gemini 웹 화면을 복사하지 않는다.
- 새 재료 INSERT와 같은 트랜잭션에 작업을 넣고, 승인된 공식·대표·제품 연결이 있으면 생성/적용하지 않는다.
- 모델에는 재료 이름·분류·식품 정의를 보낸다. 계정·레시피 원문은 보내지 않는다. 가식부100g 기준 8개 성분과 가정·불확실성을 요청한다.
- 숫자/단위/범위/성분 관계를 검사한다. 판단 불가 성분은 null, 핵심 전부 불명이면 저장하지 않는다. 검사는 실측 정확도를 보증하지 않는다.
- 모델·정책/프롬프트 버전·생성 시각·가정을 보존하고, 실제 사용된 합계에 ‘AI 추정값 포함’을 표시한다.
- 웹 시작 뒤 주기적으로 처리하며 새 재료 등록 후 빠른 실행도 지원한다. 일일 처리 시도50회, 작업당 최대3회, 한 번의 시도에서 설정된 키 최대2개다. 최초 키의402 한도 오류에는 보조 키를 시도한다.

## 배포와 검증

- 신규 SQL 0900/0910/0920을 검토한 통제 트랜잭션으로 적용해 실제 원장204→207개를 확인했다. 기존 파일 checksum은 보존했다.
- 최신 운영 화면974f52를 바탕으로 AI 변경만 겹친 웹 `7b672ef55370137367f4b77848feeb1416c9a2ea`, build `prelaunch-7b672ef55370-va1zyI`를 `pnpm deploy:dev`로 배포했다. 앱 트리는 통합 소스 `ad86aa7c617011583bc2a57c352c49afefce5738`와 동일하다. 이전 플랫폼 변경은 재실행하지 않았다.
- 새 웹 준비·교체 직전까지 DB 정책을 off로 유지했다. 실제 웹 build/GET을 확인한 후 on으로 바꾸고 승인된 두 ID만 enqueue했다. 프로필을 수동으로 삽입하거나 예전 AI 초안의 시각을 바꾸지 않았다.
- 통합 테스트313개, 배포 웹 테스트296개, 배포 도구135개, 격리SQL4개와 실제 DB→계산기→저장 검사를 통과했다. 웹 후보에 없는 과거 SQL을 요구하는 정적 검사는 통합 소스에서 수행했다.
- 전체 타입 검사와 production build 통과. 별도 배포 폴더의 기존 ESLint react-hooks 플러그인 해석 경고는 남아 있으며 내장 ESLint까지 통과했다고 표현하지 않는다.
- 실제 공개 `/recipe/9e9e82c1-f7bc-5372-9588-0f242cc8239d` 및 `/about/ai-nutrition`을390/1280px에서 확인했다. AI 표시가 보이고 가로 넘침·페이지 실행 오류는 없었다. 비로그인 공통 유튜브 알림 GET401 콘솔 메시지는 별도 기존 현상이다.
- 실제 local Data API는 올바른 내부 scope에서 disabled 응답200, 익명/잘못된 scope는 기존 `ACCOUNT_SESSION_STALE`(HTTP500, code55000)로 차단했다. 이를401/403 응답으로 기록하지 않는다.

원래 공식 영양·연결·기존 기록의 체크섬은 보존됐다. 작업 도중 남은 요리1개가 별도로 생성돼 전체 행 수가 늘었지만, 시작 시점에 존재한21개 행 전체는 동일한 체크섬으로 확인했다. 이 새 사용자 데이터를 정리하거나 되돌리지 않았다.

## 복구와 근거

AI 기록이 생긴 뒤에는 AI를 모르는 이전 웹으로 자동 복귀하면 안 된다. 배포 상태에 `backwardCompatible=false`를 기록해 기존 rollback 가드로 차단했다. 중지가 필요하면 DB enabled=false로 생성을 멈추고, 현재 추정값을 읽을 수 있는 웹에서 수정한다. 운영 DB reset·볼륨 삭제·자동 전체 복원은 하지 않는다.
