# 재료 검색 503·개인 레시피 저장 500 복구 — 2026-09-22

사용자가 D01 실제 테스트에서 `곰곰 치즈` 검색 503, 개인 레시피 저장 500, 한글 입력 후 Enter가 필요한 문제를 보고했다. 세 원인을 분리하고 기존 초안·공개 원본·권한을 유지한다.

## 원인과 수정

| 문제 | 확인한 원인 | 수정 |
| --- | --- | --- |
| 검색 503 / 계정 정비 안내 | 운영 계정 상태는 정상이다. 실제 검색 RPC의 누적 최대 실행시간 5.641초, 공개 제품 검색의 제한된 읽기 전용 재현은 5초 초과였다. 인증 계층이 3초 전송 시간초과도 같은 정비 503으로 표시한다. | 기존 fuzzy 판정에 동등한 색인 가능 조건을 더해 기존 GIN 색인을 사용한다. 시간제한·권한은 바꾸지 않는다. picker는 503을 검색 일시 실패로 안내한다. |
| 개인 복제 저장 500 | API가 `write_personal_recipe_core`에 지원하지 않는 `p_nutrition_predecessor_guard`를 보냈다. 실제 PostgREST는 함수 본문 전에 `PGRST202`로 거부한다. | 해당 호출의 잘못된 인자 1개만 제거한다. 수정 API의 guard와 DB 내부 `build_recipe_nutrition_input_guard` → 영양 snapshot 검증은 유지한다. |
| Enter 후에만 검색 | Mac 한글 입력의 마지막 음절은 입력을 멈춰도 조합 중일 수 있는데, `composing` 동안 조회 전체를 막았다. | 기존 250ms debounce를 유지하고 조합 종료 대기를 없앴다. 입력값 변환·강제 조합 종료 없이 자동 조회한다. 식사기록 검색도 동일하다. |

검색 SQL은 `20260922040000_food_catalog_search_candidates.sql`에 기록한다. 기존 `word_similarity > 0.3`와 bigram/가시성/영양 조건을 유지하고 같은 정규화 문서에 `%>` 조건을 추가한다. 연산자 임계값 0.3은 함수 범위에서만 설정한다. 새 색인·전역 설정·데이터 재작성은 없다. [PostgreSQL pg_trgm 공식 문서](https://www.postgresql.org/docs/17/pgtrgm.html)의 연산자 방향과 색인 지원을 확인했다.

공개 데이터를 사용한 읽기 전용 비교에서 제품 검색은 **5초 초과 → 3.085ms**, 재료 포함 검색은 **442ms**였다. 이는 DB 실행시간이며 사용자 화면의 전체 응답시간으로 표현하지 않는다. 아직 승인 연결이 없는 제품의 레시피 선택 제한은 유지한다.

## 검증

- 수정 전 실제 운영 화면에서 같은 검색 오류와 저장 실패를 재현했다. 확인용 제목을 사용한 실패 요청은 새 레시피를 만들지 않았다.
- UI/API 회귀 8파일 **151개 통과**. Enter/compositionend 없이 검색, 늦은 응답·더보기 차단, 선택 유지·재시도, 공개 복제 RPC 계약을 확인했다.
- 전체 184개 migration 재생 및 검색/제품/영양/YouTube 통합 **30개 통과**. 430개 후보·400개 제한·동률·모든 v2 cursor·legacy v1, 공개/자신/다른 사용자/숨김/삭제 제품, Unicode 정규화, 임계값과 caller 설정 복원을 비교했다. 별도의 새 non-superuser 연결에서 DDL, pg_trgm이 아직 로드되지 않은 첫 PostgREST 검색, 정상·오류 뒤 caller threshold 0.95 복원도 확인했다.
- 실제 POST handler → SDK 영양 조회·계산 → 격리 PostgREST → DB writer 경로를 검증했다. 잘못된 인자는 PGRST202·저장 0건, 수정 인자는 201·개인 복제·원본 보존, 같은 키 재시도는 1건이었다. 이 suite를 포함한 통합 **29개 통과**. cookie 인증·초기화·부가 성장 처리는 fixture이며 운영 브라우저 확인과 구분한다.
- SQL SHA: `4c58974b87e5ad574c7b038ab4a479b57933a8c35ec36a49da601db5cd18c9c0`. 독립 검토에서 권한·predicate·영양 검증을 확인했다.

최초 운영 rollback 검증에서는 새 DB 연결에 pg_trgm 설정이 아직 등록되지 않아 DDL 검증이 거부됐다. 최종 SQL은 DDL 직전에 기존 `word_similarity`를 한 번 호출하고 설정이 USERSET인지 확인한다. 권한 부여·소유자 승격·전역 preload 없이 해결했으며, 전체 migration 재생에서 이미 모듈이 로드된 연결만 검사하지 않도록 새 연결 회귀를 추가했다.

## 운영 반영

기존 서명된 전체 플랫폼 백업·복원 readiness를 재검증하고, 변경 직전 ledger 183의 별도 DB 논리 백업도 새 경로에 생성했다. 새 dump 116,457,020 bytes의 SHA-256은 `f313f3756e1f0c3a0487178d10a9ce07c9db3e5867d403333a3de7531a311154`이며 목록 검사·전체 SQL decode를 통과했다. 이 논리 백업은 전체 플랫폼·외장 사본 복원 증거를 대체하지 않는다.

- 최종 SQL의 운영 rollback 검증을 통과한 뒤 **2026-09-22 22:00 KST 확정 적용**했다. ledger는 **184개**, 기존 기록 6종 해시는 동일하다. 검색 함수 본문·설정은 검토본과 일치하며 기존 소유자·ACL·보호 wrapper·R2 구조 해시와 YouTube readiness/fingerprint를 보존했다.
- 웹 release **`d9df787899248abff76bc45c1ea02889c71c4996`**, build **`prelaunch-d9df78789924-5JrgTq`**를 `pnpm deploy:dev`로 반영했다. 실제 앱 파일은 검증한 `35c6b2ef2`와 같고, 앞선 응답 최적화도 유지한다. 웹 배포 검사는 **239개 통과**, production build·별도 포트·운영 확인 성공이다. 기존 build 내부 react-hooks 해석 경고는 별도 변경 파일 ESLint 통과와 구분한다.
- 실제 운영에서 `곰곰 치즈` 검색의 503이 사라지고 기존 기준에 맞는 두 결과가 표시됐다. 입력부터 결과 표시까지 관측한 시간은 데스크톱 약 1.64초, 390px 모바일 약 1.09초였다. 입력 대기와 네트워크를 포함한 단발 관측이며 일정한 성능 보장 수치가 아니다.
- 공개 레시피의 크림치즈를 **체다 치즈로 교체하면서 350g을 유지**하고 개인 복제로 저장했다. 저장된 상세로 이동한 뒤 새로고침해도 제목·재료·수량·조리 단계가 유지됐다. DB에서도 개인 복제 1건·내용 snapshot 1건·원본 연결과 공개 원본의 크림치즈 350g 보존을 확인했다.
- 검증용 개인 레시피 **`동작 확인용 · 재료 교체 0922` 한 건**을 남겼다. 공개 원본·기존 식사기록을 수정하지 않았고 새 식사기록도 만들지 않았다. 식사기록의 제품·재료 탭 역시 모바일에서 Enter 없이 검색 결과가 표시됨을 확인하고 저장 없이 닫았다. 조합 미종료 이벤트는 컴포넌트 회귀, 실제 브라우저에서는 Enter 없는 문자 입력·검색·저장 흐름을 각각 확인했다.

개인 실행 증거는 저장소 밖 `~/.homecook/operations/recipe-search-save-repair-20260922/`에 보관한다. 기존 외부 접속 구간의 간헐적 지연·520은 [응답 지연 기록](beta-response-time-20260922.md)의 별도 이슈이며, 이번 DB 검색 시간초과와 혼동하지 않는다.

이미 열려 있는 사용자의 초안은 서버 수정 후 같은 화면에서 저장을 재시도할 수 있다. 입력 중 자동 검색은 새 웹 코드를 읽어야 하므로, **현재 초안을 먼저 저장한 뒤 새로고침**하는 순서로 안내한다.
