# 무먹 2차 광고 — 집밥흐름 랜딩페이지 PRD

- 작성일: 2026-09-11
- 버전: 0.7
- 상태: 후속 사용자 승인으로 구현한 미배포·미머지 로컬 후보의 PRD. 기존 r2.1 계약 또는 독립 Stage 승인을 대체하지 않는다.
- 대상: 2차 광고의 **집밥흐름 수요검증용 랜딩페이지**
- UI 기준: 1차 광고의 기존 `/beta` 랜딩페이지
- 산출물 범위: 콘텐츠, 체험 시나리오, 측정 요구사항, 구현 인수 조건

> 후속 사용자 요청으로 이 PRD의 로컬 구현·검증을 진행했다. [로컬 구현 인수](./homeflow-local-implementation.md)에 코드 위치, 미리보기, 제공 캐릭터 반영과 검증 결과를 기록한다. 로컬 후보의 인수 기준이며 배포·master 머지·독립 Stage 승인을 의미하지 않는다.

## 1. 배경과 결정 사항

1차 광고는 **집에서 만든 요리를 식단에 기록하는 것에 대한 수요**를 조사했으며, 사용자 설명 기준 2026-09-11 종료 예정이다. 이 문서는 1차 결과를 조회하거나 성과를 평가한 보고서가 아니다.

2차 광고에서는 다음 두 가치 제안을 각각의 URL로 운영한다.

| 구분 | 검증할 가치 | 이번 작업 범위 |
| --- | --- | --- |
| 식단기록 랜딩 | 집에서 만든 요리를 식단에 기록하기 | 기존 콘텐츠·UI 재사용. 새 콘텐츠 작성 대상 아님 |
| 집밥흐름 랜딩 | 레시피 → 요리 계획 → 장보기 → 요리 → 식사 기록을 연결하기 | 이 PRD의 신규 콘텐츠 대상 |

사용자 확정 방향:

- 1차 랜딩페이지의 화면 틀, 디자인, 기본 조작을 재사용한다.
- 식단기록과 집밥흐름은 별도 URL로 구분한다. 한 페이지에서 주제를 선택하게 하지 않는다.
- 집밥흐름용 질문, 결과 설명, 체험 내용을 새로 만든다.
- 설문은 4문항이며 선택지는 존댓말 대신 단답형 또는 음슴체로 작성한다.
- Q3의 첫 선택지는 **계획 자체 없이 즉흥적으로 정하는 방식**이다. 계획은 하되 기록하지 않는 방식과 구분한다.
- Q4는 사용자가 지정한 네 선택지를 그대로 사용한다.
- 앞서 제안한 네 결과 유형의 이름과 긍정적인 방향은 유지하고 설명의 유머를 강화한다.
- 첫 화면은 광고 손그림에서 추출한 캐릭터를 사용하고, 네 유형·초대·완료는 제공 캐릭터의 배경 제거 파생본을 더 크게 보여준다. 원본 PNG와 기존 파란 배경 WebP는 보존한다. 투명 WebP 7개는 [투명 자산 기록](./assets/homeflow-transparent-manifest.json)을 기준으로 한다.
- 실제 유튜브 영상은 사용자가 선정한 **추추의 한끼식사 김치볶음밥 Shorts**를 사용한다. URL·제목·채널·재료는 §10에 확정 자료로 기록하고, 같은 영상의 실제 썸네일·채널 프로필 이미지를 사용한다.
- 불 세기·조리 시간은 제공된 원본에 있는 경우 짧은 태그로 표시한다. 출처 없는 값은 추정해 넣지 않는다.
- 사용자는 기존 R2의 메뉴→독립 활동→메뉴 복귀 UI를 보류하고, 이번 집밥흐름은 1차처럼 선형으로 진행하도록 재확인했다. 와이어프레임 확인 후 로컬 구현·검증을 승인했으며 배포·master 머지는 계속 금지한다.
- 후속 이미지 방향: **광고용 예시 화면으로 무먹을 직접 조작하는 느낌**을 유지하되 실제 앱을 정확히 복제하지 않는다. 1차 랜딩의 밝은 배경·파란 강조색·큰 버튼을 바탕으로 더 간결하고 효율적인 화면 구성을 허용한다.
- 장보기는 살 재료와 팬트리 제외 재료를 한 화면에서 함께 보여준다. 요리 계획은 주간 날짜 띠와 요리 행 중심으로 재구성하며, 일요일의 기존 장보기 완료 요리도 보여준다. 식사 기록은 사용자가 제공한 **1차 랜딩의 주간 날짜 띠·오늘 카드·네 영양 요약 칸·끼니별 행·내일 카드 일부·하단 베타 CTA**를 재사용한다.

각 체험 화면은 큰 제목을 최대 하나만 사용하고 `01 레시피 가져오기` 같은 중복 소제목을 삭제한다. 상단 진행 표시 `x / 5`는 유지한다. 체험 3은 큰 제목을 시각적으로 숨기고 목록에서 바로 시작한다. 완료 배너·반복 설명·행마다 붙는 하늘색 태그를 줄이고 내용 자체로 상태를 보여준다.

이전 대화의 ‘핵심 3장면만 필수 체험’ 제안은 적용하지 않는다. 이번 기획은 기존 UI와 화면 흐름 재사용을 우선하며, 체험 중간 이메일 신청이나 선택형 확장 경로를 추가하지 않는다.

### 최신 저장소의 별도 R2 기획과의 관계

작업 브랜치를 최신 `origin/master`에서 생성한 뒤, 이미 별도의 [r2.1 공식 계약](../marketing-demand-validation-r2-contract.md)과 [R2 workpack](../workpacks/marketing-demand-validation-round2/README.md)이 들어와 있음을 확인했다. 해당 계약은 **알림·사용 예시·설문을 자유 순서로 선택**하며 **유형 결과를 제공하지 않는다**. 질문도 이 대화의 네 문항과 다르다.

이 문서는 현재 대화에서 요청한 **1차 UI 재사용·설문 뒤 유형 결과·집밥흐름 체험**의 로컬 구현 방향을 기록한다. 미배포 `r2.2-homeflow`의 표시 문구는 최신 사용자 요청에 맞췄으며 기존 `r2.1-homeflow`와 `r2.1-recording` 문구·값·저장 자료는 그대로다. 구체적 경계는 [로컬 구현 계약](./homeflow-linear-implementation-contract.md)을 따른다. r2.1과 일치한다고 주장하거나 기존 계약을 조용히 대체하지 않는다. §13의 차이 목록을 후속 공식 계약 조정에 사용한다. 식단기록용 R2 콘텐츠·독립 활동을 이 PRD만으로 변경하지 않는다.

## 2. 목표와 검증 가설

### 제품 메시지

> 저장한 레시피를 이번 주 집밥으로. 계획부터 장보기, 요리까지 한 흐름으로 이어주는 무먹.

### 검증 목표

집밥을 준비하는 사람이 연결된 사용 흐름을 이해한 뒤, 실제 서비스 이용을 기대하고 베타 초대를 신청하는지 확인한다.

| 가설 | 확인할 자료 | 해석 범위 |
| --- | --- | --- |
| 집밥 준비 과정에 반복되는 불편이 있다 | Q4 응답 분포 | 제시한 세 불편 중 상대적 선택. 전체 불편의 포괄적 조사로 해석하지 않음 |
| 유튜브 레시피 이용자가 무먹의 흐름에 관심을 보인다 | Q2별 체험 시작·신청 비율 | 유튜브 사용 경험과 반응의 관계. 인과관계로 단정하지 않음 |
| 연결된 집밥흐름이 베타 이용 의향으로 이어진다 | 전체 방문 대비 유효 신청, 체험 완료 대비 유효 신청 | 초기 무료 베타 관심. 지속 사용·유료 수요의 증거는 아님 |
| 어떤 계획 방식의 사용자가 더 반응하는지 구분할 수 있다 | Q3 유형별 신청 수와 비율 | 유형의 우열이나 성격 진단이 아님 |

유형 테스트 참여, 체험 완주, 이메일 신청은 서로 다른 신호로 보고한다. 체험의 순차 완료만으로 개별 기능의 선호 순위를 추정하지 않는다.

## 3. 대상 사용자

- 직접 집밥을 만들거나, 앞으로 더 자주 만들어보려는 사람.
- 유튜브 레시피를 참고해 요리하는 사람.
- 메뉴 계획, 장볼 재료 정리, 요리 중 레시피 확인을 여러 곳에서 처리하는 사람.

최근 요리 횟수나 유튜브 이용 횟수가 0이어도 설문·결과·체험을 끝까지 제공한다. 답변으로 숨겨진 적합도 점수나 탈락 조건을 만들지 않는다.

## 4. 범위와 UI 재사용

### 포함

- 집밥흐름용 첫 화면 문구.
- 네 문항과 네 결과 유형, 결과별 설명·인용문·캐릭터 방향.
- Q4 답변에 맞춘 짧은 체험 연결 문구.
- 기존 5단계 체험 틀과 1차형 식사 기록 결과 화면으로 이어지는 집밥흐름 시나리오. 요리 완료·별도 분량 입력 중간 화면은 결합 CTA로 통합한다.
- 베타 초대·신청 완료 문구.
- 광고 차수·랜딩 주제별 분석 분리 요구사항.

### 재사용할 것

- 브랜드 색, 글꼴, 배경, 카드, 버튼, 여백과 기존 반응형 구성.
- 첫 화면, 질문 카드, 진행 표시, 결과 카드와 캐릭터 영역.
- 선택 강조 후 약 300ms 자동 이동, 별도 다음 버튼 없음, 뒤로가기와 답변 유지.
- 결과의 제목·인용문·설명·이미지·공유·체험 CTA 배치.
- 체험 화면 프레임, 기존 강조·전환 방식, 하단 CTA 위치.
- 이메일 입력, 동의, 전송 중·실패·재시도·완료 UI.
- 기존 접근성, 키보드·모바일 대응과 이미지 성능 기준.

### 변경 경계

‘UI 재사용’은 기존 식단기록 데이터의 의미까지 재사용한다는 뜻이 아니다. 체험 카드 안의 요리·재료·팬트리 내용과 조작 대상은 이 시나리오에 맞게 바꾸되, 1차의 시각 언어와 선형 이동 방식은 유지한다. 장보기·요리 계획은 광고 체험에 맞게 정돈하며, 실제 앱의 탭이나 모든 기능을 복제할 필요는 없다.

새 UI 테마, 새 전역 탐색 구조, 새 필수 화면, 드래그앤드롭, 별도 앱 가입, 실제 장보기·요리 데이터 저장, 실제 유튜브 분석 작업은 포함하지 않는다. 외부 유튜브 영상 입력 없이 준비된 예시를 누르는 체험으로 구성한다.

## 5. URL과 실험 분리

URL은 저장소의 기존 R2 계약에 명시된 경로를 재사용한다. 집밥흐름 페이지는 로컬 후보로 구현했지만 운영 배포는 하지 않았다. 새 콘텐츠·진도는 로컬 구현 계약 범위이며 기존 R2 계약을 덮어쓰지 않는다.

| 구분 | URL | 콘텐츠 |
| --- | --- | --- |
| 기존 1차 링크 | `/beta` 및 기존 공유·광고 링크 | 기존 의미와 기록 보존 |
| 2차 식단기록 | `/beta/r2/recording` | 식단기록 비교군. 콘텐츠·동작 수정은 이 PRD 범위 밖 |
| 2차 집밥흐름 | `/beta/r2/homeflow` | 이 PRD의 신규 콘텐츠 제안 |

요구사항:

1. URL에서 랜딩 주제가 일관되게 결정된다. 광고 문구 변형 값이 다른 주제의 콘텐츠로 바꾸면 안 된다.
2. 1차 식단기록, 2차 식단기록, 2차 집밥흐름을 분석에서 구분한다. 집행 기간과 콘텐츠 버전도 남긴다.
3. 같은 브라우저에서 두 URL을 번갈아 열거나 동시에 열어도 답변·결과·체험 진도·신청 귀속이 섞이지 않는다.
4. 1차 방문자의 기존 쿠키가 있어도 2차 집밥흐름의 질문을 건너뛰거나 옛 결과를 보여주지 않는다.
5. 새로고침·뒤로가기·재방문은 해당 랜딩 주제의 상태로 복구한다.
6. 공유 링크는 집밥흐름 결과임을 보존한다. 공유 미리보기 방문을 설문 완료로 집계하지 않는다.
7. 두 주제에 모두 신청한 사람은 주제별 반응과 서비스 전체 신규 모집 인원을 구분한다. 같은 사람에게 중복 초대를 보내는 근거로 사용하지 않는다.

단순히 주소만 바꾸고 동일 session/응답 정의에 새 문항을 덮어쓰는 구현은 허용하지 않는다. 브라우저 식별자를 실제 사람 수로 단정하지 않으며, 전체 모집 중복 제거는 기존 이메일 중복 정책과 정합성을 맞춘다.

## 6. 화면 흐름

`첫 화면 → Q1 → Q2 → Q3 → Q4 → 유형 결과 → 체험 1~5 → 체험 6: 주간 식사 기록 → 베타 신청 → 신청 완료`

체험 1~5는 상단 `x / 5` 진행 표시를 유지한다. 체험 6은 다섯 단계 뒤의 식사 기록 결과 화면이며 `6 / 5`를 표시하지 않는다.

## 7. 첫 화면 카피

- 제목: **베타 오픈 전 수요조사**.
- 설명: **나의 집밥 스타일을 알아보고 / 무먹을 먼저 체험해보세요.** 두 줄로 표시한다.
- 3단계 안내: **테스트 → 무먹체험 → 베타신청**.
- 단계별 설명: **내 집밥 유형 찾기 / 직접 눌러서 경험하기 / 오픈 소식 먼저 받기**.
- 이미지: 광고 손그림에서 추출한 **hero-ad-transparent.webp** 캐릭터를 사용한다. 레시피 미디어 카드는 넣지 않는다.
- 버튼: **4문항 테스트하기**.
- 보조 표시: **로그인 없이 · 결과 바로 확인**.

제품 체험과 초대 신청까지 이어진다는 점을 3단계로 보여준다. 실측 전에는 ‘30초면 끝’, ‘매주 2시간 절약’ 같은 수치를 약속하지 않는다.

## 8. 설문조사: 정확한 질문·선택지

아래 문구는 미배포 로컬 `r2.2-homeflow`만의 표시 기준이다. 기존 r2.1 설문은 변경하지 않는다.

공통 규칙: 한 화면에 한 문항, 각 네 선택지, 단일 선택. 선택지는 아래 단답형을 사용한다. 질문·결과 설명에는 자연스러운 존댓말을 허용한다. 선택지 길이 때문에 글자를 과도하게 줄이거나 기존 카드 구조를 바꾸지 않는다.

### Q1. 지난 7일 동안, 요리한 날은 며칠인가요?

| 순서 | 선택지 |
| --- | --- |
| 1 | 0일 |
| 2 | 1~2일 |
| 3 | 3~4일 |
| 4 | 5~7일 |

목적: 요리하는 빈도별 반응 비교. 하루에 여러 번 요리해도 하루로 센다. 기록 빈도나 집밥을 먹은 끼니 수와 혼합하지 않는다.

### Q2. 최근 4주 동안, 유튜브 레시피를 보고 요리한 횟수는?

| 순서 | 선택지 |
| --- | --- |
| 1 | 0회 |
| 2 | 1회 |
| 3 | 2~3회 |
| 4 | 4회 이상 |

목적: 유튜브 레시피 기반 요리 경험별 반응 비교. 0회를 ‘유튜브를 보지 않음’이나 ‘저장한 레시피가 없음’으로 해석하지 않는다. 기존 4선택지 UI를 유지한다.

### Q3. 집밥은 보통 어떻게 계획하나요?

질문 아래 보조 설명은 화면에 표시하지 않는다.

| 순서 | 선택지 | 결과 유형 |
| --- | --- | --- |
| 1 | 계획 없이 그때그때 정함 | 오늘의 감각형 |
| 2 | 미리 정하고 머릿속에 기억 | 머릿속 플래너형 |
| 3 | 메모·캡처로 대략 정리 | 알뜰 메모형 |
| 4 | 날짜별 메뉴까지 정리 | 집밥 설계형 |

첫 번째는 사전 계획 없음, 두 번째는 사전 계획 있음·외부 기록 없음이다. 세 번째는 날짜가 정해지지 않은 느슨한 기록, 네 번째는 날짜와 메뉴를 연결한 계획이다. 여러 방식을 함께 사용하면 가장 가까운 주된 방식을 고른다.

### Q4. 집밥을 준비할 때 가장 불편한 것은?

| 순서 | 선택지 |
| --- | --- |
| 1 | 집밥 계획 세우기 |
| 2 | 집에 있는 재료 빼고 장보기 목록 만들기 |
| 3 | 요리하면서 레시피 영상 다시 보기 |
| 4 | 별로 불편하지 않음 |

사용자 지정 문구와 네 선택지를 그대로 유지한다. ‘기타’나 추가 질문을 임의로 넣지 않는다. 두 번째 선택지는 자연스러운 줄바꿈을 허용하고 생략 부호로 의미를 자르지 않는다.

분석 한계: 이 문항은 제시한 세 불편 중 우선순위를 묻는다. 다른 불편, 최근 집밥을 하지 않은 경우, 불편의 강도·빈도는 따로 측정하지 않는다. 따라서 4번을 골랐다고 ‘집밥 관련 문제가 전혀 없는 사람’으로 단정하지 않는다.

## 9. 결과 유형과 캐릭터 기획

### 공통 결과 규칙

- 결과 유형은 **Q3 하나로만 결정**한다. 같은 Q3이면 Q1/Q2/Q4와 관계없이 같은 유형이다.
- Q4는 결과 아래의 체험 연결 문구만 바꾸며, 유형·기능 순서·데모 데이터를 바꾸지 않는다.
- 네 유형 모두 긍정적인 특징과 가벼운 생활 유머를 사용한다. 게으름·무능·체중·성별 등을 비하하지 않는다.
- 성격 검사나 과학적 진단처럼 설명하지 않는다. 기존 재미용 안내 문장은 결과 화면에서 제거한다.
- 검증되지 않은 유형 비율, 백분위, 절약 시간은 표시하지 않는다.
- 현재는 캐릭터 6종의 **-transparent.webp** 파생본과 첫 화면 전용 손그림 추출 자산을 사용한다. [투명 자산 기록](./assets/homeflow-transparent-manifest.json)의 7개 파일은 모두 `hasAlpha=true`, `alphaMin=0`으로 실제 투명을 확인했다.
- 이전 파란 배경 WebP 6개는 720×720·품질 82, 합계 193,320B로 보존한다. 원본 PNG 10,305,593B와 원본 해시는 [이전 변환 기록](./assets/homeflow-characters-manifest.json)에 남겼다. 배경 제거 파생본을 원본 파일로 덮어쓰지 않는다.
- 네 유형·초대·완료 화면에 더 큰 투명 캐릭터와 등장·반짝임을 적용한다. 완료 캐릭터는 축하 효과와 함께 위아래로 계속 떠 있는 반복 모션을 사용한다. 기기의 동작 줄이기 설정에서는 애니메이션·전환을 정지한다.
- 캐릭터에 본문 글자를 구워 넣지 않고 제목·인용문·설명은 화면 텍스트로 제공한다.

**선정 영상과 제공 재료 — 확정 자료**

**체험을 위한 가정 — 영상 정보와 구분**

- 예시 주간은 **9/7~9/13**, 오늘은 **9/12 토요일**이다. 실제 방문일과 관계없는 고정 체험 날짜다.
- 토요일 저녁에 이 김치볶음밥을 **1회분** 계획한다. 이는 한 번 요리하는 데모 단위이며 영상의 1인분 선언이 아니다. 일요일 9/13 저녁에는 **두부조림 · 장보기 완료**가 미리 등록된 데모 상태를 보여준다. 이 음식은 선정 영상에서 가져온 요리가 아니며 장보기가 이미 끝나 이번 목록 생성 대상에서 제외된다. 나머지 빈 요리 행에는 오른쪽 작은 `+` 버튼을 둔다.
- 팬트리에 설탕·고춧가루·진간장 **3종**이 이미 등록된 것으로 가정한다.
- 이번 장보기 대상은 토요일 김치볶음밥 하나다. 그 재료 **9종** 중 살 재료는 삼겹살·대파·김치·즉석밥·버터·계란 **6종**, 제외 재료는 위 보유 재료 **3종**이다.
- 처음에는 삼겹살·대파·김치·즉석밥·버터 **5종이 구매 체크**되어 있고 계란만 미체크다. 사용자가 추가 체크·제외·되살리기를 조작할 수 있다. 완료 시 구매 체크·팬트리 반영 대상으로 남은 항목만 추가하고 기존 보유 항목은 중복 추가하지 않는다. 기본 경로에서 계란까지 체크하면 6종이다.
- **요리완료! 식단기록하기**를 누르면 요리 완료와 오늘 저녁 **김치볶음밥 300g** 기록을 함께 확인한다. 300g은 사용자가 지정한 **먹은 양의 데모 값**이며 완성 중량·한 조리분의 전체 무게가 아니다. 이전의 절반 섭취·절반 보관 가정은 폐기하고 남은 무게를 추정하거나 안내하지 않는다. 별도 계량 입력을 강요하지 않는다.
- 아침 **그릭요거트 볼 250g · 420 kcal**, 점심 **닭가슴살 현미밥 400g · 700 kcal**는 이미 기록된 데모 음식이다. 이 수치는 사용자가 지정한 체험 예시이며 새 영상의 재료·영양이나 장보기 대상이 아니다.
- 영양값은 사용자 제공 **김치볶음밥 300g = 608kcal / 탄수화물 56g / 단백질 25g / 지방 32g**을 사용한다. 기존 아침·점심 시연 합계 **1120kcal / C146g / P72g / F38g**에 더해 **1728kcal / C202g / P97g / F70g**을 표시한다. 작은 표시는 **영양정보 · 체험 예시**이며 실측·공식 영양 분석을 완료했다고 주장하지 않는다. [영양 표시 기준](./homeflow-demo-nutrition.md)에 사용자 제공 값과 기존 시연 데이터·합산을 구분한다. 이전 — 표시와 600g 완성 가정 추정안은 이번 요청으로 대체한다.

**이미지·조리법 반영 규칙**

- 선정 영상의 [실제 썸네일](./assets/homecook-flow-round2-wireframes/youtube-IxXeEFTf0ZQ/thumbnail.jpg)과 [채널 프로필](./assets/homecook-flow-round2-wireframes/youtube-IxXeEFTf0ZQ/channel-profile.jpg)을 확보했다. 공개 영상 페이지의 채널 정보와 oEmbed를 확인했으며 원본 URL·해시는 [출처 기록](./assets/homecook-flow-round2-wireframes/youtube-IxXeEFTf0ZQ/source.json)에 남겼다. ImageGen 보드 안의 재렌더링된 이미지를 실제 원본으로 사용하지 않고, 구현 시 이 원본 자산을 사용한다.
- 영상 제목·채널명·출처 링크를 표시한다. 사용 가능한 자산 범위를 확인하며 광고 이미지 사용은 랜딩 출처 표시와 별도로 확인한다.
- 원본에서 확인한 불 세기·시간만 짧은 태그로 넣는다. 아직 확인하지 못한 태그는 숨기고, 원본의 상태 기준을 임의의 분 단위로 바꾸지 않는다.
- 공개 영상 설명은 비어 있고 자막 조회 응답도 비어 있어 조리 순서·불 세기·시간은 미확인이다. 와이어프레임에서는 아래 단계를 **구성 예시**로만 표시한다. 실제 영상의 조리법으로 주장하거나 이 상태로 공개 체험에 확정 반영하지 않는다. 원본 단계가 확인되면 교체한다.

로컬 preview의 상단에는 **로컬 미리보기 · 저장되지 않아요**, 운영 수집 준비 전 공개 체험에는 **미리 둘러보기 · 입력은 저장되지 않아요**를 표시한다. 수량 가정과 미확인 정보는 기능 설명을 방해하지 않도록 필요한 화면에만 짧게 드러낸다.

### 체험 1. 레시피 가져오기

- 제목: **유튜브에서 레시피를 가져왔어요**.
- 화면: 작은 영상 썸네일, 채널 프로필·이름, 출처 링크와 넓은 재료 영역.
- 기본 재료 목록: 삼겹살 120g·대파 50g·잘 익은 김치 210g·설탕 3g·고춧가루 4g. 기존 plush-v2 재료 이미지를 함께 사용한다.
- **외 4가지 재료**를 누르면 진간장 7g·즉석밥 210g·버터 8g·계란후라이 1개까지 펼치고 **재료 접기**로 복귀한다. 원재료는 계속 9종이며 계란 중량은 만들지 않는다.
- 행동: **요리 계획에 추가하기**.
- 원칙: 가져오기 완료 상태의 예시다. 중복 완료 배너를 넣거나 실제 외부 수집이 실행됐다고 주장하지 않는다. 재료를 펼치면 필요한 세로 스크롤을 허용한다.

### 체험 2. 주간 요리 계획

- 제목: **요리계획**을 캘린더 아이콘과 함께 왼쪽 정렬한다.
- 화면: 주간 날짜 띠에서 **12일 토요일** 선택. **토요일 9/12**, **일요일 9/13** 각각 아침·점심 빈 행과 저녁 요리 행을 표시한다.
- 토요일 저녁 김치볶음밥은 이미지 로드가 끝난 뒤 **1,100ms** 기다렸다가 **900ms** 동안 이동·크기 확대와 배경 강조로 등장한다. 그 뒤 안정된 행으로 남으며, 일요일 저녁에는 기존 **두부조림 · 장보기 완료**가 회색 일반 텍스트로 보인다. 끼니는 이미지 왼쪽, 작은 정사각형 **+**는 오른쪽에 배치하며 채널 프로필은 넣지 않는다.
- 행동: **장보기 목록 만들기**.
- 범위: 장보기가 끝난 두부조림은 제외하고 김치볶음밥만 이번 목록 대상이다. 하늘색 태그·계획 개수 배너·반복 설명은 넣지 않는다.
- **+** 버튼은 짧은 추가 안내를 열고 **체험 계속하기**로 닫는다. 준비된 요리 외에 실제 데이터를 생성하지 않는다.

### 체험 3. 장보기 목록과 보유 재료 제외

- 큰 제목: 화면에 표시하지 않는다. 접근성용 이름 **장보기 목록**은 유지한다.
- 화면: **살 재료 6 / 팬트리 제외 3** 목록. 살 재료는 구매 체크·기존 재료 이미지·이름·양·**이미있음** 버튼, 제외 항목은 이름·양·**되살리기**로 구성한다.
- 초기 상태: 삼겹살·대파·김치·즉석밥·버터 5종 체크, 계란 미체크. 팬트리에는 설탕·고춧가루·진간장 3종이 제외되어 있다.
- 조작: **이미있음**을 누르면 제외 영역으로 옮기고 구매 체크를 해제한다. **되살리기**는 미체크 상태로 구매 목록에 복귀시킨다. 목록 개수는 실제 조작에 맞춰 갱신한다.
- 행동: **체크하고 장보기 완료하기**. 구매 체크가 하나도 없으면 비활성화한다. 완료 시 선택된 구매 항목만 팬트리 반영 대상으로 확정한다.
- 원칙: 제외 항목을 구매 완료로 표시하지 않고 중복 설명을 넣지 않는다. 완료 뒤 되돌아오면 read-only이며 **팬트리 확인하기**로 결과를 다시 볼 수 있다.

### 체험 4. 팬트리 반영 뒤 요리 계획

- 제목: **요리계획**을 캘린더 아이콘과 함께 왼쪽 정렬한다.
- 화면: 체험 2의 이틀·세 끼 플래너를 재사용하고 오늘의 김치볶음밥 계획을 선택 상태로 강조한다. 해당 행에 **지금 요리할 메뉴**를 표시한다.
- 일시 안내: **✓ 구매한 재료를 팬트리에 추가했어요**가 나타난 뒤 **2.4초** 후 사라진다. 별도 6종 목록·행별 추가됨 태그·기존 보유 재료 안내는 반복하지 않는다.
- 행동: **김치볶음밥 요리하기**.
- 원칙: 실제 반영 상태는 직전 화면의 구매 체크·반영 대상만 사용한다. 화면 간소화 때문에 무조건 6종을 추가하거나 완료한 장보기를 수정 가능한 상태로 바꾸지 않는다.

### 체험 5. 요리모드

- 제목: 작은 김치볶음밥 썸네일 바로 옆의 **김치볶음밥** 하나만 표시한다.
- 화면: **텍스트 재료명 + 양**의 조밀한 두 열 묶음과 큰 조리법. 재료 목록에는 이미지·아이콘을 넣지 않고 계란후라이는 **1개**를 유지한다.
- 조리법: `삼겹살·대파 볶기 → 김치와 양념 넣기 → 즉석밥 넣고 볶기 → 버터로 마무리 → 계란후라이 올리기`를 **구성 예시**로 표시한다. 실제 원본 순서·불 세기·시간은 미확인이며 가짜 태그·타이머를 추가하지 않는다.
- 행동: **요리완료! 식단기록하기**.
- 변화: 데모의 요리 완료와 토요일 저녁 **300g** 기록을 명시적으로 확인하고 체험 6으로 이동한다. 별도 계량·분량 입력 화면을 넣지 않는다.
- 원칙: 일반 제품에서 요리 완료만으로 섭취를 자동 기록하도록 계약을 완화한 것이 아니다. 큰 음식 사진·영양 수치·영상·인분 조절 UI를 추가하지 않는다.

### 체험 6. 이번 주 식단

- 제목: **이번주 식단**.
- 화면: 주간 날짜 띠 → **오늘 9/12 (토)** → 네 영양 요약 칸 → 아침·점심·저녁 행 → **내일 9/13 (일)**. 저녁 추가 후 **3/3** 기록 상태다.
- 아침: **그릭요거트 볼**, 이름 아래 **250g · 420 kcal**.
- 점심: **닭가슴살 현미밥**, 이름 아래 **400g · 700 kcal**.
- 저녁: **김치볶음밥**, 이름 아래 **300g · 608 kcal**. 이미지 로드 완료 후 **1,100ms** 대기하고 **900ms** 동안 이동·확대·배경 강조로 기록이 등장한다. 값은 사용자 제공이며 별도 실측을 검증했다고 주장하지 않는다.
- 영양 요약: 저녁 추가 전 **1120kcal / C146g / P72g / F38g**, 추가 후 **1728kcal / C202g / P97g / F70g**으로 합산한다. 작은 **영양정보 · 체험 예시** 표시를 사용하고 완성 600g 가정 상세는 넣지 않는다.
- 각 끼니 오른쪽에는 작은 정사각형 **+** 버튼을 둔다. 내일은 **0/3**, **+ 식사 추가**만 보이며 자동 기록을 생성하지 않는다.
- 행동: **무료 베타 초대받기**.
- 원칙: 남은 음식 절반·잔량 안내는 넣지 않는다. 고정 CTA에 내용이 가리지 않게 하며 모션 줄이기 설정에서는 등장 효과를 정지한다.

### 체험 조작·복구

- 상단에는 진행 표시 `x / 5`만 유지하고 큰 제목 위의 단계별 중복 소제목을 없앤다. 각 화면의 큰 제목은 최대 하나이며 완료 배너·상태 태그·설명문을 반복하지 않는다. 주간 날짜·요리 행·체크 목록을 중심에 둔다.
- 요리 계획은 광고용으로 간결하게 재구성하고, 식사 기록은 1차 랜딩의 주간 식단 구성을 따른다. 실제 앱의 모든 탭과 전역 메뉴를 복제하지 않는다.
- 체험 3은 구매 영역과 팬트리 제외 영역을 함께 보여주며 제외 영역에 구매 체크 표시를 하지 않는다. 체험 4는 선택된 오늘 요리 계획을 보여주고 팬트리 반영 안내는 2.4초 뒤 사라진다.
- 요리모드의 결합 CTA로 지정된 300g 식사 기록을 확인한다. 별도 분량 입력·계량 화면·남은 음식 화면·메뉴 복귀 단계를 추가하지 않는다.
- 앱 내부 버튼이 실제 동작을 담당한다. 작동하지 않는 탭·검색·메뉴를 활성 상태로 방치하지 않는다.
- 클릭에는 요리 카드 추가, 목록 생성, 보유 재료 분리, 체크, 완료 등 눈에 보이는 상태 변화가 따른다.
- 중복 클릭으로 요리·재료·음식·신청이 늘어나지 않는다. 뒤로 돌아가도 이미 수행한 상태를 모순되게 재적용하지 않는다.
- API 실패나 공유 실패가 답변·결과·체험 내용을 지우지 않는다.
- 기본 390×844·375×812·320×720 화면은 스크롤 없이 구성한다. 320×568, 큰 글자·키보드·펼친 재료·동의 상세는 잘림 대신 필요한 스크롤을 허용한다.
- 전체 체험 완료 후 이메일 신청으로 이동하는 선형 순서를 유지한다.

## 11. 베타 신청과 완료 문구

### 신청 화면

- 더 큰 **invitation-transparent.webp** 캐릭터와 등장·반짝임 효과를 사용한다.
- 제목: **무먹, 직접 써보고 싶나요?**
- 설명: **베타가 준비되면 이메일로 초대해드릴게요.**
- 입력 표시: **이메일 주소**. 포커스 테두리는 안쪽으로 3px 들어가도록 `outline-offset: -3px`을 사용해 화면 바깥에서 잘리지 않게 한다.
- 필수 체크: **[필수] 이메일 수집·이용에 동의해요.**
- 펼침 제목: **수집 목적과 보유 기간 보기**.
- 펼침 내용: 수집 목적 **무먹 베타 오픈 알림 발송**, 수집 항목 **이메일 주소, 신청 주제·동의 기록**, 보유 기간 **2026년 11월 30일까지. 철회 시 해당 정보를 삭제해요.**
- 버튼: **베타오픈 신청하기**. 동의하지 않으면 제출할 수 없다.

homeflow 화면의 별도 개인정보처리방침 링크와 14세 안내는 사용자 요청대로 제거한다. 수집 목적·항목·보유 기간은 펼침에서 확인할 수 있고 서버의 기존 consent 필드·검증·보관·동의 제약은 유지한다. 다른 R2 화면의 공용 안내를 변경하지 않는다. 결과가 불명확한 제출은 같은 요청으로 확인하며 완료 전 성공을 표시하지 않는다.

### 신청 완료

- 더 큰 **success-transparent.webp** 캐릭터와 축하 색종이·지속적인 위아래 떠오름 모션을 사용한다.
- 제목: **신청이 완료됐어요!**
- 설명: **베타가 준비되면 / 이메일로 알려드릴게요.**
- 버튼: **처음으로 돌아가기**.

일반 모드는 성공 응답 후에만 완료 화면으로 이동한다. 로컬 미리보기의 완료는 저장 없는 예시다. 처음으로 이동해도 서버의 기존 완료를 삭제하거나 새 참여를 자동 생성하지 않는다. 동작 줄이기 설정에서는 축하 효과도 정지한다.

## 12. 측정과 결과 보고

### 보고 단위

각 보고서에 집행 차수, 랜딩 주제, 콘텐츠 버전, 집행 기간·시간대, 광고 소재, 유료/프로필/공유 유입 구분을 포함한다. 이는 **측정 개념**이며 신규 API field 또는 DB column 이름을 정의한 것이 아니다.

| 지표 | 정의 |
| --- | --- |
| 랜딩 방문 | 테스트·봇·명백한 중복 재전송을 제외한 측정 가능한 랜딩 세션 수. 사람 수와 구분 |
| 설문 시작률 | 설문 시작 세션 / 랜딩 방문 세션 |
| 설문 완료율 | 설문 완료 세션 / 설문 시작 세션 |
| 체험 시작률 | 체험 시작 세션 / 본인 설문 결과 조회 세션. 공유 미리보기 제외 |
| 체험 완료율 | 전체 체험 완료 세션 / 체험 시작 세션 |
| 신청 전환율 | 유효한 주제별 신청 세션 / 해당 주제 랜딩 방문 세션 |
| 신청 폼 전환율 | 유효한 주제별 신청 세션 / 신청 폼 조회 세션 |
| 신규 모집 비용 | 해당 집계 범위의 광고비 / 중복 제거한 신규 이메일 모집 수 |

유효한 주제별 신청은 서버가 동의·입력 검증을 통과한 제출 의사를 해당 주제에 귀속해 인정한 경우다. 같은 주제·같은 신청자의 재전송은 한 번만 센다. 다른 주제나 1차에서 이미 신청한 이메일의 재신청 관심은 **신규 모집과 별도**로 보고한다. 기존 시스템에서 이를 구별할 수 없으면 ‘측정 불가’로 표시하고 완료 화면 조회로 대신 추정하지 않는다.

서버에서 accepted/duplicate를 구분하는 기존 v2 집계와 R2의 주제별 관심 집계의 관계를 구분한다. 중복 제약을 느슨하게 해 중복 모집 수를 늘리는 방식은 사용하지 않는다. 신규 모집의 차수·주제 귀속은 보관 중인 자료에서 최초로 수락된 신청을 기준으로 하되, 이미 모집된 사람의 타 주제 관심과 별도로 표시한다. 두 주제 비용 계산에서 한 신규 신청자를 이중 계산하지 않는다. 기존 R2 계약의 `new_observed`는 제한된 보관 자료와 동시 쓰기 조건 안의 잠정 신규 관측이다. 이 값을 평생 신규 고객 수나 완전한 동일인 판별로 보고하지 않는다.

필수 결과표:

1. 1차 식단기록, 2차 식단기록, 2차 집밥흐름의 방문·완료·신청 원수와 비율.
2. 집밥흐름 Q1/Q2/Q3/Q4 응답별 신청 수와 전환율, 각 분모.
3. 광고 소재별 방문·신청·비용.
4. 신규 이메일 모집 수, 기존 신청자의 재신청 관심, 중복 재시도 구분.
5. 누락 데이터·제외 기준·버전 변경 시점과 해석 제한.

### 비교 해석

- 두 랜딩에 대응하는 광고의 대상·기간·예산·노출 위치가 다르면 단순 전환율 차이를 제품 가치만의 효과로 결론 내리지 않는다.
- 1차와 2차의 차이에는 시기, 재노출, 기존 신청자의 유입이 섞일 수 있다.
- 기존 식단기록 Q1~Q4와 신규 집밥흐름 Q1~Q4는 서로 다른 질문이다. 같은 번호나 저장 구조를 이유로 응답을 합산하지 않는다.
- 이 집밥흐름 체험에도 식사 기록이 등장하므로 ‘식단기록 기능의 독립 효과’를 분리하는 실험은 아니다. **전면에 내세운 가치 제안**의 반응을 비교한다.
- Q4로 불편을 먼저 상기시키므로 체험 반응에는 그 영향이 있을 수 있다.
- 표본이 적을 때 작은 차이를 승패로 단정하지 않는다. 이메일 제출은 지속 사용·결제 의향을 보장하지 않는다.

### 판정 계획

이 PRD는 근거 없는 절대 성공률을 정하지 않는다. 광고 집행 전에 두 랜딩의 집행 조건, 모집 비용 허용 범위, 관찰 기간, 최소 분석 표본, 중단 기준을 실행 계획에 기록한다. 값이 없으면 결과는 탐색 보고로만 분류하고 ‘수요 검증 성공’ 판정을 하지 않는다.

유형 완료만 높고 체험 시작이 낮으면 결과→제품 연결을 검토한다. 체험은 진행되는데 신청이 낮으면 효용 전달, 신청 부담, 초대 시점 기대를 함께 살핀다. 반응이 모이면 후속 베타에서 실제 자기 레시피 등록과 반복 사용을 확인한다.

## 15. 후속 작업과 남은 결정

1. 이 PRD의 문구와 체험 순서를 기준으로 공식 문서 영향과 정확한 URL·문항 값·결과 키·세션·신청 귀속 계약을 정리한다.
2. 별도 Stage 1 작업에서 기존 R2 workpack과 acceptance를 조정된 계약에 맞춰 재잠그고 독립 검토를 거친다. 기존 R2 구현·검토 완료 범위를 새 방향의 완료 증거로 재사용하지 않는다.
3. 투명 자산 7종·강화된 모션·사용자 제공 영양 표시를 포함한 이번 변경의 통합 검증 결과를 확정한다. 원본 이미지·기존 검증 이력은 보존한다.
4. 로컬 후보의 인수 조건과 후속 회귀를 검증한다. 이전 전체 테스트 결과를 새 UI 변경의 검증으로 재사용하지 않는다.
5. 광고 집행 전에 예산·기간·분석 기준과 URL별 수집 동작을 확인한다.

이번 PRD 작성 자체는 광고 집행, 개인정보 수집 개시, 운영 배포, 공식 계약 확정, Stage 승인·머지를 수행하지 않는다.

## 16. 2026-09-11 후속 검토 — 빠른 구현·배포 경로

**권고: R2의 수집 기반을 재사용하고 1차 UI를 선형 흐름으로 연결한다.** 전체 수집 시스템을 새로 만드는 것보다 기존 주제별 세션·쿠키·동의·중복 방어·신청 귀속을 활용하는 편이 유리하다. 기존 R2의 메뉴/자유활동 UI를 가져오지는 않는다. 이 판단은 코드 검토에 따른 작업량 비교이며 오늘 배포 완료를 보장하는 일정 산정이 아니다.

- 기존 R2 API의 설문 시작/제출 → 예시 시작/완료 → 신청 시작/제출을 화면 순서대로 사용할 수 있다. 서버에 새로운 활동 종류를 추가할 필요는 없다. 선형 UI와 서버의 활동 순서 강제는 별개다.
- 새 질문 의미는 R2의 기존 `r2.1-homeflow`와 다르다. 타입뿐 아니라 SQL의 질문 값·버전 제약을 함께 조정해야 하며 기존 값에 새 의미를 덮어쓰지 않는다.
- R2 응답은 활동 완료 상태를 제공하지만 답변·유형·세부 체험 장면을 돌려주지 않는다. 유형 계산·진도 복원은 별도 화면 상태 연결이 필요하며 저장 자료를 잃은 경우의 복구 범위를 후속 계약에서 정한다.
- master 머지 전 배포는 [빠른 개발 배포 문서](../engineering/prelaunch-web-deployment.md)의 `--reviewed-ref` 경로가 있다. 검토·테스트한 정확한 커밋이어야 하며 현재 실행 웹 커밋의 후속이어야 한다. 테스트·빌드·DB 가드를 생략하는 기능은 아니다.
- 기존 R2 DB가 미적용이면 함수·trigger가 있는 R2 migration은 일반 빠른 DB 배포 허용 범위에 맞지 않는다. 기존 DB 적용 상태와 새 설문 버전 migration의 적합성을 확인해야 한다.
- R2 DB·운영 키·접수 설정·현재 실행 SHA는 이번 이미지 작업에서 확인하지 않았다. 이미 광고를 집행했으므로 ‘광고 미집행’ 전제의 개발 배포 예외 적용 범위도 재검토 대상이다. 이 절은 초기 배포 경로 검토 이력이다. 후속 승인으로 로컬 구현만 진행했으며 배포·master 머지는 계속 금지되어 실행하지 않았다.

최신 수정은 토요일·일요일 세 끼 계획, 제목을 숨긴 장보기, 선택된 오늘 계획과 일시 팬트리 알림, 텍스트 요리모드, 300g 기록, 캐릭터·필수 동의·완료 모션을 포함한다. 이미지 보드의 예전 날짜·제목·팬트리 목록은 최신 화면 기준으로 사용하지 않는다.

- 실제 콘텐츠의 불 세기·시간·조리 순서는 확인한 원본 정보만 사용한다. 시안의 조리 순서는 구성 예시임을 명시하고 미확인 시간 태그는 숨긴다.
