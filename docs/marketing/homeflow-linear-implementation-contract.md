## 페이지 전환 후 시작 대기 단축

- 첫 화면 안내 순차 시작은 0.1/0.25/0.4초, CTA 강조는 0.7초다. 이미지 로드 후 재생한다.
- 체험2/6 음식 등장 시작은 이미지 로드 후 1.1초에서 0.45초로 단축한다. 기존 등장 지속시간·식단 영양 카운트 동기화는 유지한다.
- 체험4 메뉴 강조는 0.45초, 재생 아이콘은 0.65초, 요리 버튼 강조는 0.95초에 시작한다. 팬트리 안내는 기존 시간만큼 표시하며 강조와 함께 진행한다.
- 아래 과거 시작 대기 수치는 이 후속 사용자 요청으로 대체한다.

## 식단 기록 확대·영양 합계 카운트 후속 수정

- 체험6은 이미지 로딩 후 1.1초 대기한 다음 1.4초 동안 김치볶음밥이 작게 시작해 제 크기로 확대된다. 체험2의 기존 타이밍은 유지한다.
- 같은 등장 상태에 맞춰 아침·점심 합계에서 저녁을 더한 최종 영양 합계까지 숫자가 빠르게 증가하다 감속해 멈춘다. 최종값은 1,728kcal·탄수화물202g·단백질97g·지방70g이다.
- 모션 줄이기는 확대·숫자 이동을 생략하고 최종 합계를 표시한다. 숫자 갱신을 화면 읽기 도구에 반복 안내하지 않는다. 배포·master 머지는 하지 않는다.

## 2026-09-12 후속 사용자 승인 — 광고 연결·투명 캐릭터·인지 가능한 모션

- 첫 화면은 제공된 광고 손그림 캐릭터를 배경 제거해 사용한다. 유형·초대·완료 캐릭터도 실제 알파가 있는 WebP 파생본으로 바꾸고 더 크게 표시한다. 원본은 보존한다.
- 유형 문구는 쉬운 표현으로 수정한다. 오늘의 감각형 인용문은 `오늘의 메뉴? 방금 정함`, 메모형은 저장한 레시피를 찾는다는 설명, 설계형은 이미 정한 메뉴와 계획 실행을 설명한다.
- 요리계획 2/4 제목은 달력 아이콘과 왼쪽 정렬한다. 체험4에는 `지금 요리할 메뉴`와 `김치볶음밥 요리하기`로 선택을 명확히 한다. 체험2/6의 음식은 이미지 로딩 후 1.1초 대기하고 0.9초간 등장한다.
- 사용자가 김치볶음밥 300g의 영양을 608kcal·탄수화물56g·단백질25g·지방32g으로 제공했다. [영양 표시 기준](./homeflow-demo-nutrition.md)의 이 값을 사용하고 기존 아침·점심과 합쳐 1,728kcal·탄수화물202g·단백질97g·지방70g을 표시한다. `영양정보 · 체험 예시`로 구분하며 앞서 검토한 완성중량600g 추정은 폐기한다. 일반 제품의 영양 계산 계약 변경은 아니다.
- 이메일 포커스 테두리는 입력칸 안쪽에 표시한다. 신청 완료 캐릭터의 움직임은 반복하며 reduced-motion에서는 정지한다.

이전 절의 숫자 미표시는 이번 사용자 제공값에 한해 대체한다. API·DB·동의·수집 보호 및 배포·master 머지 금지는 유지한다.

## 후속 사용자 승인 — 캐릭터와 모바일 압축 UI

전달받은 캐릭터 6종을 원본 변경 없이 WebP로 압축한다. 유형 4곳과 초대·완료에 연결하고 이미지 등장·반짝임·축하 모션을 넣되 reduced-motion에서는 정지한다. 가능한 기본 모바일 화면에서 스크롤을 없애고, 펼친 재료/동의·작은 높이·큰 글자·키보드 상태는 잘림 대신 필요한 스크롤을 허용한다.

- 첫 화면은 `베타 오픈 전 수요조사`, `테스트 → 무먹체험 → 베타신청`, `4문항 테스트하기`다. 첫 화면의 레시피 미디어 카드는 제거한다.
- Q1/Q2의 `직접`을 삭제하고 Q3은 `집밥은 보통 어떻게 계획하나요?`로 바꾼다. Q3 아래 설명을 제거한다. 미배포 로컬 설문 r2.2의 표시 문구 수정이며 기존 r2.1 값·문구·자료는 보존한다.
- 결과 설명은 2줄로 정리한다. 재미용 설명과 q4=none 일반 연결 안내를 제거한다.
- 체험 날짜는 9/12 토요일 김치볶음밥, 9/13 일요일 기존 두부조림이다. 요리 계획은 각 날짜의 아침·점심 빈 행과 저녁 행을 표시한다.
- 장보기는 계란만 미체크인 구매 5체크 상태로 시작한다. `이미있음` 버튼, `팬트리 제외`, `되살리기`, `체크하고 장보기 완료하기`를 사용한다. 기존 제외→uncheck/완료 read-only는 유지한다.
- 체험4는 선택된 김치볶음밥 계획을 보여주고 팬트리 추가 안내는 짧게 나타났다 사라진다. 체험5는 작은 썸네일·제목과 텍스트 재료 묶음으로 압축한다.
- 식사 기록은 9/12 오늘·9/13 내일, 작은 정사각형 추가 버튼, 300g 기록 등장 모션을 사용한다. 실제 영상 미확인 조리 정보·영양 수치는 추정하지 않는다.
- 신청 동의는 `[필수] 이메일 수집·이용에 동의해요.` 체크와 `수집 목적과 보유 기간 보기` 펼침 영역으로 정리한다. 기존 수집 항목·목적·보관·동의 필드는 보존하고, homeflow 화면의 별도 개인정보처리방침 링크와 14세 안내는 사용자 요청대로 제거한다. 다른 R2 화면의 공용 문구는 변경하지 않는다.

배포·master 머지 금지는 계속 유지한다.

## 요청과 화면

페이지는 `/beta/r2/homeflow`다. 기존 `POST /api/v1/marketing/round2`, `round_version=r2.1`, 세 활동 `survey/example/lead`, 응답 envelope와 활동 상태를 유지한다. 별도 endpoint나 공개 응답 필드를 추가하지 않는다.

UI는 `hero → Q1..Q4 → Q3 유형 → 체험1..5 → 300g 식단 결과 → 베타 신청 → 접수 완료`다. 서버의 활동별 start/complete 보호는 그대로며, 서버에 다른 활동의 완료를 새로운 선행조건으로 추가하지 않는다. 앱 UI의 선형 이동과 서버의 활동별 독립 처리는 구분한다.

## 새 설문 버전

`topic=homeflow`, `survey_version=r2.2-homeflow`만 아래 새 답변을 받는다. 기존 `r2.1-homeflow`와 `r2.1-recording` 정의와 저장 자료는 바꾸지 않는다.

| 문항 | 값 → 표시 |
| --- | --- |
| q1 | `none` → 0일, `one_two` → 1~2일, `three_four` → 3~4일, `five_seven` → 5~7일 |
| q2 | `none` → 0회, `once` → 1회, `two_three` → 2~3회, `four_plus` → 4회 이상 |
| q3 | `spontaneous` → 계획 없이 그때그때 정함, `mental` → 미리 정하고 머릿속에 기억, `memo` → 메모·캡처로 대략 정리, `scheduled` → 날짜별 메뉴까지 정리 |
| q4 | `planning` → 집밥 계획 세우기, `shopping` → 집에 있는 재료 빼고 장보기 목록 만들기, `video` → 요리하면서 레시피 영상 다시 보기, `none` → 별로 불편하지 않음 |

질문·결과 설명은 PRD §8~9를 따른다. 결과 키는 q3와 같은 `spontaneous/mental/memo/scheduled`이며 각각 오늘의 감각형/머릿속 플래너형/알뜰 메모형/집밥 설계형에 대응한다. 결과는 q3만으로 계산한다. API는 결과를 받거나 반환하지 않으며 분석은 제출된 q3를 같은 규칙으로 해석한다.

공유는 `/beta/r2/homeflow?result=<허용 결과 키>`만 사용한다. 공유 미리보기는 서버 참여나 설문 완료를 만들지 않는다. 테스트 시작을 누르면 정상 hero/설문 경로로 진입한다. 개인정보·답변·광고 query·참여 키는 공유 URL에 넣지 않는다.

## 저장·복원

- 기존 R2 bootstrap IndexedDB·서명 쿠키·동일 event 재시도 규칙을 재사용한다.
- UI 캐시는 `homeflow + r2.2-homeflow`로 분리하고 participation ID와 만료를 대조한다. 이메일·동의·Turnstile 토큰은 영속 캐시에 넣지 않는다.
- 서버에서 확인된 설문·예시·신청 완료를 최종 기준으로 삼는다. 낮은 revision은 무시하고 캐시만으로 제출 성공을 표시하지 않는다.
- 이전 r2.1 참여가 이미 설문 완료라면 신규 설문을 강제 제출하지 않는다. 유형 캐시가 없으면 유형을 지어내지 않고 완료 안내에서 체험으로 복귀한다. 같은 참여의 설문을 덮어쓰지 않는다.
- 네트워크 결과 불명은 같은 event/payload로 재시도한다. 제출 완료 후 다른 답변으로 변경하는 요청은 기존 409를 유지한다.
- 저장소가 막혔으면 기존 cookie_resume만 허용한다. 새 참여를 메모리에 임의 생성해 서버에 쓰지 않는다.

## 로컬 미리보기와 실제 API

`MUMEOK_ROUND2_LOCAL_PREVIEW=true`이고 exact loopback host인 경우에만 저장하지 않는 메모리 체험을 제공한다. 모든 화면에 작은 `로컬 미리보기 · 저장되지 않아요` 안내를 유지한다. 실제 이메일·Turnstile·API·DB 전송 없이 `preview@example.com`으로 접수 UI를 확인한다. query만으로 preview를 열 수 없고 운영 host에서는 이 모드를 사용하지 않는다.

일반 모드는 기존 R2 API에 연결한다. 서버 설정·서명·동의·readiness가 없거나 gate가 닫혔으면 성공을 흉내내지 않고 복구 안내를 제공한다. 준비 전에도 공개 콘텐츠/체험은 열 수 있지만 서버 제출은 실제 준비 조건을 따른다.

## SQL 영향과 검증

원본 migration은 보존한다. 후속 migration에서 새 설문 버전을 인식하는 답변 검증 함수를 추가하고 설문 payload/일관성 CHECK를 새 함수로 연결한다. 기존 RPC·동의·중복·RLS·보관 정책은 완화하지 않는다. 실제 운영 DB에는 적용하지 않는다.

검증은 신규/기존 설문 parser와 SQL, Q3 유형, UI 상태 복원·오류·중복 클릭, 모바일 체험 및 소스 버전 정합성을 포함한다. 실제 저장 경로는 기존 pinned isolated runner로 검사하고 로컬 preview를 DB 저장 증거로 취급하지 않는다.

## 구현 범위와 독립 검토

사용자가 master 머지와 배포를 금지했으므로 모든 결과는 작업 브랜치의 로컬 후보로 남긴다. 기존 R2 Stage 체크/독립 승인 상태를 이번 변경의 완료로 재해석하지 않는다. 공식 문서에는 이 로컬 변경 범위만 연결하고, 배포 준비·독립 Stage 검토·머지는 별도 상태로 남긴다. 사용자가 전달한 캐릭터 6종을 WebP로 압축해 연결했다. 원본은 보존하고 이 수정에서 새 캐릭터를 생성하지 않았다.
