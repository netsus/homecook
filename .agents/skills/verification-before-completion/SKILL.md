# 완료 주장 전 검증

핵심 원칙은 간단하다. **증거의 범위 안에서만 성공을 말한다.**

## 완료 게이트

완료·통과·정상·머지 가능 상태를 말하거나 커밋·PR·머지를 실행하기 전에 다음을 순서대로 수행한다.

1. 주장마다 무엇이 증명해야 하는지 적는다.
2. 그 주장을 직접 증명하는 명령이나 수동 확인을 현재 변경에서 새로 실행한다.
3. 전체 출력, 종료값, 실패·건너뜀 개수를 읽는다.
4. 결과가 주장을 직접 뒷받침하는지 확인한다.
5. 증명되지 않은 부분은 성공으로 넓히지 말고 미실행·실패·차단 상태와 이유를 보고한다.

## 서로 대체할 수 없는 증거

- 테스트 통과는 lint, typecheck, build 통과를 뜻하지 않는다.
- lint 통과는 컴파일이나 사용자 동작을 증명하지 않는다.
- build 통과는 요구사항 충족이나 회귀 테스트 존재를 증명하지 않는다.
- 일부 테스트 통과로 전체 테스트 통과를 주장하지 않는다.
- 다른 에이전트의 완료 보고나 diff 존재만으로 구현 성공을 주장하지 않는다.
- 요구사항 충족은 요청 항목을 다시 대조해야 하며, 테스트 수치 하나로 대신하지 않는다.

## 작업별 적용

- 버그 수정: 원래 증상을 재현하는 검사 또는 직접 흐름이 수정 후 통과해야 한다. 회귀 테스트를 새로 만들었다면 가능한 범위에서 수정 전 실패와 수정 후 통과를 확인한다.
- 문서·설정·스킬 변경: 파일 형식, 참조 경로, 로더가 읽는 위치, 팀원이 실행할 명령을 확인한다.
- 의존성·lint 변경: 잠금 파일, 버전 호환, 설정 로드, 실제 lint와 typecheck 결과를 각각 확인한다.
- UI 변경: 관련 자동 검사와 함께 요청 범위에 맞는 모바일·데스크톱 흐름을 확인한다.
- 리뷰: 원 저자의 성공 요약을 그대로 인용하지 말고 현재 head와 diff, 필요한 검증을 독립적으로 확인한다.

## 보고 형식

짧게 다음만 남긴다.

- 실행한 검사와 결과
- 직접 증명된 범위
- 실행하지 않았거나 증명되지 않은 범위와 남은 위험
